### 2. 템플릿 HTML/CSS sanitize 정규식 우회 — 2026-07-30 조치 완료

Enterprise 자유 HTML 편집 경로의 sanitize가 정규식 기반이어서, **따옴표 없는 이벤트 핸들러**를 걸러내지 못했다.

- 원인: `\son\w+="..."` / `'...'` 패턴만 제거 → `<img src=x onerror=alert(1)>`(무따옴표)는 통과. 허용목록에 없던 `<svg onload=…>`, `<details ontoggle=…>` 등도 통과
- 실측: 대표 벡터 6건 중 **5건이 우회**(클라이언트 `sanitizeHtmlLite`)
- 조치: 서버 `sanitize-html`(허용목록 방식) + 클라이언트 `dompurify`로 교체. `style` 속성은 CSS 정책으로 후처리(`expression()`·`behavior:`·`url(javascript:)` 제거)
- 검증: XSS 벡터 11건 전부 차단, 정상 템플릿(`.tmpl-*` 클래스·data URI 로고) 보존 확인
- 잔여 주의: **허용목록이 서버·클라이언트 두 곳에 있다.** 변경 시 양쪽을 함께 수정해야 한다(공용 패키지로 추출은 후속 과제)

### 3. 멀티테넌시 `tenantId` 격리 감사 (T-41) — 2026-08-22 조치 완료

이 시스템은 DB Row-Level Security를 쓰지 않고 **애플리케이션이 매 쿼리에 `tenantId`를 거는** 방식이다([ADR-0002](../10_ADR_의사결정기록/ADR.md)). 한 군데만 빠져도 남의 회사 규정이 새므로, 전 서비스 쿼리를 훑어 확인했다.

#### 감사 범위·방법

- 대상: `apps/api/src` 전체 Prisma 호출 **150여 곳**(모델별 호출 수 기준)
- 방법: `tenantId` 컬럼이 **있는** 모델과 **없는** 모델을 갈라서 본다. 없는 모델(`Chapter`·`Section`·`Article`·`ArticleVersion`·`PolicyAppendix`·`PolicyRevisionReason`·`VariableUsage`·`NotificationGroupMember`)은 부모를 타고 올라가야만 테넌트가 정해지므로, **부모 사슬이 실제로 검증되는지**가 핵심이다
- 의심 지점은 코드 판단에서 멈추지 않고 **살아 있는 API에 요청을 보내 재현**시켰다

#### F-1. 조문 수정·삭제에서 장(章) 소유 미확인 — 교차 테넌트 쓰기

조문 경로는 `/policies/:id/chapters/:chapterId/articles/:articleId`다. `:id`가 내 규정인지는 확인했지만 **`:chapterId`가 그 규정 소속인지는 보지 않았다.** 조문 조회 조건이 `{ id: articleId, chapterId }`뿐이라, **내 규정 id + 남의 장·조문 id** 조합이 그대로 통과했다.

- 실측: 테넌트 A가 자기 규정 id에 테넌트 B의 장·조문 id를 붙여 `PUT` → **200, 제목이 바뀜**. `DELETE` → **204, 조문이 사라짐**
- 영향: 남의 회사 규정 조문을 **읽는 게 아니라 고치고 지울 수 있었다**. 감사 로그에는 A의 정상 요청으로 남는다
- 원인: 계층이 규정 > 장 > 조문인데 검증이 한 단계 건너뛰었다. `createArticle`에는 그 검사가 있었고 `update`·`remove`에만 빠져 있었다
- 조치: 세 메서드 모두 기존 `findChapterOrThrow(tenantId, policyId, chapterId)`를 쓰도록 통일 — 검사가 한 자리에 모여 다음에 또 빠지기 어렵다

#### F-2. 첨부파일 경로 탈출 — 교차 테넌트 읽기·삭제, 컨테이너 임의 파일 접근

첨부파일 경로를 `join('/app/uploads', tenantId, id, filename)`으로 조립했다. `id`·`filename`은 URL 경로 조각이고, **Express는 라우트를 인코딩된 상태로 맞춘 뒤 값을 `decodeURIComponent`로 푼다.** 그래서 `..%2F..%2F..%2Fetc`는 `:id` 하나에 멀쩡히 매칭되고, 풀린 뒤 `join`이 경로를 정규화해 준다. 게다가 규정 소유 확인도 없었다.

- 실측(로그인만 하면 됨):
  - `GET /policies/..%2F..%2F..%2Fetc/files/hostname` → **200, `/etc/hostname` 내용 반환**
  - `GET /policies/..%2F<피해자 테넌트 id>%2F<규정 id>/files/<파일명>` → **200, 남의 회사 첨부파일 내용 반환**
  - 같은 경로로 `DELETE` → **204, 남의 파일이 삭제됨**(컨테이너의 임의 파일도 동일하게 삭제 확인)
- 영향: 테넌트 경계가 디렉터리 이름 하나에만 걸려 있어서, **경로 탈출이 곧 격리 붕괴**다. 여기에 컨테이너 임의 파일 읽기·삭제가 얹힌다
- 조치: 경로 조립을 `apps/api/src/policies/upload-path.ts`로 분리하고 세 겹으로 막았다
  1. `tenantId`·`policyId`는 **UUID 형식 검사** — 경로 조각이 될 수 있는 값이 애초에 통과하지 못한다
  2. 파일명은 **저장 규칙(영숫자·점·밑줄·붙임표)** 밖이면 거부 — 원본 파일명은 저장에 쓰지 않으므로 그 밖의 글자는 우리가 만든 적 없는 이름이다
  3. 조립 결과가 **업로드 루트 안인지 재확인** — 앞의 검사로 충분해 보여도 새 호출부가 생겼을 때 마지막 방어선이 남는다
- 함께 조치: 네 엔드포인트(업로드·목록·다운로드·삭제) 모두 **규정 소유를 먼저 확인**한다. 업로드는 multer가 핸들러보다 먼저 디스크에 쓰므로, 소유가 아니면 방금 쓴 파일을 지운다

#### 검증

- **고치기 전 코드로 되돌려 통합 8건 중 7건이 실제로 실패하는 것을 확인**했다(나머지 1건은 원래 막혀 있던 경로). 통과하는 테스트를 쌓아두는 것만으로는 막았다고 말할 수 없다
- 정상 흐름(업로드 → 목록 → 다운로드 → 삭제) 실측 회귀 없음

#### 남는 이야기

- **`tenantId` 누락은 0건이었다. 뚫린 두 곳은 모두 "테넌트는 맞는데 그 안의 부모 사슬을 안 본" 경우다.** 다음 감사도 `tenantId` 문자열을 세는 것으로는 부족하다

### 5. Google OAuth 콜백·토큰 갱신 감사 (T-42) — 2026-08-26 조치 완료

`state` 위조·재사용 방어를 보러 들어갔는데, **더 큰 것이 그 옆에 있었다.** 다섯 건을 고쳤고 전부 살아 있는 API 또는 단위 검사로 재현시켰다.

#### 5-1. `state` 가 CSRF 방어를 전혀 하지 않았다

`state` 는 원래 요청을 시작한 브라우저와 콜백을 잇는 **CSRF 방어 장치**다(RFC 6749 §10.12). 감사 전에는 `base64url(JSON.stringify({mode, tenantSlug, tenantName}))` 이 전부였다 — 서명도, 난수도, 브라우저와의 연결도, 유효시간도 없었다. 누구나 값을 지어낼 수 있고 서버는 형식만 맞으면 받아들였다.

- 성립하는 공격(**로그인 CSRF**): 공격자가 자기 계정으로 구글 인증을 시작해 콜백 URL 을 손에 넣고, 피해자에게 그 주소를 열게 한다. 피해자 브라우저에 **공격자의 토큰**이 심기고, 그 뒤 피해자가 올리는 규정·첨부파일은 공격자 조직으로 들어간다
- 조치: **서명(HMAC-SHA256) + 유효시간 10분 + 브라우저 연결**. 발급할 때 난수를 `httpOnly`·`SameSite=Lax` 쿠키에도 심고 콜백에서 대조한다. 콜백은 성패와 무관하게 쿠키를 지우므로 **같은 state 의 두 번째 사용은 실패한다**(재사용 방어)
- 검증: 단위 13건. 서명·쿠키·유효시간·쿠키부재 네 검사를 **각각 따로 빼서** 담당 테스트가 실제로 실패하는 것을 확인했다

#### 5-2. `mode=login` 이 초대 없이 남의 조직에 계정을 만들어 줬다

조직 코드만 맞으면, 그 조직에 없던 이메일에도 **`viewer` 사용자를 새로 만들었다.** 구글 계정이 있는 누구나 `?mode=login&tenantSlug=<남의회사>` 로 들어가 그 회사 규정 열람 권한을 얻을 수 있었다.

- 이것은 [SRS AUTH-6](../03_SRS_요구사항명세/SRS_요구사항명세.md)("팀원 초대는 admin만 가능")을 **정면으로 어긴다**
- 덤으로 플랜 상한도 새어 나갔다. `POST /users` 는 `maxUsersForPlan` 을 보는데 이 경로는 보지 않았다 — **T-58(템플릿 복원)·T-13(일괄 가져오기)과 같은 종류로, 이번이 세 번째다: 주 경로에는 있는 검사가 곁길에 없다**
- 조치: 초대(관리자의 사용자 생성)를 거친 계정만 들어온다. 조직이 없을 때와 초대받지 않았을 때 **같은 답**을 준다 — 다르게 답하면 조직 코드가 실재하는지 밖에서 확인할 수 있다
- 검증: 단위 15건. 되돌리면 4건이 실패한다

#### 5-3. 구글이 확인하지 않은 이메일을 그대로 믿었다

`profile.emails[0].value` 만 읽고 `email_verified` 는 보지 않았다. 확인되지 않은 주소로 남의 이메일을 주장하면 그 사람의 기존(비밀번호) 계정에 **영구히 연결**됐다. 조치: 다른 모든 판단보다 먼저 확인 여부를 본다.

#### 5-4. 갱신 토큰의 서명·만료를 아무도 보지 않았다

컨트롤러가 JWT 페이로드를 **검증 없이 잘라** `sub` 를 꺼내 서비스로 넘겼다. 저장값과 문자열 비교를 하고 있어 위조는 막혔지만, **만료는 어디서도 보지 않았다** — `JWT_REFRESH_EXPIRES_IN=7d` 가 장식이었다.

- 실측(조치 전): 만료된 토큰을 저장값에 넣고 갱신 요청 → **200**. 조치 후 **401**
- 형식이 어긋난 값(`abc`, `a.b`, `a.!!!.c`)은 그 자리에서 터져 **500**. 조치 후 **401**, 빈 문자열은 **400**
- 조치: `verifyAsync` 로 서명·만료를 실제로 검증한 뒤 그 `sub` 를 쓴다

#### 5-5. 토큰 회전이 회전이 아니었다

`jti` 가 없어 같은 초에 두 번 발급된 토큰이 **글자까지 똑같았다**(`iat` 가 초 단위). 갱신해도 옛 토큰이 그대로 살아 있고, 저장값 비교로 폐기할 방법도 없었다. 통합 테스트를 쓰다가 드러났다. 조치: 매 발급에 `jti`(UUID)를 넣는다.

#### 5-6. 대문자가 섞인 이메일로 가입하면 다시 로그인할 수 없었다

보안 결함은 아니지만 감사 중에 드러났고, 5-2 조치와 맞물린다. 로그인은 이메일을 소문자로 낮춰서 찾는데(`LoginDto` 의 `@Transform`), **가입과 사용자 생성은 입력을 그대로 저장했다.**

- 실측(조치 전): `Alice@Co.Test` 로 가입 → 201, 토큰 발급. 이후 `Alice@Co.Test` 로 로그인 **401**, `alice@co.test` 로도 **401**. 즉 **가입은 되는데 그 계정으로는 두 번 다시 들어갈 수 없다**
- 5-2 와의 관계: 관리자가 대문자를 섞어 팀원을 만들면, 그 사람은 구글 로그인에서도 찾히지 않아 "초대받지 않음"으로 막힌다
- 조치: `RegisterDto`·`CreateUserDto` 의 이메일에도 로그인과 같은 정규화(trim + 소문자)를 건다
- 검증: 통합 2건. 대문자·소문자·공백 섞인 세 표기로 모두 로그인되는 것 확인
- **운영 확인 필요**: 이미 대문자로 저장된 계정이 있다면 지금도 잠겨 있다. 배포 전에 `SELECT count(*) FROM users WHERE email <> lower(email);` 로 확인할 것(개발 DB 는 0건). 있다면 같은 테넌트에 소문자 계정이 이미 있는지 보고 수동 정리해야 한다 — 단순 `lower()` 일괄 갱신은 유니크 제약(`tenantId+email`)에 걸릴 수 있다

#### 부수 조치

- **콜백이 `state` 를 코드 교환보다 먼저 본다.** 예전에는 교환이 끝난 뒤에 봤다 — 위조 콜백 하나가 매번 구글로 나가는 요청을 만들었다는 뜻이다. 지금은 state 부터 보고 바로 끊는다
- **실패 사유를 화면까지 전달한다.** 예전에는 무엇이 문제든 "다시 시도하세요" 하나였다. 초대받지 않은 사용자는 영원히 재시도했다

#### 남는 이야기 (조치하지 않음 — 결정 필요)

- **토큰이 URL 쿼리로 배달된다.** 콜백이 `/oauth/callback?access_token=…&refresh_token=…` 으로 리다이렉트한다. 브라우저 히스토리·프록시 접근 로그·Referer 로 샐 수 있다(화면이 곧바로 `replaceState` 로 지우지만 완전하지는 않다). 고치려면 **세션 전달 방식 자체**를 바꿔야 한다(일회용 교환 코드 또는 httpOnly 쿠키) — 프런트 인증 저장소·axios 클라이언트까지 걸리는 설계 변경이라 별도 결정으로 남긴다. 기술부채 #12
- **CORS 가 `origin: true` + `credentials: true`** 다. 지금은 인증이 Bearer 토큰이라 악용되지 않지만, 쿠키 기반으로 옮기는 날 그대로 CSRF 구멍이 된다. 기술부채 #13
