01한눈에 보기

전체 시스템을 한 장으로 본 그림이다. 파란 판 위가 서버 한 대이고, 그 위의 타일 하나가 각각 컨테이너 하나다. 판 바깥은 외부 주체다.

이 그림에서 바로 읽어야 할 것 세 가지:

  • 브라우저는 web만 직접 만난다. api는 nginx 뒤에 있고, 외부에서 오는 모든 요청은 /api/ 프록시를 거친다.
  • python3는 별도 컨테이너가 아니라 api 안에 같이 산다. PDF 생성·추출을 위해 Node가 자식 프로세스로 부른다 (08절).
  • CI는 검증까지만 한다. 점선이 배포가 아니라는 뜻이다 — 실제 배포는 아직 사람이 docker compose build로 한다.
눈에 띄는 것 redis는 컨테이너로 떠 있는데 들어오는 화살표가 없다. 애플리케이션 코드에 참조가 0건이라 그림에도 그대로 비워 뒀다 (13절 구조적 부채).

인증(Google OAuth)·플랜 게이팅·버전 워크플로처럼 그림 한 장에 넣으면 오히려 읽기 어려워지는 것들은 아래 각 절에서 따로 다룬다.

02개요

policy_manager는 회사(테넌트) 단위 멀티테넌트 SaaS다. 하나의 백엔드·DB를 여러 테넌트가 공유하고 모든 핵심 테이블의 tenantId 컬럼으로 데이터를 격리한다. 단일 호스트 Docker Compose 배포를 기준으로 설계돼 있으며, 브라우저는 nginx(web)만 직접 호출하고 nginx가 /api/를 NestJS(api)로 프록시한다.

도메인의 중심은 법령 구조를 따르는 규정 문서다. 규정 → 장(章) → 절(節) → 조(條) → 항 → 목 계층을 표현하고, 조문 단위 버전 관리·승인 워크플로·시점 조회를 제공한다.

04요청 처리 경로

모든 요청은 AppModule에 등록된 전역 가드 4단을 통과한다. 순서가 곧 의미다 — 먼저 신원을 확인하고, 요금제 한도를 보고, 역할을 보고, 마지막에 호출량을 본다.

데코레이터대상 가드효과
@Public()JwtAuthGuard인증 없이 접근 허용 (로그인, 공개 브랜딩 등)
@MinPlan('pro')PlanGuard지정 등급 미만 테넌트는 차단
@Roles('admin')RolesGuard테넌트 내 역할 제한
@PlatformRoles('global_admin')RolesGuardSaaS 운영자 전용 경로

컨트롤러 진입 전 전역 ValidationPipe가 DTO를 검증한다 (whitelist, forbidNonWhitelisted, transform) — DTO에 선언되지 않은 필드는 조용히 버려지는 게 아니라 요청 자체가 거부된다.

기동 시 시크릿 검증

main.ts는 Nest 앱을 만들기 전에 assertProductionSecrets()를 호출한다. NODE_ENV=production인데 리포에 공개된 기본 시크릿 (JWT_SECRET, JWT_REFRESH_SECRET, MINIO_SECRET_KEY)이 그대로면 경고가 아니라 기동 실패다. JWT 키는 최소 32자 길이도 함께 본다. 로컬 기본값 편의와 운영 사고 방지를 동시에 얻기 위한 장치다.

07도메인 모델

규정 문서 구조가 이 시스템의 핵심이다. 법령은 편 > 장 > 절 > 조 > 항 > 목 체계를 따르지만, 사내 규정은 이 체계를 반드시 다 쓰지는 않는다. 그래서 상위 계층을 모두 선택(nullable)으로 뒀다.

계층표현 방식필수 여부
장(章)Chapter 테이블필요. 단 suppressHeader로 출력에서 숨겨 "장 없는 규정"을 만들 수 있다
절(節)Section 테이블선택 Article.sectionId가 nullable
조(條)Article.number필수
항Article.clauseNumber선택 같은 테이블의 nullable 컬럼
목Article.itemNumber선택 같은 테이블의 nullable 컬럼

조·항·목을 별도 테이블로 쪼개지 않고 한 테이블에 담은 이유는, 실무에서 조와 항이 서로 승격·강등되는 편집이 잦기 때문이다. 계층을 테이블로 고정하면 그때마다 행을 옮겨야 한다. 배경은 ADR-0011 참고.

시점 조회 (as-of)

"2024년 3월 시점의 이 규정"을 재구성하는 기능이다. GET /api/policies/:id/effective-dates가 해당 규정에 존재하는 시행일 목록을 주고, GET /api/policies/:id/as-of?date=…가 그 시점에 유효했던 조문 집합을 조립한다. 국가법령정보센터의 시점 조회와 같은 개념이다.

08데이터베이스 · 마이그레이션

  • PostgreSQL 15, 확장 pg_bigm (한국어 2-gram 검색 성능)
  • Prisma 모델 24개 — 상세는 08_ERD 테이블명세서
2026-08-02 baseline 스쿼시 마이그레이션 13건을 00000000000000_init(전체 스키마) + 00000000000001_enable_pgbigm 2건으로 정리했다. 빈 DB에서 prisma migrate deploy만으로 전체 스키마가 재현되며 드리프트 0으로 확인했다. db push --accept-data-loss 폴백은 제거했다. (ADR-0012)

이 변경으로 얻은 것:

  • prisma migrate dev가 정상 동작한다(섀도 DB 재생 가능) — 더 이상 SQL을 손으로 쓰지 않는다
  • baseline 이전에 만들어진 DB는 기동 시 1회 자동 처리된다: migrate deploy 실패 → 기존 스키마 감지 → 옛 이력 행 정리 → baseline을 applied로 표시 → 재시도
  • 마이그레이션이 끝내 실패하면 컨테이너가 종료된다. 예전처럼 db push로 넘어가 데이터를 덮어쓰지 않는다
한계 Prisma 마이그레이션에 down 스크립트가 없다. 스키마 롤백은 자동화 불가이므로 배포 전 pg_dump 백업이 사실상 유일한 안전장치다. 절차는 16_Runbook 7절 참고.

09외부 프로세스 연동 (Node ↔ Python)

PDF 입출력은 Node 생태계보다 파이썬 쪽이 압도적으로 낫다. 그래서 api 컨테이너 안에 python3와 PyMuPDF·pdfplumber를 함께 설치하고, Node가 자식 프로세스로 호출한다. 의존성은 apps/api/scripts/requirements.txt 단일 소스로 관리한다.

용도호출부스크립트호출 방식
규정 PDF 내보내기 policies/policy-pdf.service.ts scripts/pdf_render.py spawn (비동기)
업로드 PDF 텍스트 추출 regulation-parse/regulation-parse.service.ts scripts/ 추출기 spawnSync (동기)
주의 spawnSync는 자식 프로세스가 끝날 때까지 Node 이벤트 루프를 멈춘다 — 한 테넌트의 대용량 PDF 파싱이 다른 모든 테넌트의 요청을 대기시킨다. PDF 내보내기 쪽은 spawn으로 처리했으나 파싱 쪽은 아직 동기 호출이 남아 있다.

PDF 렌더링 설계

  • 입력: stdin으로 JSON(html, title, metaLine, pageNumbers) → 출력: stdout으로 PDF 바이트
  • 한글 폰트는 PyMuPDF wheel에 동봉된 CJK 폰트(Droid Sans Fallback)를 그대로 쓴다 — 컨테이너에 폰트를 따로 설치할 필요가 없다
  • 텍스트가 이미지가 아니라 실제 문자로 남아 검색·복사가 된다
  • 저장 직전 subset_fonts()로 실제 사용 글자만 임베드 (약 3.5MB → 수십 KB)
베이스 이미지 컨테이너 베이스가 Alpine이 아니라 node:20-slim(Debian)인 이유가 여기 있다. PyMuPDF는 musllinux(Alpine) wheel을 제공하지 않아 소스 빌드로 넘어가다 실패한다. Dockerfile은 --only-binary=:all:로 소스 빌드를 아예 차단해, wheel이 없으면 런타임이 아니라 빌드 시점에 실패하게 만든다. (ADR-0013)

10인프라 · 배포

이미지 빌드

  • api 빌드 컨텍스트는 리포 루트다. 워크스페이스 락파일(package-lock.json)이 루트에만 있어서, 컨텍스트가 apps/api이면 npm install이 매번 새로 해석된다
  • 설치는 npm ci --workspace=apps/api — 락파일 기준 재현 설치
  • 빌더·런너 모두 node:20-slim — 같은 베이스여야 builder가 만든 Prisma 엔진을 런너가 그대로 쓴다

기동 시퀀스

  1. assertProductionSecrets() — 기본 시크릿이면 즉시 종료
  2. prisma migrate deploy
  3. (2가 실패하고 기존 스키마가 있으면) baseline 자동 처리 후 재시도
  4. 그래도 실패하면 FATAL 종료 — 데이터를 덮어쓰지 않는다
  5. 데모 데이터 시드
  6. node dist/main

시크릿 주입

docker-compose.yml은 모든 시크릿을 ${VAR:-기본값} 형태로 바꿔 .env 주입을 우선하도록 했다. 로컬은 기본값으로 그냥 뜨고, 운영은 .env로 덮는다. 운영값 생성은 npm run secrets:init.

상세 배포·롤백 절차는 16_Runbook 배포·롤백 참고.

11인증 · 권한

테넌트 역할 (Role)

  • admin — 테넌트 전체 관리
  • editor — 규정 작성·편집
  • viewer — 열람·검색만

플랫폼 역할 (PlatformRole)

  • none — 일반 사용자
  • global_admin — SaaS 운영자,
    테넌트 간 통합 콘솔 접근

인증 방식

  • 이메일 / 비밀번호 (bcrypt)
  • Google OAuth
  • JWT access + refresh (자동 갱신)

두 축은 독립이다. 테넌트 역할은 "이 회사 안에서 무엇을 할 수 있는가", 플랫폼 역할은 "서비스 운영자인가"를 뜻한다. RolesGuard 하나가 두 데코레이터를 모두 처리한다.

12멀티테넌시 · 플랜

모든 핵심 테이블에 tenantId FK를 두어 격리한다. DB 레벨 RLS는 적용하지 않았고, 애플리케이션 레벨 필터링에 의존한다.

리스크 쿼리 한 곳에서 tenantId 조건을 빠뜨리면 타 회사 규정이 노출된다. 코드 리뷰로만 막고 있는 상태다 — 전수 감사가 작업관리대장 T-41로 잡혀 있다. 상세는 15_보안 검토서 참고.

GitHub Actions가 main·develop에 대한 push / PR마다 두 개의 job을 돌린다. 같은 브랜치에 연속 push하면 앞선 실행은 취소된다.

14구조적 부채

기능 부족이 아니라 아키텍처 차원에서 남아 있는 항목만 정리한다. 전체 목록은 13_기술부채 대장.

항목내용영향추적
테넌트 격리가 앱 레벨에만 존재 DB RLS 미적용, 쿼리마다 tenantId 조건에 의존 높음 T-41
