# 코드리뷰 체크리스트

작성일: 2026-07-21
근거: policy_manager 실제 아키텍처(멀티테넌시, 플랜 게이팅, Prisma) 기준. 대표·개발자1·PM이 서로 리뷰할 때 공통으로 확인.

## 공통

- [ ] 변경 범위가 요청받은 작업(SRS/WBS 항목)과 일치하는가, 불필요한 리팩터링이 섞여있지 않은가
- [ ] 하드코딩된 시크릿·API 키가 추가되지 않았는가
- [ ] 신규 환경 변수를 추가했다면 `.env.example`과 [07_env.example 변경이력](../07_env.example/env_변경이력.md)에 반영했는가

## 백엔드 (NestJS/Prisma)

- [ ] 새 쿼리/서비스 메서드가 **`tenantId`로 필터링**되는가 (테넌트 간 데이터 노출 방지 — [08_ERD_테이블명세서](../08_ERD_테이블명세서/ERD_테이블명세서.md) 참고)
- [ ] 새 라우트에 인증/역할 가드(`@Roles`/`@PlatformRoles`/`@Public`)가 의도대로 붙어 있는가
- [ ] 요청 DTO에 `class-validator` 검증이 있는가 (빈 값, 길이, enum 범위 등)
- [ ] 스키마 변경 시 `prisma migrate dev`로 마이그레이션 파일을 생성했는가 (db push에만 의존하지 않는가)
- [ ] 플랜별 제한(Starter/Pro/Enterprise)이 관련된 기능이면 `plan-limits.ts` 또는 가드로 제한을 적용했는가
- [ ] 에러 응답이 사용자에게 내부 구현(스택트레이스, 쿼리 등)을 노출하지 않는가

## 프론트엔드 (React)

- [ ] 새 페이지/기능이 로딩·빈 상태·에러 상태를 `LoadingBlock`/`EmptyState`/toast 패턴으로 처리하는가
- [ ] 서버 상태는 TanStack Query, 클라이언트 상태는 Zustand로 일관되게 분리했는가
- [ ] 새 텍스트를 `i18n/messages.ts`에 등록했는가 (하드코딩 금지)
- [ ] 역할별 접근 제어가 필요한 화면이면 `App.tsx`의 `PrivateRoute` 로직과 일치하는가
- [ ] 색상·스타일은 Tailwind 유틸리티 또는 기존 CSS 변수 토큰을 사용했는가 (임의 색상 하드코딩 지양)

## 배포 영향

- [ ] docker-compose 환경변수/포트 변경이 있다면 [16_Runbook_배포롤백](../16_Runbook_배포롤백/Runbook_배포롤백.md)에 반영했는가
- [ ] 마이그레이션이 있다면 운영 배포 시 `prisma migrate deploy` 절차로 검증했는가
