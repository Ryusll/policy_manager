# 개발컨벤션

작성일: 2026-07-21
근거: 현재 코드베이스에서 실제로 지켜지고 있는 패턴을 문서화. 일부 항목은 팀 확정이 필요한 "미정"으로 표시.

## 1. 공통

- 파일 인코딩/개행: UTF-8, LF, 파일 끝 개행 1개, 줄 끝 공백 제거 (`.editorconfig` 기준)
- 언어: 코드/식별자는 영문, 주석·UI 텍스트·문서는 한국어 위주 (일부 영문 병기, i18n으로 en 지원)

## 2. 백엔드 (`apps/api`, NestJS)

- 모듈 단위 폴더 구조: `<도메인>/​<도메인>.module.ts`, `.controller.ts`, `.service.ts`, `.dto.ts` (예: `policies/policies.controller.ts`)
- 컨트롤러: `@Controller('<kebab-case-경로>')`, 라우트 인증은 기본적으로 전역 가드가 적용되므로 예외적으로 공개할 라우트에만 `@Public()` 명시
- 권한: 테넌트 역할 제한은 `@Roles('admin' | 'editor' | 'viewer')`, 플랫폼 전용은 `@PlatformRoles('global_admin')`으로 라우트에 명시
- DTO: `class-validator` 데코레이터로 검증, 전역 `ValidationPipe`가 whitelist/forbidNonWhitelisted를 적용하므로 DTO에 없는 필드는 자동 거부됨 — 새 필드 추가 시 DTO 갱신 필수
- Prisma 스키마: 모델 필드는 camelCase, DB 컬럼은 `@map("snake_case")`로 매핑 (예: `tenantId` → `tenant_id`). 테이블명은 `@@map("snake_case_복수형")`
- 신규 필드/테이블 추가 시 반드시 `prisma migrate dev`로 마이그레이션 파일을 생성해 커밋할 것 (현재 baseline 마이그레이션 부재로 `db push` 폴백에 의존 중인 상태이므로, 최소한 신규 변경부터는 마이그레이션 파일을 남겨 기술부채를 키우지 않는다)
- 플랜별 제한값은 `apps/api/src/common/plan-limits.ts`에 함수로 모아 관리 (하드코딩 금지)

## 3. 프론트엔드 (`apps/web`, React)

- 폴더 구조: `pages/`(라우트 단위 화면), `components/`(공용·개별 컴포넌트, `components/ui/`는 범용 UI), `stores/`(Zustand), `hooks/`(React Query 훅), `api/`(axios 클라이언트), `lib/`(순수 로직), `i18n/`
- 서버 상태는 TanStack Query, 클라이언트/영속 상태는 Zustand 사용 (서버 상태를 Zustand에 직접 저장하지 않음)
- 공용 UI는 `components/ui/*` 재사용 우선 (`PageHeader`, `EmptyState`, `LoadingBlock`, `ToastHost`) — 새 페이지 작성 시 이 패턴을 따를 것
- 스타일: Tailwind 유틸리티 우선, 테마 색상은 하드코딩 대신 CSS 변수 기반 클래스(`navy-*`, `gold-*`, `index.css`의 `.btn-*`/`.badge-*`/`.stat-card` 등) 사용
- 다국어 텍스트는 `i18n/messages.ts`에 키로 등록, 컴포넌트에 하드코딩 금지
- 라우트 접근 제어는 `App.tsx`의 `PrivateRoute`에서 일괄 관리 (개별 페이지에서 role 분기 로직 중복 작성 지양)

## 4. Lint / 포맷

- `npm run lint` 스크립트가 양쪽 앱에 존재하나, 현재 저장소에 `.eslintrc*`/`eslint.config.*` 설정 파일이 없어 실제로는 기본 설정 또는 미동작 상태 — 설정 파일 추가가 필요함 ([기술부채 대장](../13_기술부채대장/기술부채_대장.md) 참고)
- Prettier 설정 없음 — 팀 확정 필요 (미정)

## 5. 브랜치 / 커밋 (미정)

현재 git 저장소가 초기화되어 있지 않아(로컬 파일 기반) 브랜치 전략·커밋 메시지 규칙이 정해진 바 없음. git 도입 시 다음을 확정할 것:
- 브랜치 전략 (예: main + 기능 브랜치)
- 커밋 메시지 규칙 (예: 접두사 `feat/fix/docs/chore`)
- PR/코드리뷰 여부 — [14_코드리뷰체크리스트](../14_코드리뷰체크리스트/코드리뷰체크리스트.md) 참고
