# SRS (요구사항 명세)

작성일: 2026-07-21
근거: 실제 구현(코드) 역산 + `docs/VEDA_FeatureList.docx`. 이미 구현된 동작을 "현재 구현된 요구사항"으로 정리했으며, 신규 요구사항 추가 시 이 문서에 이어서 작성한다.

## 1. 인증·사용자 (REQ-AUTH)

| ID | 요구사항 |
|---|---|
| AUTH-1 | 이메일/비밀번호로 회원가입(신규 테넌트+최초 admin) 및 로그인 가능해야 한다 |
| AUTH-2 | Google OAuth로 로그인/가입 가능해야 하며, `GOOGLE_CLIENT_ID/SECRET` 미설정 시 503으로 명확히 응답해야 한다 |
| AUTH-3 | JWT access/refresh 토큰을 발급하고, refresh 토큰으로 재발급이 가능해야 한다 |
| AUTH-4 | 테넌트 내 역할은 admin/editor/viewer 3종이어야 하며, viewer는 검색·규정상세·소개 화면만 접근 가능해야 한다 |
| AUTH-5 | `global_admin` 플랫폼 역할을 가진 사용자만 통합 관리자 화면·API에 접근 가능해야 한다 |
| AUTH-6 | 팀원 초대(사용자 생성)는 admin만 가능해야 한다. **플랜별 허용 범위는 미결이다** — 현재 코드는 플랜을 보지 않고(`POST /users` 에 `@MinPlan` 없음) 상한(`maxUsersForPlan`)만 강제해 Starter 도 10명까지 만들 수 있다. 기획서·이 문서·API명세서는 "Starter 불가/Pro+"라고 적어 왔으나 **코드와 통합 테스트(T-59 매트릭스)는 플랜 무관**이다. 유료 경계이므로 가격 정책과 함께 정할 것 — **D-07** |
| AUTH-7 | **조직 합류 경로는 admin의 사용자 생성 하나뿐이어야 한다.** Google 로그인은 이미 있는 계정에 신원을 연결할 뿐 계정을 만들지 않는다(`mode=register`로 새 조직을 만드는 경우는 예외). AUTH-6을 우회하는 경로가 생기지 않도록 하는 불변식 — [ADR-0018](../10_ADR_의사결정기록/ADR.md) |
| AUTH-8 | OAuth `state`는 서명·유효시간·브라우저 연결(쿠키)을 모두 검증해야 하며, 한 번 쓴 `state`는 재사용되지 않아야 한다 |
| AUTH-9 | refresh 토큰은 서명과 만료를 검증해야 하며, 갱신 시 반드시 새 토큰으로 회전되어야 한다 |

## 2. 규정·조문 구조 (REQ-POLICY)

| ID | 요구사항 |
|---|---|
| POLICY-1 | 규정은 코드(테넌트 내 유일)·제목·설명·담당부서·분류·개정일·시행일을 가져야 한다 |
| POLICY-2 | 규정은 장(Chapter) → 절(Section) → 조(Article, 조 루트) → 항(clauseNumber) → 목(itemNumber) 계층을 지원해야 한다 |
| POLICY-2a | **장·절은 선택, 조는 필수**여야 한다. 사내 규정은 법령의 `편>장>절>조` 구조를 반드시 따르지 않으므로, 장을 만들지 않고 조부터 바로 추가할 수 있어야 한다 (2026-08-02 대표 지시) |
| POLICY-2b | 절(節)은 장에 속하는 선택 계층이며, 절에 속하지 않는 조가 같은 장에 공존할 수 있어야 한다 |
| POLICY-3 | 행 유형은 `clauseNumber`/`itemNumber` null 여부로 판별되어야 한다 (조 루트: 둘 다 null / 항: clauseNumber만 있음 / 목: itemNumber 있음) |
| POLICY-4 | 항·목은 제목 없이 본문만으로 등록 가능해야 한다 |
| POLICY-5 | 조 루트 없이 제목+1항을 동시 입력하면 조 제목 행과 1항 본문 행이 자동 분리 생성되어야 한다 |
| POLICY-6 | 장은 `suppressHeader` 설정 시 목차·전문·인쇄에서 장 제목을 숨겨야 한다. 장 없이 조부터 만든 규정은 이 숨김 장을 사용하며, 가져오기 시에도 원문에 장이 없으면 임의의 "제1장 총칙"을 만들지 않아야 한다 |
| POLICY-7 | 조문에는 판례/법령/규칙 참조 여부(플래그)와 근거 메모를 기록할 수 있어야 한다 |
| POLICY-8 | 부칙·별표·서식(PolicyAppendix)을 정렬 순서와 함께 CRUD할 수 있어야 한다 |
| POLICY-9 | 규정 첨부파일을 업로드·다운로드·삭제할 수 있어야 한다. 표시 이름은 올린 그대로여야 하고(한글 포함), 업로드·삭제는 감사 로그에 남아야 한다 (T-90) |
| POLICY-9a | **저장 위치는 미결이다.** 코드는 API 컨테이너의 로컬 볼륨(`/app/uploads`)에 저장한다 — MinIO 클라이언트도, `STORAGE_TYPE` 을 읽는 코드도 없다. compose 는 MinIO 컨테이너와 자격증명을 넘기지만 쓰이지 않는다. **API 를 2대 이상으로 늘리면 첨부가 인스턴스별로 갈린다.** 오브젝트 스토리지로 옮길지 로컬 저장을 정식으로 확정할지 결정 필요 — **D-06** |
| POLICY-10 | 조·항·목 표기는 법령 관례를 따라야 한다: **조 = `제N조`, 항 = `①②…`, 목 = `1. 2. …`** (`legalArticleLabel.ts`, 2026-08-02 대표 확인 — 기구현) |
| POLICY-11 | 규정은 개정일과 시행일을 **각각 구분해** 관리·표시해야 한다(단일 "기준일" 아님) (기구현) |
| TPL-7 | 출력 양식의 결재란(작성·검토·승인 서명 칸)은 **선택 항목**이어야 하며 기본값은 표시하지 않음이어야 한다. 결재란을 쓰지 않는 고객사가 있기 때문 (`showApprovalLine`, 기본 `false` — 2026-08-02 대표 확인, 기구현) |

## 3. 버전·개정 워크플로 (REQ-VERSION)

| ID | 요구사항 |
|---|---|
| VER-1 | 조문 버전 상태는 draft → review → published → archived 순으로 전이해야 한다 |
| VER-2 | 시행 승인(published 전환) 시 승인 사유가 필수여야 하며, 기존 published 버전은 자동으로 archived 되어야 한다 |
| VER-3 | 두 버전 간 diff를 줄 단위/단어 단위로 비교할 수 있어야 한다 |
| VER-4 | 검토 반려(reject)와 버전 폐지(archive)를 화면에서 처리할 수 있어야 한다. **반려는 사유가 필수**이며 되돌린 초안에 그대로 보여야 하고(`ArticleVersion.reviewNote`), 폐지 시 마지막 게시본이면 경고해야 한다 (T-10, 2026-08-23) |
| VER-5 | 템플릿 변수(`{{VAR}}`) 사용은 버전 단위로 자동 추적(VariableUsage)되어야 한다 |

## 4. 가져오기 (REQ-IMPORT)

| ID | 요구사항 |
|---|---|
| IMPORT-1 | TXT/DOCX/PDF 업로드 또는 텍스트 붙여넣기로 규정을 가져올 수 있어야 한다 |
| IMPORT-2 | 파싱 프로필(혼합형/한국형/영문형)과 분할 모드(auto/blank_block/line_each/delimiter/markdown)를 선택할 수 있어야 한다 |
| IMPORT-3 | 가져오기 전 장/조문 인식 결과를 미리보기로 확인할 수 있어야 한다 |
| IMPORT-4 | 가져오기는 항(①②…)·목(1. 2. …) 패턴을 인식해 `clauseNumber`/`itemNumber`를 자동으로 채워야 한다. 「항·목 자동 인식」 옵션으로 끌 수 있고, 인식 결과 개수를 등록 전에 안내해야 한다 (2026-07-30 구현) |
| IMPORT-5 | 가져오기 이력(PolicyImportLog)이 테넌트별로 기록·조회되어야 한다 |

## 9. 브랜딩 (REQ-BRAND)

| ID | 요구사항 |
|---|---|
| BRAND-1 | 테넌트(고객사) 브랜딩(로고·브랜드 마크 1~2자·로고 크기·테마 색)을 편집할 수 있어야 하며, Pro+ 플랜에서만 편집 가능해야 한다. 로고·마크는 **관리자만** 편집할 수 있다(회사 전체에 반영되므로) |
| BRAND-2 | 테넌트 브랜딩(로고·브랜드 마크·로고 크기)은 서버(`TenantBranding`)에 저장되어 기기·브라우저를 바꿔도 유지되고 구성원 전체에 동일하게 적용되어야 한다. 조회는 모든 구성원, 저장은 관리자+Pro 이상 ([ADR-0014](../10_ADR_의사결정기록/ADR.md)) |
| BRAND-3 | 플랫폼(운영사) 브랜딩(법인명·사업자번호·제품명·로고·lockup)은 `global_admin`이 편집하고 서버(PlatformBranding)에 저장되어야 한다 |
| BRAND-4 | 플랫폼 브랜딩은 비로그인 상태에서도 조회 가능한 공개 API(`GET /platform-branding`)로 제공되어 로그인·푸터에 표시되어야 한다 |
| BRAND-5 | 테마 색은 아직 브라우저 localStorage 전용이다 — 서버 동기화 범위 밖(알려진 제한) |

## 10. 감사 로그 (REQ-AUDIT)

| ID | 요구사항 |
|---|---|
| AUDIT-1 | 주요 변경(버전 승인, 플랜 변경, 사용자 생성/역할 변경, 템플릿 변경, 벌크 임포트 등)은 AuditLog에 기록되어야 한다 |

## 11. 멀티테넌시·플랜·결제 (REQ-TENANT)

| ID | 요구사항 |
|---|---|
| TENANT-1 | 모든 핵심 데이터는 `tenantId`로 격리되어야 하며, 한 테넌트의 사용자가 다른 테넌트 데이터에 접근할 수 없어야 한다 |
| TENANT-2 | 플랜별 규정 개수·사용자 수 상한이 강제되어야 한다 (Starter 5규정/10명, Pro 10,000규정/50명, Enterprise 사실상 무제한) |
| TENANT-3 | 플랜 변경(업그레이드)은 결제 프로바이더에 따라 동작해야 한다: `mock`(기본)은 즉시 반영, 그 외 프로바이더는 `PAYMENT_HOSTED_CHECKOUT_URL`로 리다이렉트 후 웹훅(`payment.succeeded`, 시크릿 검증)으로 반영한다 |
| TENANT-4 | 결제 처리 결과는 `tenant.plan` 갱신·감사 로그와 함께 **결제 이력/구독(BillingPayment·BillingSubscription·BillingCustomer)에 기록**되어야 하며, `planExpiresAt` 은 구독 종료일로 채워져야 한다. 같은 요금제 재결제는 구독을 연장하고, 요금제 변경은 이전 구독을 닫고 새로 연다. **mock 결제는 0원으로 기록**한다(요금표를 지어내면 이력이 그럴듯하게 거짓이 된다) (T-17, 2026-08-23) |
| TENANT-5 | `global_admin`은 통합 관리 콘솔에서 테넌트 목록·플랜·사용자 역할을 관리할 수 있어야 한다 |

## 12. 비기능 요구사항 (REQ-NFR)

| ID | 요구사항 |
|---|---|
| NFR-1 | API 요청은 100 req/min으로 레이트리밋되어야 한다 (ThrottlerGuard) |
| NFR-2 | 모든 입력은 서버에서 whitelist 검증되어야 하며, DTO에 없는 필드는 거부되어야 한다 |
| NFR-3 | 헬스체크(`/api/health`) 엔드포인트를 제공해 컨테이너 오케스트레이션이 상태를 확인할 수 있어야 한다 |
| NFR-4 | UI는 한국어/영어를 지원해야 한다 |
| NFR-5 | 핵심 워크플로(로그인, 규정 CRUD, 버전 승인, 테넌트 격리, 플랜×권한)에 자동화 테스트가 있어야 하며 CI 에서 돌아야 한다 — **단위 337 · 통합 234**(2026-08-30), CI 는 typecheck·lint·test·build·PDF 렌더러·통합 6단계 (T-30·T-31·T-32) |

## 13. 범위 밖 (알려진 미구현)

2026-07-21 코드 실사 기준. 아래는 요구사항에서 제외하고 향후 과제로 관리한다.

### 13.1 코드가 없거나 스키마만 있는 것
| 항목 | 실제 상태 |
|---|---|
| ~~규정 내보내기(Export)~~ | **2026-08-23 정리**(T-16 · [ADR-0015](../10_ADR_의사결정기록/ADR.md)). 빈 `ExportModule` 과 미사용 `ExportJob` 테이블 제거. 내보내기는 **동기**로 확정(PDF 는 응답 본문으로 반환), 이력은 감사 로그 `policy.export.pdf` 로 남긴다 |
| ~~결제 이력·구독 관리~~ | **2026-08-23 해소**(T-17). 결제 시 세 테이블에 기록하고 `planExpiresAt` 을 구독 종료일로 채운다. `GET /billing/history` + 요금제 모달에 이력 표시. **mock 결제는 0원으로 남는다**(테스트 결제 표시) |
| 실 PG 연동 | mock 즉시 반영, 또는 범용 hosted-checkout 리다이렉트+웹훅 골격만 존재. 특정 PG사(토스/아임포트 등) SDK 연동은 없음 |

### 13.2 백엔드 API는 있으나 UI가 없는 것
