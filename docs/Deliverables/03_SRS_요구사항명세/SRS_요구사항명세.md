## 1. 인증·사용자 (REQ-AUTH)

| ID | 요구사항 |
|---|---|
| AUTH-1 | 이메일/비밀번호로 로그인 가능해야 한다. **고객사(조직)와 그 첫 관리자(마스터)는 아스트룸이 통합 관리자 콘솔에서 개설한다**(2026-10-08 PM 결정, T-122). 누구나 새 조직을 만드는 **공개 회원가입은 운영에서 닫혀 있고**(`ALLOW_PUBLIC_SIGNUP` 미설정 = 닫힘) 개발·테스트에서만 연다. 닫힌 서버에서는 구글로 새 조직을 만드는 경로도 막힌다 |
| AUTH-2 | Google OAuth로 로그인/가입 가능해야 하며, `GOOGLE_CLIENT_ID/SECRET` 미설정 시 503으로 명확히 응답해야 한다 |
| AUTH-3 | JWT access/refresh 토큰을 발급하고, refresh 토큰으로 재발급이 가능해야 한다 |
| AUTH-4 | 테넌트 내 역할은 admin/editor/viewer 3종이어야 하며, viewer는 검색·규정상세·소개 화면만 접근 가능해야 한다 |
| AUTH-5 | `global_admin` 플랫폼 역할을 가진 사용자만 통합 관리자 화면·API에 접근 가능해야 한다 |
| AUTH-6 | 팀원 초대(사용자 생성)는 admin만 가능해야 한다. **플랜과 무관하다** — 마스터가 직원 계정을 만들어 나눠 주는 제품이라 Starter 고객사도 발급할 수 있어야 하고, 플랜 차이는 사용자 상한(`maxUsersForPlan`: Starter 10 / Pro 50)으로만 둔다. (D-07 정리 — 2026-10-08 PM 결정, 화면 개방은 T-122. 그 전까지 문서는 "Starter 불가/Pro+", 코드는 플랜 무관으로 어긋나 있었다) |
| AUTH-7 | **조직 합류 경로는 admin의 사용자 생성 하나뿐이어야 한다.** Google 로그인은 이미 있는 계정에 신원을 연결할 뿐 계정을 만들지 않는다(`mode=register`로 새 조직을 만드는 경우는 예외). AUTH-6을 우회하는 경로가 생기지 않도록 하는 불변식 — [ADR-0018](../10_ADR_의사결정기록/ADR.md) |
| AUTH-8 | OAuth `state`는 서명·유효시간·브라우저 연결(쿠키)을 모두 검증해야 하며, 한 번 쓴 `state`는 재사용되지 않아야 한다 |
| AUTH-9 | refresh 토큰은 서명과 만료를 검증해야 하며, 갱신 시 반드시 새 토큰으로 회전되어야 한다 |
| AUTH-10 | **사용자 정보를 화면에서 고칠 수 있어야 한다.** 모든 사용자는 자기 **이름**을 직접 바꾸고(`PATCH /users/me`, 이름 외 항목은 거부), admin 은 같은 조직 구성원의 **이름·이메일·역할**을 바꾼다(`PATCH /users/:id`). 역할 변경은 다음 요청부터 즉시 적용되어야 하고, 모든 변경은 감사 로그(`user.updated`·`user.role_changed`)에 남아야 한다. 구성원 수정에는 **플랜 게이트를 두지 않는다**(초대 허용 범위는 D-07 에서 별도로 정한다) (T-113) |
| AUTH-12 | **비밀번호를 화면에서 바꾸고 재설정할 수 있어야 한다.** 본인 변경은 현재 비밀번호를 확인하고, 관리자는 같은 조직 구성원의 비밀번호를 재설정할 수 있되 **본인에게는 쓸 수 없다**. 새 비밀번호는 8자 이상·72바이트 이하(bcrypt 한도)이며, 변경·재설정 시 대상의 모든 세션 갱신이 끊겨야 한다. 이메일 발송이 없으므로 셀프 "비밀번호 찾기"는 범위 밖이다 — 조직의 마지막 관리자가 잊었을 때는 서버 스크립트(`scripts/oracle/reset-password.sh`)로 복구한다 (T-114) |
| AUTH-11 | **조직에는 admin 이 항상 1명 이상 있어야 한다.** 마지막 admin 의 역할을 내리는 요청은 거부하며, 두 admin 이 동시에 서로를 내리는 경우에도 한 명은 남아야 한다. 관리자 전용 기능(사용자 추가·역할 변경·감사 로그)을 쓸 사람이 사라지면 화면에서는 복구할 수 없기 때문이다 (T-113) |
| AUTH-13 | **다른 사람이 정해 준 비밀번호는 첫 로그인 때 본인이 바꿔야 한다.** 관리자가 만든 계정·관리자 재설정·아스트룸의 고객사 개설·서버 재설정 스크립트로 정해진 비밀번호가 대상이다(`mustChangePassword`). 바꾸기 전에는 비밀번호 변경·내 정보·로그아웃 외의 API 를 **서버가** 막는다(403 `PASSWORD_CHANGE_REQUIRED`) — 화면만 막으면 정해 준 사람이 그 비밀번호로 API 를 그대로 쓸 수 있다 (T-122) |
| AUTH-14 | 플랫폼 관리자(`global_admin`, 아스트룸 운영자)는 **고객사를 개설하고 마스터 계정을 발급**할 수 있어야 한다. 마스터 비밀번호는 서버가 만든 임시 비밀번호로 **한 번만** 보여 주며 저장·기록하지 않는다. 공개 회원가입이 닫힌 새 서버의 첫 플랫폼 관리자는 서버 스크립트(`scripts/oracle/create-tenant.sh --platform-admin`)로 만든다 (T-122) |

## 2. 규정·조문 구조 (REQ-POLICY)

| ID | 요구사항 |
|---|---|
| POLICY-1 | 규정은 코드(테넌트 내 유일)·제목·설명·담당부서·분류·개정일·시행일을 가져야 한다 |
| POLICY-2 | 규정은 장(Chapter) → 절(Section) → 조(Article, 조 루트) → 항(clauseNumber) → 목(itemNumber) 계층을 지원해야 한다 |
| POLICY-2a | **장·절은 선택, 조는 필수**여야 한다. 사내 규정은 법령의 `편>장>절>조` 구조를 반드시 따르지 않으므로, 장을 만들지 않고 조부터 바로 추가할 수 있어야 한다 (2026-08-02 대표 지시) |
| POLICY-2b | 절(節)은 장에 속하는 선택 계층이며, 절에 속하지 않는 조가 같은 장에 공존할 수 있어야 한다 |
| POLICY-3 | 행 유형은 `clauseNumber`/`itemNumber` null 여부로 판별되어야 한다 (조 루트: 둘 다 null / 항: clauseNumber만 있음 / 목: itemNumber 있음) |
| POLICY-4 | 항·목은 제목 없이 본문만으로 등록 가능해야 한다 |
| POLICY-5 | 조 루트 없이 제목+1항을 동시 입력하면 조 제목 행과 1항 본문 행이 자동 분리 생성되어야 한다 |
| POLICY-6 | 장은 `suppressHeader` 설정 시 목차·전문·인쇄에서 장 제목을 숨겨야 한다. 장 없이 조부터 만든 규정은 이 숨김 장을 사용하며, 가져오기 시에도 원문에 장이 없으면 임의의 "제1장 총칙"을 만들지 않아야 한다 |
| POLICY-7 | 조문에는 판례/법령/규칙 참조 여부(플래그)와 근거 메모를 기록할 수 있어야 한다 |
| POLICY-8 | 부칙·별표·서식(PolicyAppendix)을 정렬 순서와 함께 CRUD할 수 있어야 한다 |
| POLICY-9 | 규정 첨부파일을 업로드·다운로드·삭제할 수 있어야 한다. 표시 이름은 올린 그대로여야 하고(한글 포함), 업로드·삭제는 감사 로그에 남아야 한다 (T-90) |
| POLICY-9a | **저장 위치는 미결이다.** 코드는 API 컨테이너의 로컬 볼륨(`/app/uploads`)에 저장한다 — MinIO 클라이언트도, `STORAGE_TYPE` 을 읽는 코드도 없다. compose 는 MinIO 컨테이너와 자격증명을 넘기지만 쓰이지 않는다. **API 를 2대 이상으로 늘리면 첨부가 인스턴스별로 갈린다.** 오브젝트 스토리지로 옮길지 로컬 저장을 정식으로 확정할지 결정 필요 — **D-06** |
| POLICY-10 | 조·항·목 표기는 법령 관례를 따라야 한다: **조 = `제N조`, 항 = `①②…`, 목 = `1. 2. …`** (`legalArticleLabel.ts`, 2026-08-02 대표 확인 — 기구현) |
| POLICY-11 | 규정은 개정일과 시행일을 **각각 구분해** 관리·표시해야 한다(단일 "기준일" 아님) (기구현) |
| POLICY-12 | 본문 글자 크기를 단계로 조절할 수 있어야 하며(90~150%) 선택이 유지되어야 한다. **인쇄·PDF·HWPX 산출물은 이 배율의 영향을 받지 않아야 한다** — 화면 배율이 조판을 바꾸면 "내가 본 것과 다른 문서"가 나온다 (T-75) |
| TPL-7 | 출력 양식의 결재란(작성·검토·승인 서명 칸)은 **선택 항목**이어야 하며 기본값은 표시하지 않음이어야 한다. 결재란을 쓰지 않는 고객사가 있기 때문 (`showApprovalLine`, 기본 `false` — 2026-08-02 대표 확인, 기구현) |

## 3. 버전·개정 워크플로 (REQ-VERSION)

| ID | 요구사항 |
|---|---|
| VER-1 | 조문 버전 상태는 draft → review → published → archived 순으로 전이해야 한다 |
| VER-2 | 시행 승인(published 전환) 시 승인 사유가 필수여야 하며, 기존 published 버전은 자동으로 archived 되어야 한다 |
| VER-3 | 두 버전 간 diff를 줄 단위/단어 단위로 비교할 수 있어야 한다 |
| VER-6 | **서로 다른 두 규정**을 조문 단위로 대조할 수 있어야 한다(본사↔지사, 표준규정↔우리 규정). 공유 식별자가 없으므로 조·항·목 번호로 맞대되, **번호는 같은데 제목이 다른 짝은 경고로 표시**해야 한다 — 조용히 짝지으면 표가 그럴듯하게 틀린다. 같은 규정의 두 시점 비교(VER-3)·인용 관계 추적(3단비교)과는 다른 기능이다 (T-91) |
| VER-4 | 검토 반려(reject)와 버전 폐지(archive)를 화면에서 처리할 수 있어야 한다. **반려는 사유가 필수**이며 되돌린 초안에 그대로 보여야 하고(`ArticleVersion.reviewNote`), 폐지 시 마지막 게시본이면 경고해야 한다 (T-10, 2026-08-23) |
| VER-4a | 폐지는 **폐지 시행일**을 남겨야 하며, 그 날부터 시점 조회·신구조문대비표·법령 영향 분석·개정 후보에서 그 조문을 **시행 중이 아닌 것**으로 봐야 한다. 새 버전에 밀려 내려간(대체) 버전과 구분한다 — 둘 다 archived 라 시점 조회가 폐지한 조문을 옛 본문으로 되살렸다. 폐지 시행일은 **오늘(한국 날짜)**로 정하고 고르지 않는다(미래 폐지는 T-127 뒤, 소급 없음). 시행일이 없거나, 아직 시행 전이거나, 오늘 뒤에 시행될 버전이 따로 있으면 폐지를 거부한다. 폐지한 조문을 다시 시행할 때는 시행일이 폐지일 이후(같은 날 가능)여야 한다 — 일반 승인·한꺼번에 시행 모두 (T-126, 2026-10-09) |
| VER-4b | 시점 조회·신구조문대비표는 **그날 시행 중이던 버전의 계층**(장·절·조·항·목 번호, 조 제목)으로 조립해야 한다(특허 도 5·13). 계층이 실제로 바뀌는 승인(재파싱 묶음의 제안 계층, 장·절 번호·제목 변경) 때 그 조문의 발행 이력에 그때의 계층을 얼려 둔다 — 그 전 날짜는 옛 번호로, 승인한 시행일부터 새 번호로 보인다. 조 순서 재정렬·번호 직접 수정은 지금 계층의 바로잡기라 버전을 만들지 않으며, 다른 조문의 얼린 자리와 겹치면 막는다. 이 기능 전의 기록은 계층이 남아 있지 않아 지금 계층으로 보인다(T-110 ②, 버전별 계층 최소안) |
| VER-5 | 본문의 변수 표식(`{{KEY}}`)은 **입력용**이다 — 검토를 요청할 때 그날 유효한 값으로 바뀌어 본문에 저장되고, 그 자리가 변수 연결(위치)로 남아야 한다. 값을 정할 수 없는 표식이 있으면 검토 요청을 받지 않고, 표식이 남은 본문은 어느 경로로도 발행하지 않는다. 승인할 때 그 시행일의 값이 검토 요청 때와 다르면 승인하지 않는다 (T-109 — 예전 "버전 단위 사용 추적"을 대체) |

## 4. 가져오기 (REQ-IMPORT)

| ID | 요구사항 |
|---|---|
| IMPORT-1 | TXT/DOCX/PDF 업로드 또는 텍스트 붙여넣기로 규정을 가져올 수 있어야 한다 |
| IMPORT-2 | 파싱 프로필(혼합형/한국형/영문형)과 분할 모드(auto/blank_block/line_each/delimiter/markdown)를 선택할 수 있어야 한다 |
| IMPORT-3 | 가져오기 전 장/조문 인식 결과를 미리보기로 확인할 수 있어야 한다 |
| IMPORT-4 | 가져오기는 항(①②…)·목(1. 2. …) 패턴을 인식해 `clauseNumber`/`itemNumber`를 자동으로 채워야 한다. 「항·목 자동 인식」 옵션으로 끌 수 있고, 인식 결과 개수를 등록 전에 안내해야 한다 (2026-07-30 구현) |
| IMPORT-5 | 가져오기 이력(PolicyImportLog)이 테넌트별로 기록·조회되어야 한다 |
| IMPORT-6 | **가져와서 바로 시행할 때는 그 본문이 실제로 시행된 날(시행일)을 반드시 받아** 첫 버전과 규정 단위 시행일에 넣어야 한다(PDF·법제처·JSON 일괄·텍스트 가져오기 모두). "오늘"로 채우지 않는다 — 이미 시행 중인 규정의 과거 시점 조회가 틀어진다. 법제처 가져오기의 법령 시행일은 참고로만 보여 준다(회사 규정 시행일과 다를 수 있다). 예전 경로로 시행일 없이 들어간 시행본은 관리자가 근거와 함께 확인한 날짜로 보정하며, 같은 조문의 앞뒤 시행본과 순서가 어긋나는 날짜는 거부한다. 시행일 없는 시행본은 시점 조회 규칙에서 빠져 법령 개정 분석(LAW-4~)의 기준 본문이 되지 못하기 때문이다 (T-123 · 특허 도 4 S450) |

## 12. 법령 개정 연계 (REQ-LAW)

다른 절이 "이미 구현된 동작의 역산"인 것과 달리, 이 절은 **앞으로 만들 것**을 먼저 적었다(2026-09-21 신설 당시 전량 미구현). 구현된 항목은 행마다 **구현됨(T-xx)** 으로 적는다.

근거는 특허 명세서 `26PD0271KR_명세서_수정안rev1.docx`(발명의 명칭 「법령 개정 연계형 사내 규정 개정 관리 방법, 시스템 및 컴퓨터 판독가능한 기록매체」)이고, 대표가 2026-09-21에 "만들 것을 쓴 것"이라고 확인했다. 설계는 [18_법령개정연계_설계](../18_법령개정연계_설계/법령개정연계_설계안.md)에 있고, 각 요구사항 옆의 (청구항 N)은 그 근거가 되는 청구항이다.

> **이 절이 2026-09-21까지 없었던 이유**: 요구사항 대조를 두 번(9/2·9/13) 했는데도 나오지 않았다. 개발문서가 아닌 특허 명세서에만 있었기 때문이다. **제품의 핵심 차별점이 요구사항 문서에 없는 상태**였다.

| ID | 요구사항 |
|---|---|
| LAW-1 | 상위 법령을 **사내 규정(`Policy`)과 별개의 엔티티**(법령원·법령·법령조항)로 저장해야 하며, 법령 데이터는 **테넌트 공용**이어야 한다. 근로기준법은 모든 고객사에 같은 내용이므로 테넌트마다 복사하면 같은 법을 고객사 수만큼 조회하게 된다 — [ADR-0020](../10_ADR_의사결정기록/ADR.md) (청구항 1·3) |
| LAW-2 | **법령조항 식별자와 사내 조문 식별자를 잇는 법령 관계 정보**를 저장할 수 있어야 하며, 관계 유형·적용 범위·근거 문구·신뢰도·**사용자 확정 상태**를 함께 가져야 한다. 현재 `Article.relatedLawNote`는 자유 텍스트 메모라 기계가 따라갈 수 없다 (청구항 1·3) |
| LAW-2a | 법령 관계 정보는 **테넌트별**이어야 한다(`LawLink.tenantId`). 어느 법에 우리 회사의 어느 조문이 걸려 있는지는 회사 기밀이다. **법령조항 식별자로 시작하는 조회는 법령 쪽에 `tenantId`가 없으므로 관계 정보에서 경계를 걸어야 한다** (청구항 3) |
| LAW-3 | 외부 법령 제공 서버(법제처 DRF)를 **주기적으로 조회**해 조항별 버전을 비교하고, 달라진 조항에 대해 **변경 이벤트**(법령원·법령·법령조항 식별자, 변경 전후 본문, 공포일, 법령 시행일, 수신경로)를 저장해야 한다 (청구항 1·3). **구현됨(T-104)** — 바뀌지 않는 **법령ID** 로 지금 판의 MST 를 찾아 저장된 MST 와 다를 때만 새 판을 받는다(MST 는 판마다 새로 매겨지고 한 MST 의 본문은 불변이라, 저장된 MST 재조회로는 개정을 못 잡는다). 예약 실행은 서버 cron → 컨테이너 CLI |
| LAW-3a | 동기화 실패는 **"개정 없음"과 구별되어 기록·노출**되어야 한다. 법제처 API는 실패해도 HTTP 200에 에러 본문을 주므로, 조용히 실패하면 개정을 놓친 것을 알 수 없다. **구현됨(T-104)** — 실행마다 `LawSyncRun`, 법령마다 `lastCheckError`(법령 목록·상세에 "확인 실패" 표시), CLI 는 실패 시 종료 코드 1 |
| LAW-4 | 변경된 법령조항을 기점으로 관계 정보를 따라가 **영향 조문을 식별**해야 하며, 하나의 법령조항이 **여러 규정·여러 조문**에 도달할 수 있어야 한다. 영향 조문마다 **영향 분석 기준일에 유효한 발행 버전**(제1 조문)을 취득한다 (청구항 1·3). **구현됨(T-105)** — `GET /law-changes/:id/impact`. 기준일 기본값은 법령 시행일과 오늘 중 늦은 날(시행 전 개정이면 그날 시행될 우리 본문, 이미 시행됐으면 지금 본문 — 그 사이 회사가 고친 내용을 되돌리는 초안을 막는다). 기준일에 시행 중인 버전이 없는 조문은 빼지 않고 "제1 조문 없음"으로 돌려준다 — 기준일에 폐지돼 있으면 그 까닭(폐지일)을 따로 보인다(T-126) |
| LAW-4a | 영향 조문 식별은 **사용자가 확정한 관계만** 사용해야 한다. 자동 추천 상태의 관계로 초안을 만들면 틀린 연결이 그럴듯한 개정안을 만들어 낸다. **구현됨(T-105)** — 추천 연결은 영향에 넣지 않고 "확인이 필요한 연결 N건"으로만 보인다 |

| LAW-7 | 후보는 **변경된 부분과 그 변경 근거를 함께** 검토 화면에 표시해야 한다. 근거 없이 초안만 내놓으면 검토가 형식이 된다 (청구항 6). **구현됨(T-106·T-107)** — 메뉴 "개정 검토"(`/amendments`, 관리자·편집자): 후보 목록(기본은 처리할 것 = 작성·검토, 규정·시행 여부 필터, 비활성 규정의 후보도 숨기지 않음)과 상세(기준 본문 · 삭제 취소선·추가 밑줄의 후보 · 바뀐 곳을 누르면 그 변경의 근거 — 적용 규칙·법령 변경·연결, 근거가 없는 변경은 점선으로 검토 대상 표시). 법령 화면의 영향 패널 미리보기에서 상세로 이어진다. 기준 본문이 그 사이 바뀐 후보는 경고하고 그 조문만 "다시 만들기"(옛 후보는 그대로) |

| LAW-10 | 발행 버전 본문·변경 이벤트·개정 후보·비교 정보·**승인자**를 서로 연결한 감사 로그를 남겨, 후속 버전에서 **개정의 원천과 승인자를 추적**할 수 있어야 한다 (청구항 6). **구현됨(T-108)** — 감사 `amendment.approve` 한 건에 발행 버전(id·번호·본문 해시·시행일·발행 시각)·변경 이벤트(id·법령·전후 판 키)·후보(id·승인한 판·해시·검토 요청·기준 본문·발행 이력 지문)·비교 정보(승인한 판의 기록)·승인자, 개정 당시 근거(연결 스냅샷·규칙 세트)를 묶는다(버전 생성·상태 전환·알림과 한 트랜잭션). 발행된 버전에는 `changeEventId`·`sourceCandidateId` 가 남아 버전에서 원천으로 거슬러 간다 |
| LAW-11 | **법령 시행일 / 발행일 / 사내 규정 시행일**을 서로 구분되는 날짜로 관리해야 한다. 현재는 개정일·시행일 2종뿐이라 법령 시행일을 담을 곳이 없다. **시점 조회의 기준은 사내 규정 시행일 하나**여야 한다 — 발행일을 기준으로 삼으면 "발행했지만 아직 시행 전인 개정"이 조회 결과에 섞인다 (청구항 7). **구현(T-108·T-111)** — `ArticleVersion.publishedAt`(발행일)은 개정 후보 승인·일반 승인·한꺼번에 시행·가져오기 확정·JSON 일괄 등록·재파싱 묶음 승인이 모두 기록한다. 그 전에 발행된 버전은 승인 시각(`approvedAt` — 처음부터 발행하는 그 순간에 적어 왔다)으로 채우고 보정 표시(`publishedAtFromApproval`)를 남겼다. 승인 시각도 없는 발행 이력은 비워 두고 "발행 기록 없음"으로 보인다(생성일·시행일로 메우지 않는다). 법령 시행일은 후보 승인으로 발행된 버전이 `changeEventId` 로 가리키는 변경 이벤트의 값이다 — 버전에 옮겨 적지 않고, 연결이 없는 버전에 그 법령의 최신 시행일을 대신 보이지 않는다. 버전 카드·연혁 탭·개정 이력 타임라인·개정 후보 승인 결과가 사내 시행일 → 발행일시(한국 시각) → 법령 시행일(법령명·조항) 순서로 함께 보이고, 사내 시행일이 법령 시행일보다 이르면 "법령보다 조기 시행"과 승인 사유로 가는 길을 붙인다 |
| LAW-12 | 규정 문서를 **재파싱할 때 조문 식별자를 유지**해야 한다. 규정 식별 정보·계층 정보·본문 **내용 지문**으로 기존 조문과의 대응을 판정하며, **계층이 달라도 지문이 같으면 같은 조문(조문 이동)** 으로 본다. 번호만 보면 조 번호가 밀린 개정이 "삭제+신설"로 보이고 그 순간 법령 연결과 버전 이력이 끊긴다 (청구항 2) **1단계 구현(T-110 ①)** — 다시 가져온 원문을 사람이 고른 규정(파일 이름이 아니라 규정 식별 정보)의 조문과 맞추는 재파싱 검토. 계층(조·가지·항·목 번호, 장·절은 장 단위로 대응)과 내용 지문(정규화한 본문의 SHA-256 — 줄바꿈·공백·문자 표현만 맞추고 수치·부정 표현·단위·문장 부호는 남긴다) 두 축으로 본다: 같은 번호·같은 본문 → 그대로, 번호가 달라도 본문이 전체에서 하나뿐이고 상위 조·하위 항·앞뒤 조가 같은 쪽으로 대응되면 옮김(미리 골라 둠), 같은 자리의 본문이 바뀌면 개정인지 새 조문인지 사람이 고른다, 후보가 여럿이면 판정 보류(한 축만 맞는다고 고르지 않는다), 띄어쓰기만 같은 짝은 확인 대상, 폐지된 조문은 수동 후보로만, 남은 것은 새 조문 후보와 원문에 없음(삭제 여부 확인 — 이력은 지우지 않는다). 결정은 검토에 남고 다시 비교해도 같은 항목이면 옮겨 온다. 규정 데이터는 바꾸지 않는다 — 반영(초안·새 조문·삭제 확인)과 묶음 승인은 2단계(T-110 ②) **2단계 구현(T-110 ②)** — 반영은 검토 대상 만들기다: 기존 조문의 개정·이동·조 제목 변경은 그 조문의 **묶음 초안**(본문·제안 계층)으로만 만들고 지금 본문·번호는 그대로 둔다. 새 조문·새 장·절은 승인 때 만든다. 장·절의 번호·제목이 바뀌면 그 장·절의 시행 중인 조문도 계층만 바꾸는 초안을 받는다. 묶음은 같은 사내 규정 시행일로 함께 검토 요청·승인한다(전부 되거나 전부 안 됨). 승인 시행일부터 그 뒤의 모든 시행일에서 같은 자리에 시행 중인 조문이 둘이 되면 승인하지 않는다. 원문에 없는 조문은 유지·폐지(관리자)를 정해 두면 승인 때 그 날로 폐지하고, 승인 뒤에도 정할 수 있다. 옮김·본문 바뀜을 새 조문으로 돌리면 그 기존 조문은 곧바로 원문에 없음 항목이 된다. 묶음 버전은 하나씩 검토 요청·승인·반려하지 못하고 한꺼번에 시행에서도 빠진다. 단계마다 규정 → 조문 잠금 아래 규정 상태 지문을 다시 확인한다 |
| LAW-13 | 변수 마스터는 **변수 값별로 유효기간과 테넌트 범위**를 가져야 하고, 변수 바인딩은 **본문 내 사용 위치**를 가져야 한다. 후보 생성 시 사내 규정 시행일에 해당하는 값을 골라 각 사용 위치에 반영한다. 현재 `Variable`에는 유효기간이 없고 `VariableUsage`에는 위치가 없다 (청구항 5·9) **1단계 구현(T-109 ①)** — 값마다 유효기간 [시작, 종료)(시작 없음 = 처음부터, 끝 없음 가능, 종료일 당일은 다음 값), 범위는 그 회사(전역·회사 안 조직 범위는 미룸), 같은 변수에서 기간이 겹치면 저장은 하되 "검토 필요"이고 그날 값이 **정확히 하나**일 때만 쓴다, 옛 기본값은 "기간 미확정"으로 옮겨 기간을 정하기 전에는 쓰지 않는다. 연결은 기준 버전·본문 구간(UTF-16)·당시 문구·앞뒤 문맥·출현 순번 — 같은 문구가 여러 번 나와도 고른 자리만. 시행 중인 문구를 화면에서 골라 잇고, 새 버전을 발행하면 차이로 위치를 옮긴 연결을 새 버전에 만든다(옛 연결은 이력, 옮기지 못하면 "다시 이어야 함"). **2단계 구현(T-109 ②)** — 후보에 예정 사내 시행일(법령 시행일·영향 분석 기준일과 다르다)을 두고 그 날 값을 영향 조문이면서 연결된 자리에 넣는다(같으면 그대로, 정할 수 없으면 넣지 않고 "변수 값 미정", 법령 고침과 같은 자리면 원문을 두고 양쪽 제안). 변수 근거는 법령 근거와 따로 남고 보인다. 승인 때 그 시행일로 다시 골라 다르면 승인하지 않는다(그 날로 다시 만들어 재검토), 발행 때 연결은 새 값으로 이어진다. 감사 기록에 변수 선택(값·유효기간·범위·연결) |
