## 1. 인증·사용자 (REQ-AUTH)

| ID | 요구사항 |
|---|---|
| AUTH-1 | 이메일/비밀번호로 로그인 가능해야 한다. **고객사(조직)와 그 첫 관리자(마스터)는 아스트룸이 통합 관리자 콘솔에서 개설한다**(2026-10-08 PM 결정, T-122). 누구나 새 조직을 만드는 **공개 회원가입은 운영에서 닫혀 있고**(`ALLOW_PUBLIC_SIGNUP` 미설정 = 닫힘) 개발·테스트에서만 연다. 닫힌 서버에서는 구글로 새 조직을 만드는 경로도 막힌다 |
| AUTH-2 | ~~Google OAuth로 로그인/가입 가능해야 한다~~ → **삭제(2026-10-10, T-136)**. 아스트룸이 고객사를 개설하고 마스터가 직원 계정을 발급하는 B2B 계정 체계(AUTH-1)와 맞지 않는다. 로그인은 이메일·비밀번호 하나이고, `/auth/google`·`/auth/google/callback` 은 없다(404). 비밀번호 없이 구글로만 만든 예전 계정은 로그인 시 401 `code: PASSWORD_NOT_SET` 으로 안내하고, 회사 관리자의 비밀번호 재설정(AUTH-12)으로 들어온다 |
| AUTH-3 | JWT access/refresh 토큰을 발급하고, refresh 토큰으로 재발급이 가능해야 한다 |
| AUTH-4 | 테넌트 내 역할은 admin/editor/viewer 3종이어야 하며, viewer는 검색·규정상세·소개 화면만 접근 가능해야 한다 |
| AUTH-5 | `global_admin` 플랫폼 역할을 가진 사용자만 통합 관리자 화면·API에 접근 가능해야 한다 |
| AUTH-6 | 팀원 초대(사용자 생성)는 admin만 가능해야 한다. **플랜과 무관하다** — 마스터가 직원 계정을 만들어 나눠 주는 제품이라 Starter 고객사도 발급할 수 있어야 하고, 플랜 차이는 사용자 상한(`maxUsersForPlan`: Starter 10 / Pro 50)으로만 둔다. (D-07 정리 — 2026-10-08 PM 결정, 화면 개방은 T-122. 그 전까지 문서는 "Starter 불가/Pro+", 코드는 플랜 무관으로 어긋나 있었다) |
| AUTH-7 | **조직 합류 경로는 admin의 사용자 생성 하나뿐이어야 한다.** AUTH-6을 우회하는 경로가 생기지 않도록 하는 불변식(구글 로그인은 T-136 으로 없앴다) — [ADR-0018](../10_ADR_의사결정기록/ADR.md) |
| AUTH-8 | ~~OAuth `state`는 서명·유효시간·브라우저 연결(쿠키)을 모두 검증해야 한다~~ → **해당 없음(T-136)** — OAuth 경로를 없앴다 |
| AUTH-9 | refresh 토큰은 서명과 만료를 검증해야 하며, 갱신 시 반드시 새 토큰으로 회전되어야 한다. **화면은 회전된 새 토큰을 저장해야 한다** — T-137 전 화면은 새 토큰을 버려 로그인 30분쯤 뒤 두 번째 갱신이 거절되고 로그인 화면으로 튕겼다. 같은 토큰으로 동시에 갱신하면 한쪽만 성공하고, 여러 탭은 차례로 갱신한다(T-137) |
| AUTH-10 | **사용자 정보를 화면에서 고칠 수 있어야 한다.** 모든 사용자는 자기 **이름**을 직접 바꾸고(`PATCH /users/me`, 이름 외 항목은 거부), admin 은 같은 조직 구성원의 **이름·이메일·역할**을 바꾼다(`PATCH /users/:id`). 역할 변경은 다음 요청부터 즉시 적용되어야 하고, 모든 변경은 감사 로그(`user.updated`·`user.role_changed`)에 남아야 한다. 구성원 수정에는 **플랜 게이트를 두지 않는다**(초대 허용 범위는 D-07 에서 별도로 정한다) (T-113) |
| AUTH-12 | **비밀번호를 화면에서 바꾸고 재설정할 수 있어야 한다.** 본인 변경은 현재 비밀번호를 확인하고, 관리자는 같은 조직 구성원의 비밀번호를 재설정할 수 있되 **본인에게는 쓸 수 없다**. 새 비밀번호는 8자 이상·72바이트 이하(bcrypt 한도)이며, 변경·재설정 시 대상의 모든 세션 갱신이 끊겨야 한다. 이메일 발송이 없으므로 셀프 "비밀번호 찾기"는 범위 밖이다 — 조직의 마지막 관리자가 잊었을 때는 서버 스크립트(`scripts/oracle/reset-password.sh`)로 복구한다 (T-114) |
| AUTH-11 | **조직에는 admin 이 항상 1명 이상 있어야 한다.** 마지막 admin 의 역할을 내리는 요청은 거부하며, 두 admin 이 동시에 서로를 내리는 경우에도 한 명은 남아야 한다. 관리자 전용 기능(사용자 추가·역할 변경·감사 로그)을 쓸 사람이 사라지면 화면에서는 복구할 수 없기 때문이다 (T-113) |
| AUTH-13 | **다른 사람이 정해 준 비밀번호는 첫 로그인 때 본인이 바꿔야 한다.** 관리자가 만든 계정·관리자 재설정·아스트룸의 고객사 개설·서버 재설정 스크립트로 정해진 비밀번호가 대상이다(`mustChangePassword`). 바꾸기 전에는 비밀번호 변경·내 정보·로그아웃 외의 API 를 **서버가** 막는다(403 `PASSWORD_CHANGE_REQUIRED`) — 화면만 막으면 정해 준 사람이 그 비밀번호로 API 를 그대로 쓸 수 있다 (T-122) |
| AUTH-14 | 플랫폼 관리자(`global_admin`, 아스트룸 운영자)는 **고객사를 개설하고 마스터 계정을 발급**할 수 있어야 한다. 마스터 비밀번호는 서버가 만든 임시 비밀번호로 **한 번만** 보여 주며 저장·기록하지 않는다. 공개 회원가입이 닫힌 새 서버의 첫 플랫폼 관리자는 서버 스크립트(`scripts/oracle/create-tenant.sh --platform-admin`)로 만든다 (T-122) |
| AUTH-15 | **로그인 세션은 기기(브라우저)마다 따로 있어야 한다** — 다른 PC 에서 로그인해도 먼저 쓰던 PC 가 튕기지 않는다. 로그아웃은 그 기기의 세션만, 비밀번호 변경·재설정은 그 사람의 모든 세션을 끝낸다(이미 받은 접근 토큰은 만료(15분)까지). 로그인 화면의 **자동 로그인**(기본 꺼짐)을 켜면 30일, 끄면 브라우저를 닫을 때까지(서버는 12시간) 유지되고, 둘 다 쓸 때마다 다시 늘어난다(`AUTH_REMEMBER_TTL`·`AUTH_SESSION_TTL`). 갱신 토큰은 해시만 저장한다. T-137 전에 받은 토큰은 다음 갱신 때 한 번만 세션으로 옮긴다 (T-137, [ADR-0024](../10_ADR_의사결정기록/ADR.md)) |

## 2. 규정·조문 구조 (REQ-POLICY)

| ID | 요구사항 |
|---|---|
| POLICY-1 | 규정은 코드(테넌트 내 유일)·제목·설명·담당부서·분류·개정일·시행일을 가져야 한다 |
| POLICY-2 | 규정은 장(Chapter) → 절(Section) → 조(Article, 조 루트) → 항(clauseNumber) → 목(itemNumber) 계층을 지원해야 한다 |
| POLICY-2a | **장·절은 선택, 조는 필수**여야 한다. 사내 규정은 법령의 `편>장>절>조` 구조를 반드시 따르지 않으므로, 장을 만들지 않고 조부터 바로 추가할 수 있어야 한다 (2026-08-02 대표 지시) |
| POLICY-2b | 절(節)은 장에 속하는 선택 계층이며, 절에 속하지 않는 조가 같은 장에 공존할 수 있어야 한다 |
| POLICY-3 | 행 유형은 `clauseNumber`/`itemNumber` null 여부로 판별되어야 한다 (조 루트: 둘 다 null / 항: clauseNumber만 있음 / 목: itemNumber 있음) |
| POLICY-4 | 항·목은 제목 없이 본문만으로 등록 가능해야 한다 |
| POLICY-5 | 조 루트 없이 제목+1항을 동시 입력하면 조 제목 행과 1항 본문 행이 자동 분리 생성되어야 한다 |
| POLICY-6 | 장은 `suppressHeader` 설정 시 목차·전문·인쇄에서 장 제목을 숨겨야 한다. 장 없이 조부터 만든 규정은 이 숨김 장을 사용하며, 가져오기 시에도 원문에 장이 없으면 임의의 "제1장 총칙"을 만들지 않아야 한다 |
| POLICY-7 | 조문에는 판례/법령/규칙 참조 여부(플래그)와 근거 메모를 기록할 수 있어야 한다 |
| POLICY-8 | 부칙·별표·서식(PolicyAppendix)을 정렬 순서와 함께 CRUD할 수 있어야 한다 |
| POLICY-9 | 규정 첨부파일을 업로드·다운로드·삭제할 수 있어야 한다. 표시 이름은 올린 그대로여야 하고(한글 포함), 업로드·삭제는 감사 로그에 남아야 한다 (T-90) |
| POLICY-9a | **저장 위치는 미결이다.** 코드는 API 컨테이너의 로컬 볼륨(`/app/uploads`)에 저장한다 — MinIO 클라이언트도, `STORAGE_TYPE` 을 읽는 코드도 없다. compose 는 MinIO 컨테이너와 자격증명을 넘기지만 쓰이지 않는다. **API 를 2대 이상으로 늘리면 첨부가 인스턴스별로 갈린다.** 오브젝트 스토리지로 옮길지 로컬 저장을 정식으로 확정할지 결정 필요 — **D-06** |
| POLICY-10 | 조·항·목 표기는 법령 관례를 따라야 한다: **조 = `제N조`, 항 = `①②…`, 목 = `1. 2. …`** (`legalArticleLabel.ts`, 2026-08-02 대표 확인 — 기구현) |
| POLICY-11 | 규정은 개정일과 시행일을 **각각 구분해** 관리·표시해야 한다(단일 "기준일" 아님) (기구현) |
| POLICY-12 | 본문 글자 크기를 단계로 조절할 수 있어야 하며(90~150%) 선택이 유지되어야 한다. **인쇄·PDF·HWPX 산출물은 이 배율의 영향을 받지 않아야 한다** — 화면 배율이 조판을 바꾸면 "내가 본 것과 다른 문서"가 나온다 (T-75) |
| TPL-7 | 출력 양식의 결재란(작성·검토·승인 서명 칸)은 **선택 항목**이어야 하며 기본값은 표시하지 않음이어야 한다. 결재란을 쓰지 않는 고객사가 있기 때문 (`showApprovalLine`, 기본 `false` — 2026-08-02 대표 확인, 기구현) |

## 3. 버전·개정 워크플로 (REQ-VERSION)

| ID | 요구사항 |
|---|---|
| VER-1 | 조문 버전 상태는 draft → review → published → archived 순으로 전이해야 한다 |
| VER-2 | 시행 승인(published 전환) 시 승인 사유가 필수여야 하며, 기존 published 버전은 자동으로 archived 되어야 한다 |
| VER-3 | 두 버전 간 diff를 줄 단위/단어 단위로 비교할 수 있어야 한다 |
| VER-6 | **서로 다른 두 규정**을 조문 단위로 대조할 수 있어야 한다(본사↔지사, 표준규정↔우리 규정). 공유 식별자가 없으므로 조·항·목 번호로 맞대되, **번호는 같은데 제목이 다른 짝은 경고로 표시**해야 한다 — 조용히 짝지으면 표가 그럴듯하게 틀린다. 같은 규정의 두 시점 비교(VER-3)·인용 관계 추적(3단비교)과는 다른 기능이다 (T-91) |
| VER-4 | 검토 반려(reject)와 버전 폐지(archive)를 화면에서 처리할 수 있어야 한다. **반려는 사유가 필수**이며 되돌린 초안에 그대로 보여야 하고(`ArticleVersion.reviewNote`), 폐지 시 마지막 게시본이면 경고해야 한다 (T-10, 2026-08-23) |
| VER-4a | 폐지는 **폐지 시행일**을 남겨야 하며, 그 날부터 시점 조회·신구조문대비표·법령 영향 분석·개정 후보에서 그 조문을 **시행 중이 아닌 것**으로 봐야 한다. 새 버전에 밀려 내려간(대체) 버전과 구분한다 — 둘 다 archived 라 시점 조회가 폐지한 조문을 옛 본문으로 되살렸다. 폐지 시행일은 **오늘(한국 날짜)**로 정하고 고르지 않는다(미래 폐지는 T-127 뒤, 소급 없음). 시행일이 없거나, 아직 시행 전이거나, 오늘 뒤에 시행될 버전이 따로 있으면 폐지를 거부한다. 폐지한 조문을 다시 시행할 때는 시행일이 폐지일 이후(같은 날 가능)여야 한다 — 일반 승인·한꺼번에 시행 모두 (T-126, 2026-10-09) |
| VER-4b | 시점 조회·신구조문대비표는 **그날 시행 중이던 버전의 계층**(장·절·조·항·목 번호, 조 제목)으로 조립해야 한다(특허 도 5·13). 계층이 실제로 바뀌는 승인(재파싱 묶음의 제안 계층, 장·절 번호·제목 변경) 때 그 조문의 발행 이력에 그때의 계층을 얼려 둔다 — 그 전 날짜는 옛 번호로, 승인한 시행일부터 새 번호로 보인다. 조 순서 재정렬·번호 직접 수정은 지금 계층의 바로잡기라 버전을 만들지 않으며, 다른 조문의 얼린 자리와 겹치면 막는다. 이 기능 전의 기록은 계층이 남아 있지 않아 지금 계층으로 보인다(T-110 ②, 버전별 계층 최소안) |
| VER-5 | 본문의 변수 표식(`{{KEY}}`)은 **입력용**이다 — 검토를 요청할 때 그날 유효한 값으로 바뀌어 본문에 저장되고, 그 자리가 변수 연결(위치)로 남아야 한다. 값을 정할 수 없는 표식이 있으면 검토 요청을 받지 않고, 표식이 남은 본문은 어느 경로로도 발행하지 않는다. 승인할 때 그 시행일의 값이 검토 요청 때와 다르면 승인하지 않는다 — 같은 값을 제자리에서 고쳐 문구만 바뀐 것도 다른 값이다(T-139) (T-109 — 예전 "버전 단위 사용 추적"을 대체) |

JSON 일괄 등록은 원래 한 트랜잭션이다 |

| SEARCH-6 | (T-146, D-09 재결정) 외부 AI 호출은 처리 지역을 **미국으로 고정**해야 한다(Anthropic `inference_geo: us` — 처리방침에 적는 이전 국가와 맞추려고. 기본값 global 은 미국·유럽·아시아·호주 여러 나라에서 처리된다). 질문 화면은 받는 곳(Anthropic, PBC)·국가(미국)·보내는 항목(질문, 회사 규정의 조 목차, 고른 조문 본문)·보관 기간(Anthropic 30일 이내 삭제, VEDA 질문 기록 90일)을 보여야 한다 |

| TENANT-2 | 플랜별 규정 개수·사용자 수 상한이 강제되어야 한다 (Starter 5규정/10명, Pro 10,000규정/50명, Enterprise 사실상 무제한). 규정 수는 동시에 만들어도 넘지 않아야 한다 — 새 규정·가져오기 확정·일괄 등록이 회사 행을 잠근 뒤 센다(T-135) |
| TENANT-3 | 고객사의 플랜 변경(결제)은 결제 프로바이더 설정(`PAYMENT_PROVIDER`)에 따라 동작해야 한다. **설정이 없으면 결제 미사용**이고(운영 기본 — 설정을 빠뜨린 서버가 열리면 안 된다) 결제 시작은 403 `BILLING_CLOSED` 로 거부하며 요금제·구독·결제 기록을 바꾸지 않는다. `mock` 은 명시했을 때만 즉시 반영하는 개발용이고, 그 외 프로바이더는 `PAYMENT_HOSTED_CHECKOUT_URL`로 보낸 뒤 웹훅(`payment.succeeded`)으로 반영한다 (T-125 — 2026-10-08 전에는 설정이 없으면 `mock` 이었다) |
| TENANT-4 | 결제 처리 결과는 `tenant.plan` 갱신·감사 로그와 함께 **결제 이력/구독(BillingPayment·BillingSubscription·BillingCustomer)에 기록**되어야 하며, `planExpiresAt` 은 구독 종료일로 채워져야 한다. 같은 요금제 재결제는 구독을 연장하고, 요금제 변경은 이전 구독을 닫고 새로 연다. **mock 결제는 0원으로 기록**한다(요금표를 지어내면 이력이 그럴듯하게 거짓이 된다) (T-17, 2026-08-23) |
| TENANT-5 | `global_admin`은 통합 관리 콘솔에서 테넌트 목록·플랜·사용자 역할을 관리할 수 있어야 한다. **가격 확정(D-02·D-03) 전 임시 운영 방침: 요금제 변경은 이 경로로만 한다** — 운영은 결제 미사용, 요금제 창은 가격·결제 버튼 대신 "아스트룸에 문의" 안내만 보이고 서버를 부르지 않는다. 인원 표시는 TENANT-2 와 같아야 한다 (T-125, [ADR-0022](../10_ADR_의사결정기록/ADR.md)) |
| TENANT-6 | 로그인 없이 열린 결제 웹훅은 **실결제 프로바이더가 설정되고 `PAYMENT_WEBHOOK_SECRET` 이 설정된 서버에서, 같은 비밀키를 댄 요청만** 받아야 한다. 결제 미사용·mock 은 403 `PAYMENT_DISABLED`, 비밀키 미설정은 403 `WEBHOOK_SECRET_NOT_CONFIGURED`, 불일치는 401 이며 본문을 보기 전에 판단한다. 비교는 응답 시간 차가 없어야 한다 (T-125 — 전에는 비밀키가 없으면 검사를 건너뛰었다) |

## 12. 법령 개정 연계 (REQ-LAW)

다른 절이 "이미 구현된 동작의 역산"인 것과 달리, 이 절은 **앞으로 만들 것**을 먼저 적었다(2026-09-21 신설 당시 전량 미구현). 구현된 항목은 행마다 **구현됨(T-xx)** 으로 적는다.

근거는 특허 명세서 `26PD0271KR_명세서_수정안rev1.docx`(발명의 명칭 「법령 개정 연계형 사내 규정 개정 관리 방법, 시스템 및 컴퓨터 판독가능한 기록매체」)이고, 대표가 2026-09-21에 "만들 것을 쓴 것"이라고 확인했다. 설계는 [18_법령개정연계_설계](../18_법령개정연계_설계/법령개정연계_설계안.md)에 있고, 각 요구사항 옆의 (청구항 N)은 그 근거가 되는 청구항이다.

> **이 절이 2026-09-21까지 없었던 이유**: 요구사항 대조를 두 번(9/2·9/13) 했는데도 나오지 않았다. 개발문서가 아닌 특허 명세서에만 있었기 때문이다. **제품의 핵심 차별점이 요구사항 문서에 없는 상태**였다.

| ID | 요구사항 |
|---|---|
| LAW-1 | 상위 법령을 **사내 규정(`Policy`)과 별개의 엔티티**(법령원·법령·법령조항)로 저장해야 하며, 법령 데이터는 **테넌트 공용**이어야 한다. 근로기준법은 모든 고객사에 같은 내용이므로 테넌트마다 복사하면 같은 법을 고객사 수만큼 조회하게 된다 — [ADR-0020](../10_ADR_의사결정기록/ADR.md) (청구항 1·3). **구현됨(T-100)** |
| LAW-2 | **법령조항 식별자와 사내 조문 식별자를 잇는 법령 관계 정보**를 저장할 수 있어야 하며, 관계 유형·적용 범위·근거 문구·신뢰도·**사용자 확정 상태**를 함께 가져야 한다. 현재 `Article.relatedLawNote`는 자유 텍스트 메모라 기계가 따라갈 수 없다 (청구항 1·3). **구현됨(T-101·T-102)** — `LawLink`(관계 유형·적용 범위·근거 문구·신뢰도·확정 상태). `relatedLawNote` 는 메모로 따로 남는다. 근거 문구가 사내 조문 본문에서 나왔으면 **그 판(원천 판)**도 함께 남긴다(T-177, 특허 도 3 S320) — 연결할 때(근거 문구를 고칠 때) 서버가 근거 문구를 담은 판을 찾고(오늘 시행 판 먼저), 연결 화면과 개정 후보 근거가 그 판을 보이며 본문에서 찾은 근거 문구가 지금 판(후보는 기준 본문) 본문에 없으면 알린다(원천 판이 그 뒤 지워져도). 어느 판 본문에도 없는 문구(메모·직접 쓴 설명)는 원천 없이 두고 알리지 않는다 |
| LAW-2a | 법령 관계 정보는 **테넌트별**이어야 한다(`LawLink.tenantId`). 어느 법에 우리 회사의 어느 조문이 걸려 있는지는 회사 기밀이다. **법령조항 식별자로 시작하는 조회는 법령 쪽에 `tenantId`가 없으므로 관계 정보에서 경계를 걸어야 한다** (청구항 3). **구현됨(T-101·T-105)** |
| LAW-3 | 외부 법령 제공 서버(법제처 DRF)를 **주기적으로 조회**해 조항별 버전을 비교하고, 달라진 조항에 대해 **변경 이벤트**(법령원·법령·법령조항 식별자, 변경 전후 본문, 공포일, 법령 시행일, 수신경로)를 저장해야 한다 (청구항 1·3). **구현됨(T-104)** — 바뀌지 않는 **법령ID** 로 지금 판의 MST 를 찾아 저장된 MST 와 다를 때만 새 판을 받는다(MST 는 판마다 새로 매겨지고 한 MST 의 본문은 불변이라, 저장된 MST 재조회로는 개정을 못 잡는다). 예약 실행은 서버 cron → 컨테이너 CLI. **T-151(PAT-07, 특허 도 7 S770)부터 판을 차례로 반영한다** — 현행 목록(`target=law`)은 현행만 주므로(2026-10-14 실호출), 시행일법령 목록(`target=eflaw`)을 법령ID(`LID`)로 받은 판 목록으로 저장 판 **뒤에 공포된 판 전부**(연혁·현행·시행 예정)를 공포 순(공포일·공포번호·MST)으로 하나씩 반영하고, 판마다 그 판의 공포일·법령 시행일로 이벤트를 남긴다. 판 하나가 저장 단위 하나이고(법령 행·판 기록·조항·이벤트), 중간에 실패하면 앞 판까지 확정하고 멈춘다 — 실패한 판을 건너뛰지 않는다 |
| LAW-3a | 동기화 실패는 **"개정 없음"과 구별되어 기록·노출**되어야 한다. 법제처 API는 실패해도 HTTP 200에 에러 본문을 주므로, 조용히 실패하면 개정을 놓친 것을 알 수 없다. **구현됨(T-104)** — 실행마다 `LawSyncRun`, 법령마다 `lastCheckError`(법령 목록·상세에 "확인 실패" 표시), CLI 는 실패 시 종료 코드 1 |
| LAW-4 | 변경된 법령조항을 기점으로 관계 정보를 따라가 **영향 조문을 식별**해야 하며, 하나의 법령조항이 **여러 규정·여러 조문**에 도달할 수 있어야 한다. 영향 조문마다 **영향 분석 기준일에 유효한 발행 버전**(제1 조문)을 취득한다 (청구항 1·3). **구현됨(T-105)** — `GET /law-changes/:id/impact`. 기준일 기본값은 법령 시행일과 오늘 중 늦은 날(시행 전 개정이면 그날 시행될 우리 본문, 이미 시행됐으면 지금 본문 — 그 사이 회사가 고친 내용을 되돌리는 초안을 막는다). 기준일에 시행 중인 버전이 없는 조문은 빼지 않고 "제1 조문 없음"으로 돌려준다 — 기준일에 폐지돼 있으면 그 까닭(폐지일)을 따로 보인다(T-126). **수정(2026-10-14, T-148)**: 변경된 법령조항뿐 아니라 그 **상위 조항(같은 법령의 조·항)에 건 확정 연결**도 영향으로 잡는다. 인용 자동 찾기는 '제60조'를 조 머리 행에 잇는데, 항이 여럿인 조의 머리 행은 본문이 비어 있어 항 개정 이벤트가 항에만 생긴다(실행 확인) — 그대로 두면 가장 흔한 연결이 실제 개정을 받지 못한다. 같은 조문이 여러 단계에 연결돼 있으면 가장 가까운 연결 하나를 쓰고, 상위 조항으로 찾은 영향은 그렇다고 표시한다. 아래로는(항에 건 연결 → 조 머리 행 변경) 퍼뜨리지 않는다. **구현됨(T-148)** — 영향 조회·변경 목록(거르기·개수)·자동 생성이 같은 범위 계산을 쓰고, 상위 조항으로 찾은 후보는 신뢰도 '보통'까지에 '상위 조항 연결로 찾음' 표시가 붙는다. 회사 화면에 돌려주거나 후보를 만드는 연결 조회는 연결의 회사와 조문의 실제 소속을 함께 본다(법령 추적 해제 차단은 일부러 회사와 무관하게 연결이 하나라도 있으면 막는다) |
| LAW-4a | 영향 조문 식별은 **사용자가 확정한 관계만** 사용해야 한다. 자동 추천 상태의 관계로 초안을 만들면 틀린 연결이 그럴듯한 개정안을 만들어 낸다. **구현됨(T-105)** — 추천 연결은 영향에 넣지 않고 "확인이 필요한 연결 N건"으로만 보인다 |
| LAW-5 | 변경 전후 법령 본문·제1 조문·관계 정보를 기초로 **개정 후보 본문(제2 조문)과 변경 근거 정보**를 생성하고, 제1·제2 조문 간 **변경 전후 비교 정보**를 생성해야 한다 (청구항 1). **구현됨(T-106, 규칙 기반)** — `POST /amendments/generate`. 법령 전후 본문을 비교(개정 연혁 표기 `<개정 …>` 는 뺀다)해 바뀐 문구를 찾고, 기준값·용어·인용 문장 규칙으로 우리 조문의 **대응 문구 자리에만** 옮긴다(문장 구조는 그대로). 비교 정보는 규칙 기록과 따로 제1·제2 조문의 **실제 차이**(문자 구간)를 계산하고, 근거가 연결되지 않은 변경을 표시한다. 고칠 근거가 확실하지 않으면 — 대응 문구가 없거나, 같은 문구가 여러 곳인데 근거 문구로 좁혀지지 않거나, 참고 관계·적용 범위가 있는 연결이거나, 법 문장이 추가·삭제됐거나, 조항이 삭제됐으면 — 본문은 제1 조문 그대로 두고 **'직접 작성 필요'** 로 넘긴다(그럴듯한 오답보다 낫다, ADR-0021). **수정(2026-10-14, T-155)**: 같은 문구가 한 곳뿐이어도 근거 문구가 있으면 그 문장 안에 있는지 확인하고, 근거 문구가 없으면 반영하되 신뢰도는 '보통'까지로 둔다(지금은 뜻이 다른 같은 숫자도 바꾸고 '높음'을 준다). 값이 바뀌는 초안에는 '회사 기준을 그대로 둘지 확인'을 표시한다 — 숫자가 늘었는지 줄었는지로 유리·불리를 판단하지는 않는다(기한이 줄면 오히려 강화다) |

| LAW-22 | 같은 규정의 개정 후보(하나 또는 여럿)를 **개정안 문서** — 신구조문대비표(현행·개정안·비고)와 개정 이유·법령 근거 — 로 한/글(.hwpx)·PDF로 낼 수 있어야 한다. 이사회·노사협의회 안건 자료로 쓴다. 관리자·편집자만 쓰고, 감사 기록은 규정 내보내기와 따로 남긴다. 워드(.docx)는 결정 대기(D-15). T-162 |
| LAW-23 | (**D-11 결정 전에는 만들지 않는다**) 개정 후보마다 AI가 **검토 우선순위(높음·보통·낮음)와 근거**를 붙인다 — 대표 피드백의 Critical/Warning/Info다. 입력은 법 조항 변경 전·후, 법제처 개정 이유, 우리 조문(기준 본문), 연결 정보다. 근거는 번호를 붙여 준 원문 문장 가운데서만 고르고, 범위 밖 인용은 버린다. 회사 값과 법 값은 나란히 보이기만 하고 유불리를 판단하지 않는다. 위법·위반·무효 같은 단정 표현은 걸러 내고, 알림과 출력 문서에는 싣지 않는다. **정렬·표시에만 쓴다** — 후보를 만들지 말지, 연결 확정, 닫는 사유, 대시보드 숫자에는 쓰지 않고, '낮음'도 숨기지 않는다. 외부 AI 전송은 D-09 재결정과 [ADR-0025](../10_ADR_의사결정기록/ADR.md)를 그대로 따른다 — 회사별 기본 꺼짐, 관리자가 고지(보내는 항목에 법령 분석용 조문 본문·목차를 더한 판)를 보고 확인해야 켜지고, 처리 지역은 미국, 기록은 90일 뒤 지운다. 모델·입력 원천·프롬프트 판을 함께 저장한다. T-163(공용 기반·회사 설정)·T-164 |
| LAW-24 | (**D-11 결정 전에는 만들지 않는다**) 법 조항 번호 없이 내용으로만 법을 따르는 조문도 찾도록, 법령이 개정되면 **AI가 회사의 조 목차에서 관련 조를 골라 '추천' 연결**로 넣는다. 대상은 그 법령에 연결이나 법령 단위 언급이 있는 회사뿐이고, 회사마다 따로(한 호출에 한 회사) 영향 분석 기준일의 목차로 한다. AI가 고른 조는 그 회사 목차 안의 것만 받고 저장 직전에 소속을 다시 확인한다. 목차가 잘려 일부를 못 봤으면 그렇다고 보인다. 추천 연결은 한 건씩 확정한다 — 확정해야 후보가 생긴다(ADR-0021). 외부 AI 전송 규칙은 LAW-23과 같다. 임베딩은 쓰지 않는다(14.5). T-168 |
| LAW-25 | 인용 자동 찾기는 **시행 중 본문**(현재 규칙)을 읽고, 다음 표기도 잡아야 한다: 두 글자 법령명(상법·민법), 공백·가운뎃점이 있거나 '…에 관한 법률'로 끝나는 제명(공백을 무시하고 비교), 약칭(LAW-16), 시행령·시행규칙, '같은 법'·'동법'·'(이하 "법"이라 한다)', 범위·열거(제60조부터 제62조까지, 제60조 및 제61조), '준용' 문구(관계 유형을 준용으로). 부정문('적용하지 않는다')은 신뢰도를 낮춘다. 조 번호 없이 법령만 언급한 문장('근로기준법에 준하여')은 '법령 단위 언급'으로 모아 LAW-24로 넘긴다. 지금은 대표가 든 예시('상법 제363조에 따라', '근로기준법에 준하여')도 잡지 못한다(실행 확인). T-156(시행 중 본문)·T-165 |
| LAW-26 | 규정 단위로 **인용을 한꺼번에 찾고**, 근거 문장에 법령명과 조 번호가 그대로 있는 명시 인용 추천만 **한꺼번에 확정**할 수 있어야 한다. 확정하기 전에 '확정하면 개정 후보 N건이 생깁니다'를 보인다. 연결에는 추천 출처(글자 패턴·AI 모델·프롬프트 판·사람)와 확정 방식(한 건·한꺼번에)을 남기고 후보 근거 스냅샷에도 싣는다. 인용했지만 등록되지 않은 법령은 이름을 짚어 바로 등록하게 하고, 연결의 관계 유형·적용 범위를 화면에서 고칠 수 있게 한다. 가져오기를 확정하면 찾기를 저절로 돌린다(추천까지만). T-166 |
| LAW-27 | 회사마다 **감시 법령 목록**을 둔다. 등록은 '우리 회사 감시 추가'만 하고, 공용 법령의 판은 동기화만 바꾸며, 해제는 우리 회사 감시만 지운다(마지막 감시이고 연결·후보가 없을 때만 법령 행을 지운다). 아스트룸이 관리하는 **추천 법령 묶음**(예: 상법·자본시장법·근로기준법·남녀고용평등법·산업안전보건법·중대재해처벌법·개인정보 보호법과 각 시행령)을 한 번에 감시에 넣을 수 있다. 같은 법령의 중복 행을 합칠 때 조항이 달라진 연결은 '추천'으로 내리고 그 회사에 다시 확인하라고 알린다. 이미 등록된 법령의 감시 회사는 D-16으로 정한다. T-167 |
