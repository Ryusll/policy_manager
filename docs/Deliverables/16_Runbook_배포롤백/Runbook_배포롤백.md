```bash

```

`.env`에서 최소한 아래를 운영값으로 설정:

- `PUBLIC_URL` — 사용자가 브라우저에 입력하는 실제 URL (예: `https://your-domain.com`). CORS에 사용됨

## 3. 최초 배포

```bash
npm run docker:up          # = docker compose up -d
npm run docker:logs        # 기동 로그 확인
```

`api` 컨테이너는 `docker-entrypoint.sh`에 따라 기동 시 자동으로:
1. `prisma migrate deploy`
2. (1이 실패하고 **기존 스키마가 있으면**) baseline 이전 DB로 보고 자동 처리 — 옛 이력 행 정리 → `00000000000000_init`을 applied로 표시 → `migrate deploy` 재시도
3. 그래도 실패하면 **FATAL 종료** (데이터를 덮어쓰지 않는다)
4. 데모 데이터 시드 (테넌트 `demo`, 계정 `admin@demo.com` / `password123`; seed.ts에는 `astrum`/`admin@astrum.com`도 포함)
5. `node dist/main`으로 서버 기동

> 2026-08-02부터 `db push --accept-data-loss` 폴백은 **제거**됐다([ADR-0012](../10_ADR_의사결정기록/ADR.md)). 스키마는 마이그레이션으로만 반영되며, 실패는 조용히 넘어가지 않고 컨테이너를 멈춘다.

## 7. 롤백

이 프로젝트는 이미지 태그 버전 관리·마이그레이션 down 스크립트가 정의되어 있지 않으므로, 롤백은 다음 원칙을 따른다:

1. **코드 롤백**: 직전 정상 커밋으로 소스를 되돌린 뒤 4번(재빌드·재기동) 수행
2. **DB 롤백**: Prisma 마이그레이션에 down 스크립트가 없으므로 스키마 자동 롤백 불가 →
   - 배포 전 반드시 DB 백업: `docker compose exec postgres pg_dump -U postgres policy_manager > backup_YYYYMMDD.sql`
   - 문제 발생 시 복원: `docker compose exec -T postgres psql -U postgres policy_manager < backup_YYYYMMDD.sql`
3. **볼륨 데이터**: `postgres_data`, `minio_data`, `api_uploads` 볼륨은 `docker compose down`으로는 삭제되지 않음. `down -v`는 볼륨까지 삭제하므로 **운영에서 절대 사용 금지**
5. **재파싱 묶음(632466a, T-110 ②) 이전 코드로 되돌릴 때 (T-131)** — 옛 코드는 묶음 초안(`reparse_item_id`)을 일반 초안으로 보고 하나씩 승인할 수 있어 **묶음 일부만 발행**되고, 버전별 계층(`structure`)을 무시해 그 전 날짜의 시점 조회가 지금 계층으로 나온다. 순서대로:
   1. 쓰기를 막는다(점검 공지 후 웹을 내리거나 관리자 외 접속 차단) — 진행 중인 요청이 끝날 때까지 기다린다
   2. **지금 코드로** 반영·검토 중인 재파싱 묶음을 모두 반려한다(재파싱 검토 화면 `묶음 반려`)
   3. 읽기 전용으로 확인한다(7-6 방식) — 둘 다 0 이어야 한다:
      `SELECT count(*) FROM reparse_reviews WHERE status IN ('applied','submitted');` · `SELECT count(*) FROM article_versions WHERE reparse_item_id IS NOT NULL AND status IN ('draft','review');`
   4. 이미 승인한 묶음이 있으면(`SELECT count(*) FROM article_versions WHERE structure IS NOT NULL;` 가 0 이 아니면) **632466a 이전으로는 되돌리지 않는다** — 반려로 풀리지 않는다. 그 기록을 읽는 632466a 이후 릴리스까지만 되돌린다
   5. 이미지를 바꿔 기동이 끝날 때까지 1의 쓰기 차단을 유지한다
   6. 이미 그렇게 되돌렸다가 다시 올렸다면: 발행 이력에 남은 제안 계층을 지우고(`UPDATE article_versions SET structure = NULL WHERE status IN ('published','archived') AND structure->>'kind' = 'proposal';`) 반영·검토 중으로 멈춘 묶음을 지금 코드로 반려한다
4. **첨부파일 백업**: 규정 첨부는 DB가 아니라 `api_uploads` 볼륨에만 있어 `pg_dump` 에 **포함되지 않는다.** 아래 8절의 서버 밖 백업이 DB와 첨부를 함께 내보내므로, 그것이 돌고 있으면 이 항목은 자동으로 충족된다.

## 7-1. 시크릿 교체 (운영 배포 전 필수)

`docker-compose.yml`의 기본 시크릿은 **리포에 그대로 적혀 있어 공개된 값과 같다.** 운영에 그대로 올라가면 JWT 위조·DB 직접 접근이 가능하다. 그래서 `NODE_ENV=production`에서 기본값이 감지되면 **API가 기동을 거부한다**([`secrets-guard.ts`](../../../apps/api/src/common/config/secrets-guard.ts)).

### 교체 대상

| 변수 | 용도 | 조건 |
|---|---|---|
| `JWT_SECRET` | 액세스 토큰 서명 | 32자 이상, `JWT_REFRESH_SECRET`와 **다른 값** |
| `JWT_REFRESH_SECRET` | 갱신 토큰 서명 | 32자 이상 |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | DB 계정 (compose가 `DATABASE_URL`을 조립) | `postgres:postgres` 금지 |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | 오브젝트 스토리지 | minio 서비스와 api가 같은 값을 공유 |

### 절차

```bash
# 1) 값 생성 (각각 따로 실행 — 같은 값 재사용 금지)
openssl rand -base64 48   # JWT_SECRET
openssl rand -base64 48   # JWT_REFRESH_SECRET
openssl rand -base64 24   # POSTGRES_PASSWORD
openssl rand -base64 24   # MINIO_SECRET_KEY

# 2) .env에 기입 (.env는 .gitignore 대상 — 커밋 금지)
cp .env.example .env && ${EDITOR:-vi} .env

# 3) 기동 전 치환 결과 확인 (실제 값이 들어갔는지, ${...}가 남지 않았는지)
docker compose config | grep -E "JWT_SECRET|POSTGRES_PASSWORD|MINIO_SECRET_KEY"

# 4) 기동 — 기본값이 남아 있으면 여기서 API가 부팅에 실패한다
docker compose up -d --build
docker compose logs api | head -30
```

### 주의

- **DB·MinIO 시크릿은 첫 기동 때 볼륨에 굳는다.** 이미 뜬 적 있는 환경에서 `POSTGRES_PASSWORD`만 바꾸면 기존 볼륨의 계정과 어긋나 접속이 실패한다. 운영 중 교체는 `ALTER USER ... PASSWORD`로 DB 안에서 바꾸고 `.env`를 맞추는 순서로 한다(볼륨 삭제 금지).
- **JWT 시크릿을 바꾸면 기존 토큰이 전부 무효**가 된다. 전 사용자 재로그인이 필요하므로 공지 후 교체한다.
- 장애 중 기동만 급히 되살려야 하면 `ALLOW_DEFAULT_SECRETS=1`로 가드를 우회할 수 있다. **우회한 기동은 그 자체로 사고 대응 대상**이며, 즉시 정상 교체 후 재기동한다.

## 7-2. 오래된 서버에 재배포 (모르는 서버 인수인계용)

(이 저장소는 공개이므로 서버 주소는 적지 않는다 — 인프라 담당자에게 확인할 것.)
리포 최초 커밋이 6-25이므로 **git 이력에 없는 코드로 배포돼 있다.** git만 보고 서버 상태를
추정하지 말고 반드시 먼저 조사한다.

### 0단계. 조사 (읽기 전용)
```bash
ssh <서버>            # 접속 경로는 인프라 담당자에게 확인
cd <프로젝트 디렉터리>   # docker-compose.yml 이 있는 곳
sh scripts/server-recon.sh
```
이 출력으로 ① 소스 위치 ② 기본 시크릿 사용 여부 ③ DB 마이그레이션 이력 ④ 실데이터 규모가 확정된다.

### 위험 1 — 스키마 드리프트 (가장 위험)
6월 DB에는 `sections`(절, 8-02 도입)가 없는데, **baseline `00000000000000_init` 안에는 있다.**
기동 스크립트의 자동 baseline 처리는 baseline을 *실행하지 않고* "적용됨"으로 표시하므로,
그대로 두면 **`sections` 테이블이 없는 채로 적용 완료 표시**가 되어 런타임에 깨진다.

→ 자동 경로에 맡기지 말고, 배포 전에 실제 차이를 뽑아 적용한다:
```bash
# 서버 DB와 현재 스키마의 차이를 SQL로 생성 (읽기 전용, 적용 안 함)
npx prisma migrate diff   --from-url "$DATABASE_URL"   --to-schema-datamodel apps/api/prisma/schema.prisma   --script > /tmp/drift.sql
less /tmp/drift.sql       # DROP 문이 있으면 반드시 사람이 검토
```
`DROP TABLE`/`DROP COLUMN`이 보이면 **적용하지 말고** 원인을 먼저 규명한다(6월 이후 서버에서만 만들어진 것일 수 있다).

### 위험 2 — 시크릿 가드로 API 부팅 거부
재배포하면 `secrets-guard.ts`가 들어간다. 기본값(공개된 JWT 키, `minioadmin123`, `postgres:postgres`)이
남아 있으면 **운영 모드에서 API가 뜨지 않는다.** 조사 6번 항목이 0이 아니면 먼저 7-1을 수행한다.
DB·MinIO 시크릿은 볼륨에 굳어 있으므로 `.env`만 바꾸면 접속이 깨진다(7-1 주의 참고).

### 절차
```bash
# 1) 백업 (필수)
docker compose exec -T postgres pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" > backup_$(date +%F).sql
ls -lh backup_$(date +%F).sql          # 0바이트가 아닌지 확인

# 2) 소스 갱신
git fetch origin && git checkout develop && git pull origin develop

# 3) 시크릿 정리 (7-1)  — 조사 6번이 0이 될 때까지
docker compose config | grep -cE 'your-super-secret|minioadmin123|postgres:postgres@'

# 4) 스키마 드리프트 해소 (위험 1)

# 5) 재배포
docker compose up -d --build
docker compose logs -f api      # 'migrate deploy completed.' 와 기동 로그 확인

# 6) 확인 — 새 엔드포인트가 401(있음)이어야 한다. 404면 옛 빌드가 그대로다
curl -s -o /dev/null -w '%{http_code}\n' "http://<호스트>/api/policies/0/as-of?date=2026-01-01"
```

### 롤백
문제 시 `git checkout <직전 커밋> && docker compose up -d --build` 후 필요하면 1)의 덤프를 복원한다.

## 7-3. 서버 밖 백업 (필수)

### 왜 필요한가

**규정 본문(DB)과 첨부파일이 둘 다 이 서버 안에만 있다.** 기존 절차의
`pg_dump > backup_YYYYMMDD.sql` 은 같은 서버에 파일을 만드는 것이라,
배포하다 잘못됐을 때 되돌리는 용도는 되지만 **서버 자체가 사라지면 백업도
함께 사라진다.** Always Free 인스턴스는 유휴 상태가 이어지면 회수되기도 한다.

첨부파일은 DB 백업에 들어 있지도 않았다. 둘 다 내보내야 복구가 성립한다.

### 설정

S3 호환 저장소면 어디든 된다(Oracle Object Storage, AWS S3, 별도 서버의 MinIO).
`.env` 에 아래를 채운다 — 값은 인프라 담당자가 발급한다.

```
BACKUP_S3_ENDPOINT=https://<네임스페이스>.compat.objectstorage.<리전>.oraclecloud.com
BACKUP_S3_BUCKET=policy-manager-backup
BACKUP_S3_ACCESS_KEY=...
BACKUP_S3_SECRET_KEY=...
BACKUP_KEEP_DAYS=30
```

> Oracle Object Storage 를 쓴다면 콘솔에서 **Customer Secret Key** 를 발급받아
> 위 두 값에 넣는다(사용자 API 키와 다르다). 엔드포인트는 버킷의
> "S3 호환성" 안내에 표시된다.

### 매일 자동 실행

```bash
crontab -e
# 매일 새벽 3시. 실패하면 종료 코드가 0이 아니라 cron 이 메일로 알린다.
0 3 * * * cd /home/ubuntu/policy_manager && bash scripts/backup-offsite.sh >> /var/log/policy-backup.log 2>&1
```

한 번 손으로 돌려 확인:

```bash
bash scripts/backup-offsite.sh
```

DB 덤프 → 첨부 아카이브 → 업로드 → **업로드된 크기 대조** → 오래된 것 정리
순으로 진행하고, 어디서든 어긋나면 종료 코드 1로 멈춘다. 0바이트 덤프를
성공으로 넘기지 않는다.

### 복원되는지 확인 (한 달에 한 번은 돌릴 것)

**복원해 본 적 없는 백업은 백업이 아니라 희망이다.**

```bash
bash scripts/restore-offsite.sh --verify
```

최신 백업을 내려받아 **임시 DB에 넣어 보고** 원본과 테이블·행 수를 대조한 뒤
임시 DB를 지운다. 운영 데이터는 건드리지 않는다. 첨부 아카이브도 열어 본다.

### 실제 복구

```bash
bash scripts/restore-offsite.sh --restore 2026-09-07T030000Z
```

파괴적이다. `RESTORE` 를 직접 입력해야 진행되며, api·web 을 멈추고 DB와 첨부
볼륨을 덮어쓴 뒤 다시 띄운다. 백업 목록은 `--verify` 실행 로그나 저장소 콘솔에서 확인한다.

### 한계

- 하루 한 번이므로 **최대 24시간치를 잃을 수 있다.** 더 촘촘히 하려면 주기를 줄인다.
- 첨부 아카이브는 스택이 도는 중에 만들므로, 그 순간 업로드 중이던 파일 하나가
  빠질 수 있다. 다음 회차에 포함된다.
- 저장소 자격증명이 서버 `.env` 에 있다. 서버가 털리면 백업도 지워질 수 있다 —
  저장소 쪽에서 **버전 관리나 삭제 보호**를 켜 두는 것이 안전하다.

## 7-4. 비밀번호 재설정 (서버에서)

화면에서는 ① 본인이 `내 정보 > 비밀번호 변경`, ② 관리자가 구성원 행의 `비밀번호 재설정` 으로 바꾼다.
이메일 발송이 없어 "비밀번호 찾기"는 없다. **조직의 마지막 관리자가 비밀번호를 잊으면** 화면으로는 불가능하므로 서버에서:

```bash
bash scripts/oracle/reset-password.sh <조직코드> <이메일>
```

비밀번호는 두 번 입력받으며 화면·셸 기록에 남지 않는다. 해당 사용자의 모든 세션이 끊기고, 감사 로그에 `user.password_reset`(`via: server-script`)이 남는다. **다음 로그인 때 본인이 비밀번호를 바꾸게 된다**(T-122 — 다른 사람이 정한 비밀번호이므로).

## 7-5. 법령 동기화 (매일, T-104)

등록된 법령에 새 판이 났는지 법제처에서 확인한다. 서버 crontab 에 한 줄:

```bash
30 4 * * * cd ~/policy_manager && bash scripts/oracle/law-sync.sh >> ~/law-sync.log 2>&1
```

- 확인 시도가 오래된 법령부터 20건(`--limit 50` 처럼 늘릴 수 있다). 하나라도 실패하면 **종료 코드 1** — 로그의 `실패:` 줄에 법령과 사유가 남는다.
- **법제처 인증값(`LAW_GO_KR_OC`)이 필요하다.** 법제처가 서버 IP·도메인을 이유로 거절할 수도 있는데(지금 운영 서버는 IP 등록 없이 통과한다), 이 거절도 HTTP 200 으로 와서 조용히 넘어가기 쉽다 — 그래서 실패를 따로 기록한다. 실패하면 법령 목록에 `확인 실패` 가 뜬다.
- 결과는 통합 관리자 콘솔의 `법령 동기화` 패널에서도 보이고, 거기서 바로 실행할 수도 있다(플랫폼 관리자).
- **멈춤 경고(T-153 ④)** — 마지막 성공 실행(실패 없이, 또는 일부만 실패하고 끝난 실행)이 36시간을 넘으면 그 패널과 고객 법령 화면에 경고가 뜬다(T-213 부터 관리자·편집자 대시보드의 '법령 개정' 구역에도 같은 경고가 뜬다). 볼 순서: ① 서버 `crontab -l` 에 위 줄이 있는지 ② `tail -50 ~/law-sync.log` 의 마지막 실행과 `실패:` 줄(법제처 인증·응답 오류인지) ③ 패널의 `지금 확인` — 성공하면 경고가 사라진다. 단 아래 반영 절차 4 에서 crontab 줄을 되살리기 전이면 누르지 않는다 — 첫 반영이 돈다. 절차가 마지막 성공 뒤 36시간을 넘기면 그동안 고객 법령 화면에도 경고가 뜨고, 절차 6에서 지워진다. 법령 하나만 점검한 실행도 성공으로 세므로, 그것으로 경고가 사라져도 예약 실행은 따로 확인한다. 패널에 빨간 '동기화 상태를 불러오지 못해…'가 뜨면 경고 계산 자체가 실패한 것이다 — `docker compose logs --tail 100 api` 를 본다.
- **'마지막 확인'은 성공 시각이다(T-153 ⑤)** — 확인에 실패한 법령은 시각이 그대로 남고(성공한 적이 없으면 비어 '등록한 판' — 상세 머리말은 '아직 개정 확인에 성공한 적이 없습니다'), 실패 사유만 적힌다. 동기화 차례는 따로 둔 시도 시각(`last_attempted_at`)으로 정해 실패한 법령이 매번 맨 앞에 서지 않는다. 반영 때 마이그레이션(`20261108120000`)이 지난 실패로 찍힌 '마지막 확인'을 실행 기록의 마지막 성공 시각(그 실행의 시작 시각)으로 되돌리고, 성공 기록이 없으면 비운다. 실행 시간을 절반 넘게 남기고 시작했는데도 시간 상한까지 판을 하나도 반영하지 못한 법령은 확인 실패로 남기고 차례를 뒤로 돌린다(그 법령만 돈 실행이나 결과가 모두 실패인 실행은 실패 실행이 된다. 늦게 시작해 못 한 법령은 기록을 바꾸지 않고 앞에 남는다). 판 목록 받기가 실행 시간의 절반을 넘긴 경우뿐이라 기본 설정(응답 제한 15초, 목록 10쪽)에서는 거의 없다 — 서버 로그에 '실패: … 확인 시간 안에 새 판을 하나도 반영하지 못했습니다'(참고: 실행 시간을 다 쓰고도…)가 보이면(화면에서 누른 실행은 패널 이력에서) 법제처 응답 시간과 DB 상태를 본다.
- 실행 중 서버가 재시작돼 `진행 중` 으로 남은 기록은 30분 뒤 다음 실행이 "중단됨"으로 닫는다.
- **T-151 부터 두 확인 사이에 공포된 판을 공포 순으로 하나씩 반영한다**(시행 예정 판 포함). 법령당 한 번에 5판(`LAW_SYNC_MAX_VERSIONS`), 실행 전체 20분(`LAW_SYNC_BUDGET_MS`)까지 — 남은 판은 다음 실행이 잇는다. 어느 판에서 실패하면 앞 판까지 반영하고 멈추며 로그의 `실패:` 줄에 판(MST)과 사유가 남는다.
- **T-151 운영 반영 절차** — 첫 동기화가 저장 판 뒤의 판을 한꺼번에 이벤트·개정 후보로 만든다(되돌리기 어렵다). 아래 4 에서 되살릴 때까지 crontab 의 law-sync 줄을 주석 처리해 두고, 그때까지 통합 관리자 콘솔의 "지금 확인" 도 누르지 않는다(같은 첫 반영이 돈다).
  1. **배포 전**(Mac, 7-6 방식 — 읽기 전용이고 새 표를 쓰지 않는다): `ORACLE_SSH=ubuntu@<서버주소> bash scripts/oracle/run-readonly-sql.sh scripts/oracle/sql/t151-law-id-check.sql` — ① 법령ID 없는 행(동기화되지 않는다) ② 같은 법령ID 의 중복 행. 0건이었어도 **배포 직후 한 번 더** 돌린다(그 사이 옛 코드가 MST 로만 찾아 행을 더 만들 수 있다). 둘 다 0건이면 2-1 로(2-1 은 건너뛰지 않는다).
  2. 0건이 아니면 **배포 직후 바로**(그 사이 고객 등록이 법령ID 없는 행 옆에 둘째 행을 만들 수 있다). **해제·삭제부터 하지 않는다**(연결·변경 이력이 지워진다).
     - ① 의 행이고 `같은_이름_다른_행` 이 0 이며 ② 에 같은 법령명이 없으면: 그 행의 **같은 판(저장 MST)을 다시 등록**한다. 등록 화면은 현행 판만 보여 주므로 API 로(회사 관리자 역할이 있는 계정, 서비스 주소는 저장소에 적지 않는다): `curl -s https://<서비스 주소>/api/auth/login -H "Content-Type: application/json" -d '{"email":"<관리자>","password":"<비밀번호>","tenantSlug":"<회사>"}'` 의 `accessToken` 으로 `curl -s https://<서비스 주소>/api/laws -H "Authorization: Bearer <accessToken>" -H "Content-Type: application/json" -d '{"mst":"<저장 MST>"}'`. 응답의 `externalLawId` 가 채워지고 `alreadyTracked` 가 false 여야 한다(409 "옛 중복" 이면 아래 T-154). 저장 공포일이 늦은 행부터 하고, 마친 뒤 1 의 SQL 을 다시 돌려 그 행이 빠졌는지, `--plan --law <법령 id>` 로 반영할 판을 본다. **T-150 부터 등록은 법제처 목록의 현행 판으로 한다** — 저장 MST 가 지금 현행 판이 아니면 다시 등록이 현행 판으로 둘째 행을 만들 수 있으니 하지 말고 T-154 로 넘긴다(먼저 `--plan --law <법령 id>` 의 현행 판과 저장 판이 같은지 본다).
     - 그 밖(`같은_이름_다른_행` 1 이상, ② 에 같은 법령명, 다시 등록 응답이 409 "옛 중복", 서버 로그 "법령 행이 N개입니다", 동기화 확인 실패 "같은 법령이 따로 등록돼 있어", 이름이 바뀐 것으로 의심되는 법령)은 옛 중복이다 — 다시 등록하지 말고 T-154 로 넘긴다(연결을 한 행으로 모으고 나머지를 지운다).
  2-1. **묻힌 법령 보정(T-150 ④)** — 묻힘은 두 경우다. ㉠ 시행 예정 판으로 등록했다(T-150 ③ 전). ㉡ 등록한 판(현행)보다 먼저 공포된 판이 등록 때 시행 전이었다 — 판 본문이 공포 순으로 쌓여 그 개정이 본문에 이미 들어 있다(2026-11 운영의 근로기준법 제21472호·자본시장법 제21647호·산업안전보건법 제21534호). 둘 다 서버의 `bash scripts/oracle/law-sync.sh --rebaseline all` 이 잡는다 — 모든 법령의 계획만 찍고, 보정이 필요하거나 확인할 법령('확인 필요' 줄·계획 실패 포함)이 하나라도 있으면 종료 코드 1 이다(출력을 tee 로 남기면 종료 코드 대신 마지막 요약 줄로 판단한다). **새 코드 배포 뒤의 관문은 이것 하나다** — 새 코드 배포 직후·**첫 동기화 전에** 돌려 요약이 '확인할 법령 0개'면 3 으로. `t150-buried-laws-check.sql`(7-6 방식)은 배포 전 보조 점검으로 ㉠만 미리 본다 — SQL 에 잡혀도 `--rebaseline <법령 id>` 가 '보정할 것이 없습니다'면 정상이다. 보정하고도 '확인 필요'가 남는 법령 — 법령ID 가 없거나(T-154), 연결·후보가 생겨 `--reset` 이 막힌 법령 — 은 계획 출력(묻힌 판·사유)을 대장에 새 행으로 올리고, 연결한 회사가 있으면 그 회사에 묻힌 조를 알린 뒤 3 으로 간다(다른 법령의 동기화를 막지 않는다). 보정 뒤 `--law` 동기화는 끝에 그 법령만이 아니라 처리하지 않은 변경 이벤트 전부의 개정 후보·알림을 만든다 — 먼저 처리하지 않은 이벤트 수(`law_change_events.amendments_processed_at IS NULL`)가 0 인지 본다. 법령마다 `bash scripts/oracle/law-sync.sh --rebaseline <법령 id>` 로 계획을 보고, 맞으면 `--apply` 로 되돌린다(이벤트 없이 앞 판 본문으로). 계획에 '주의 — 연결 N건'이 찍히면, 되돌린 뒤 다음 동기화가 등록 때 이미 시행 중이던 판의 개정까지 그 회사들의 후보로 만든다 — 그래도 되는지 본 뒤 적용한다. 동기화가 이미 뒤 판을 반영한 법령은 `--reset` 을 더해야 처음부터 다시 반영한다 — 그 법령에 연결·개정 후보·후보로 발행한 조문 판이 하나도 없을 때만, 그 법령의 변경 이벤트·판 기록을 지우고 앞 판부터 공포 순으로 다시 반영한다(연결이 있으면 이미 시행된 옛 개정까지 후보로 쏟아지므로 막는다 — 연결·후보가 생긴 뒤에는 `--reset` 도 막혀 묻힌 개정은 끝내 후보가 되지 않는다). 운영의 근로기준법·자본시장법은 `--reset --apply`, 산업안전보건법은 `--apply` 로 T-187 2차 반영 때 고친다 — 회사가 그 법령에 연결을 걸기 전에. 계획·적용 출력은 `... 2>&1 | tee ~/rebaseline-$(date +%Y%m%d%H%M).log` 로 남기고 대장(T-187)에 옮긴다 — `--reset` 이 지운 이벤트는 DB 에 기록이 남지 않고(T-199 ⑥), 다시 생긴 이벤트는 새 id 라 예전 '최근 법령 변경' 링크(`?change=`)는 열리지 않는다. 적용 뒤 '경고 — 다시 거는 사이 … 생겼습니다'가 나오면 다음 동기화 전에 사람이 본다. D-18 ② 가 정해졌으면 **같은 창에서 바로** `bash scripts/oracle/law-sync.sh --law <법령 id>` 로 그 법령만 동기화한다 — 되돌린 채로 두면 법령 화면이 앞 판을 보인다('등록한 판'으로 적힌다). 동기화가 반영한 판이 `--rebaseline` 이 찍은 '다시 반영할 판'과 같은지, 판마다 이벤트가 생겼는지 본다. 되돌리기는 배포 직전 백업 복원뿐이다.
  3. 반영될 판을 미리 본다(DB 에는 쓰지 않는다 — 법제처 응답 캐시만 쓴다): 서버에서 `cd ~/policy_manager && bash scripts/oracle/law-sync.sh --plan` — 법령마다 저장 판·현행 판·반영할 판(공포번호·제개정구분·단계 시행일)이 찍힌다. 한 번에 확인 시도가 오래된 100개까지 보고, 더 있으면 요약에 전체 수가 찍힌다(각 줄의 `[법령 id]`, 나머지는 법령 화면 주소의 id 로 `--law <법령 id>`). 판이 많거나 시행일이 한참 지난 판이 보이면 첫 반영의 후보·알림 처리(D-18 ②)를 먼저 정한다.
  4. **진행 기준**: D-18 ①·② 가 정해졌고 1~3(2-1 포함)을 마쳤으면 crontab 줄을 되살린다. 남은 옛 중복·법령ID 없는 행은 그 법령만 확인 실패로 남고(고객 화면에는 "아스트룸에 문의", 법령ID 없는 행은 통합 관리자 화면 동기화 이력에 운영자 안내가 함께 뜬다) 다른 법령은 정상으로 돈다. 옛 중복인 법령은 정리(T-154) 전까지 새 등록도 409 다.
  5. T-149 를 함께 낸 반영(2차, T-187)이면 7-10 의 놓친 개정 후보 보충을 한 번 돌린다 — `--plan` 으로 수를 보고 실행한 뒤 다시 돌려 0건인지 본다(지금 운영은 법령 관계가 없어 0건일 것이다).
  6. **동기화 확인(T-153 ④, 2차 반영부터)** — 1~5 를 마친 뒤 패널의 `지금 확인`을 한 번 누른다(4 에서 crontab 줄을 되살리기 전에는 누르지 않는다 — 위 첫 반영이 돈다). 이력 맨 위에 방금 실행이 '성공'(법령ID 없는 행 같은 알려진 실패가 남았으면 '일부 실패')으로 남았는지, `GET /api/platform-admin/law-sync/status` 의 `lastSuccessAt`(UTC — 한국 시각에서 9시간 뺀 값)이 누른 시각 뒤인지 본다 — `stale: false` 만으로는 모자란다(2-1 의 `--law` 실행이나 반영 전 실행이 36시간 안에 있으면 이미 false 다). 마지막 성공 뒤 36시간 안에 이 단계를 마치지 못하면 그동안 패널과 고객 법령 화면에 멈춤 경고가 뜬다(이 단계에서 지워진다). 누른 요청이 오류나 시간 초과로 끝나도(웹 프록시는 2분까지 기다린다 — 첫 반영처럼 오래 걸리면 화면은 '실행하지 못했습니다'를 띄우고 실행은 서버에서 계속 돈다) 패널을 새로 고침해 이력 맨 위가 '진행 중'인지 먼저 보고 끝날 때까지 기다린다. 방금 실행이 '실패'로 끝났거나 `lastSuccessAt` 이 누른 시각보다 앞이면 패널 이력의 실패 사유·참고로 법제처 인증·응답 오류인지 본다(서버 `~/law-sync.log` 에는 cron 이 부른 예약 실행만 남는다). '이미 진행 중'(409)이면 앞서 누른 실행이나 되살린 예약 실행이 도는 중이니 끝난 뒤 다시 누른다 — 30분 넘게 그대로면 api 재시작으로 남은 기록이다(30분 뒤 다음 실행이 '중단됨'으로 닫는다). 이 단계를 성공으로 마친 뒤 뜬 경고는 예약 실행 문제다 — 위 '멈춤 경고'의 순서로 보고, 예약 실행은 다음 날 `~/law-sync.log` 로도 확인한다. 예약이 없는 환경(로컬·복원본)에서 시연하면 마지막 실행 36시간 뒤부터 경고가 뜨니 시연 전에 한 번 돌린다.

## 7-6. 운영 DB 읽기 전용 점검 (Mac에서, T-121)

데이터를 고치지 않고 **건수만** 보는 점검 SQL은 `scripts/oracle/sql/` 에 둔다. Mac 에서:

```bash
ORACLE_SSH=ubuntu@<서버주소> bash scripts/oracle/run-readonly-sql.sh scripts/oracle/sql/<파일>.sql
```

- 서버 주소는 저장소에 적지 않는다(공개 저장소). 실행할 때 넘긴다. 키는 기본 `~/.ssh/veda_oci`(`ORACLE_SSH_KEY` 로 바꿀 수 있다).
- 읽기 전용은 두 겹이다: SQL 파일이 `BEGIN TRANSACTION READ ONLY` … `ROLLBACK` 으로 감싸고, 접속도 `default_transaction_read_only=on` 으로 연다. 쓰기 문이 섞여 있으면 DB가 거절한다.
- 점검 SQL은 규정 **본문을 출력하지 않는다**(회사·규정 코드·이름·날짜·건수만).

## 7-7. 고객사 개설과 첫 플랫폼 관리자 (T-122)

**운영은 공개 회원가입이 닫혀 있다** — Oracle compose 가 `ALLOW_PUBLIC_SIGNUP` 을 넘기지 않으므로 기본값(닫힘)이다. 고객사는 아스트룸이 연다.

- **평소**: 통합 관리자 콘솔 › **고객사 개설**(회사명·기관 코드·플랜·마스터 이메일·이름). 임시 비밀번호가 **한 번만** 나온다 — "전달용 내용 복사"로 마스터에게 전달한다. 마스터는 처음 로그인할 때 비밀번호를 바꾸고, 직원 계정은 마스터가 설정 › 팀원 초대에서 발급한다(직원도 첫 로그인 때 바꾼다).
- **새 서버의 첫 플랫폼 관리자**(화면으로는 만들 수 없다):

```bash
bash scripts/oracle/create-tenant.sh astrum "아스트룸" 운영자이메일 "운영자 이름" --platform-admin
```

  임시 비밀번호는 이 출력에만 나온다. 기관 코드 `astrum` 으로 로그인해 바로 바꾼다.
- **데모 데이터를 넣은 적 있는 서버**: 시드가 만든 `admin@astrum.com`(비밀번호가 공개 저장소에 적혀 있다)이 플랫폼 관리자로 남아 있다. 실제 운영자를 플랫폼 관리자로 지정한 뒤 이 계정의 플랫폼 관리자 권한을 해제하고 비밀번호도 바꾼다(7-4).
- 요청 횟수 제한은 IP 당·경로별 분당 100(`THROTTLE_LIMIT`, 운영 기본값). 개발·CI 의 docker-compose 만 1000 으로 올린다 — 통합 테스트가 한 IP 에서 수백 번 로그인한다.
- **로그인 세션(T-137)**: 배포 직후에도 이미 로그인한 사람은 튕기지 않는다 — 옛 갱신 토큰은 다음 갱신 때 한 번만 기기 세션으로 옮겨진다. 세션 수명은 `AUTH_REMEMBER_TTL`(자동 로그인, 기본 30d)·`AUTH_SESSION_TTL`(기본 12h). 특정 사람을 모든 기기에서 내보내려면 관리자가 비밀번호를 재설정한다
- **요금제 변경은 통합 관리 › 테넌트 플랜에서 플랫폼 관리자가 한다**(가격 확정 전 임시 운영 방침, T-125 · [ADR-0022](../10_ADR_의사결정기록/ADR.md)). 운영은 **결제 미사용**이다 — Oracle compose 가 `PAYMENT_PROVIDER` 를 넘기지 않으므로 고객사의 결제 시작은 403, 결제 웹훅도 받지 않는다. 운영에 `PAYMENT_PROVIDER=mock` 을 넣지 않는다(돈을 받지 않고 요금제를 올린다). 확인: `curl -s -X POST https://<도메인>/api/billing/webhook -H 'Content-Type: application/json' -d '{"type":"ping"}'` 가 403 `PAYMENT_DISABLED` 면 정상(데이터는 바뀌지 않는다)

## 7-8. 지운 파일은 서버에서 따로 지운다

`package.py` 묶음을 기존 `~/policy_manager` 위에 풀기 때문에, **저장소에서 지운 파일이 서버에는 남는다.** 남은 소스는 이미지 빌드에 그대로 들어가므로, 지운 의존성을 불러오는 파일이 남으면 빌드가 깨진다(2026-10-11 배포 때 구글 로그인 파일로 실제로 발생할 뻔했다).

배포마다 풀기 전에 서버 소스 목록과 묶음 목록을 비교해, 묶음에 없는 파일만 지운다(읽기 전용 목록 → 확인 → 삭제).

```bash
ssh <서버> "cd ~/policy_manager && find apps scripts -type f -not -path '*/node_modules/*' -not -path '*/dist/*' -not -path '*/uploads/*' | sort" > server-files.txt
python3 - <묶음.tar.gz> server-files.txt <<'PY'
import tarfile, sys
pkg = {m.name.split('/', 1)[1] for m in tarfile.open(sys.argv[1]).getmembers() if m.isfile()}
print('\n'.join(f for f in map(str.strip, open(sys.argv[2])) if f and f not in pkg))
PY
```

## 7-9. 규정 질문(AI) — 키를 넣기 전 순서와 질문 기록 파기 (T-146)

규정 질문은 질문할 때 질문·회사 규정의 조 목차·관련 조문을 Anthropic(미국)으로 보낸다. 고객사 동의 없이 외부로 나가는 일이 없게, **운영 AI 키(`ANTHROPIC_API_KEY`)는 아래 순서를 마친 뒤에 넣는다**(D-09 재결정 2026-10-14, ADR-0025).

명령은 서버의 `~/policy_manager` 에서 실행한다. 운영은 `scripts/oracle/compose.sh`(`.env.oracle`·`docker-compose.oracle.yml`)로만 돈다 — 개발용 `.env` 와 맨 `docker compose` 를 쓰지 않는다. 점검 SQL `scripts/oracle/sql/t146-ai-qa-check.sql` 은 7-6 방식(Mac)으로 돌린다. 키 값은 화면·로그·대화에 찍지 않는다.

1. 운영 키가 들어갈 길을 막고 T-146 을 배포한 뒤, 이미 외부로 나간 것이 없는지 본다(키 값은 찍지 않는다).
   - 배포 전: env 파일 `grep -cE '^[[:space:]]*(export[[:space:]]+)?ANTHROPIC_API_KEY[[:space:]]*[=:][[:space:]]*[^[:space:]#]' .env.oracle` 이 0 이어야 한다(빈 따옴표 `=""` 도 1 로 센다 — 그 줄은 `ANTHROPIC_API_KEY=` 로 둔다). 서버 셸 `[ -z "${ANTHROPIC_API_KEY:-}" ] && echo 비어 있음 || echo 들어 있음` 은 "비어 있음"이어야 한다. 아니면 env 파일은 편집기로 비우고, 셸은 `unset ANTHROPIC_API_KEY` 한 뒤 로그인 스크립트(`~/.bashrc`·`~/.profile` 등)의 export 줄도 지운다 — 배포가 API 를 다시 만들 때 이 값들이 들어간다.
   - T-146 을 배포하고, 배포된 컨테이너에 키가 없는지 본다: `bash scripts/oracle/compose.sh exec -T api sh -c '[ -z "$ANTHROPIC_API_KEY" ] && echo 비어 있음 || echo 들어 있음'`(들어 있으면 위처럼 비우고 4단계 2번 명령으로 다시 만든다). 마이그레이션 `20261014090000_ai_qa_consent` 적용도 확인한다 — 점검 SQL 의 켜진 회사 수가 0 이어야 한다. 점검 SQL 은 이 마이그레이션의 칸을 읽으므로 배포 뒤에만 돈다.
   - 같은 점검 SQL 의 "AI 를 부른 질문" 목록이 비어 있어야 한다(마이그레이션은 질문 기록을 건드리지 않는다). 있으면 동의 절차 없이(T-130 은 기본 켜짐) 이미 외부로 나간 것이니 사고로 다룬다 — 2단계(파기 cron)로 가지 말고 PM 에 알려 회사별 건수를 남긴 뒤 판단을 기다린다.
2. 질문 기록 파기 cron 을 걸고(아래) 한 번 직접 돌려 본다: `bash scripts/oracle/ai-qa-purge.sh; echo $?` → `[ai-qa-purge] 90일 지난 기록 N건 삭제` 줄과 0.
3. 선행 작업을 끝낸다. 대장 T-157 은 개발 환경 확인(구조화 출력·대체 모델·캐싱·처리 지역)까지만 여기의 선행 조건이다 — 운영 키는 4단계 2번에서만 넣고, T-157 의 운영 확인은 4단계가 대신한다. 그리고 T-171(백업 보관 기간을 정해 고지 문구·판 올림을 운영에 배포하고, 처리방침 보관 기간 항목에도 적는다), 처리방침의 국외 이전 항목 공개, 쓰려는 고객사와 개인정보 처리위탁 계약(재위탁·국외 이전 동의 — `19_법무문서`, 변호사 검토 뒤). 4·5단계의 동의는 T-171 이 반영된 고지로 받는다.
4. 운영 키를 넣고 실제 호출을 한 번 확인한다. 키는 넣는 즉시 모든 회사에 적용되므로(메뉴가 보이고 관리자가 켤 수 있다) 사용이 적은 시간에 하되, cron(04:10 파기·04:30 법령 동기화)과 겹치는 04:00~05:00 은 피한다.
   1. 키를 넣기 전에 운영에 배포된 고지의 보관 기간을 찍어 본다: `bash scripts/oracle/compose.sh exec -T api node -e "console.log(require('./dist/ask/ask-notice').aiQaNotice().retention.join('\n'))"`. 백업 일수가 T-171 에서 정하고 처리방침에 적은 일수와 같아야 한다 — 다르거나 숫자가 없으면 키를 넣지 않고 3단계로 돌아간다. 점검 SQL 도 한 번 돌려 켜진 회사 목록을 적어 둔다(되돌릴 때의 기준).
   2. `.env.oracle` 을 편집기로 열어 `ANTHROPIC_API_KEY=` 에 키를 넣는다(줄이 없으면 더한다. 셸 기록에 남지 않게 `echo` 로 쓰지 않는다). `bash scripts/oracle/compose.sh up -d --wait --force-recreate api web` 로 API·웹 컨테이너를 다시 만든다 — 환경변수는 다시 만들어야 들어가고(`restart` 로는 안 된다), 웹(nginx)은 기동할 때 API 주소를 한 번만 찾으므로 함께 다시 만든다. 명령이 끝나면 웹을 거친 `/api/health` 까지 상태 확인을 통과한 것이다.
   3. 아스트룸 자체 시험 회사(고객 데이터가 없는 회사 — 없으면 통합 관리자 화면에서 만든다)의 관리자로 로그인해 **규정을 하나 만들고 지난 날짜를 시행일로 발행한다**. 규정 질문 화면에서 "회사 전체 켜기"로 고지를 확인하고 켠 뒤 그 규정 내용을 묻는다.
   4. 점검 SQL 에서 시험 회사의 `최근_하루_답한_질문` 이 1 이상이어야 AI 가 실제로 답한 것이다(화면 문구만으로는 가리지 못한다 — 시행 중인 규정이 없거나 고르기 전에 끝나면 AI 를 부르지 않는다). 그리고 `bash scripts/oracle/compose.sh logs api` 에서 기동 줄(`Application is running on port`) 뒤로 `AI 처리 지역이 us 가 아님` 경고가 없어야 한다(응답의 처리 지역이 us 가 아니거나 응답에 지역이 없어도 이 경고가 남는다).
   5. **2~4번 가운데 하나라도 어긋나면 5단계로 가지 않고 되돌린다.** 먼저 로그를 저장한다(다시 만들면 옛 컨테이너 로그가 사라진다): `bash scripts/oracle/compose.sh logs --no-color api > ~/ai-qa-check-$(date +%Y%m%d%H%M).log`. 시험 회사를 끄고, `.env.oracle` 의 키를 빈 값으로 되돌려 2번 명령으로 다시 만든 뒤 규정 질문 메뉴가 사라졌는지(직접 들어가면 "규정 질문(AI)은 아직 준비 중입니다") 본다(열어 둔 탭은 새로고침한 뒤). 1단계의 컨테이너 확인 명령으로 "비어 있음"도 본다. 점검 SQL 의 켜진 회사 목록을 1번에서 적어 둔 것과 견줘, 그사이 켠 회사가 있으면 그 회사에 알린다. 그다음 저장한 로그로 원인을 확인하고, 확인이 끝나면 그 로그 파일을 지운다.
   6. 모두 맞으면, 시험 회사는 계속 쓸 게 아니면 끈다.
5. 고객사 관리자가 규정 질문 화면에서 고지를 확인하고 켠다. 아스트룸이 대신 켜는 길은 없다(동의는 고객사 몫).

질문 기록 파기 — 서버 crontab 에 한 줄(법령 동기화 04:30 과 겹치지 않게):

```bash
10 4 * * * cd ~/policy_manager && bash scripts/oracle/ai-qa-purge.sh >> ~/ai-qa-purge.log 2>&1
```

- 90일(코드 상수 `AI_QA_LOG_RETENTION_DAYS`)보다 오래된 질문·답 기록을 모든 회사에서 지운다. 로그에는 지운 건수만 남고 질문 내용은 남지 않는다. 실패하면 종료 코드 1.
- **파기가 실제로 도는지 주 1회 확인한다**(cron 이 빠지면 고지의 "90일 보관한 뒤 지웁니다"가 거짓이 된다): `tail ~/ai-qa-purge.log` 와 점검 SQL — 가장 오래된 기록의 지난 일수가 90 을 넘으면 cron 을 확인한다(하루 한 번, 정확히 90일 기준으로 지우므로 정상이면 지난 일수 — 하루 미만은 버린 값 — 가 90 을 넘지 않는다).
- 보관 일수는 관리자가 동의한 고지에 실린다 — 바꾸려면 코드에서 바꾸고 `apps/api/src/ask/ask-notice.ts` 의 그 제공사 고지 판(`AI_QA_NOTICE_VERSIONS`, T-208 부터 제공사별)을 올려 배포한다(고지 지문 시험이 잡는다). 판을 올리면 모든 회사가 관리자가 다시 확인할 때까지 꺼진다.
- **백업에는 파기 전 기록이 남는다.** 고지는 "장애 복구용 백업에는 백업 보관 기간 동안 남습니다"라고만 적는다. 지금 배포 전 로컬 덤프(`backups/oracle/*`)는 자동으로 지워지지 않고, 서버 밖 백업 보관 기간도 7-3(30일)과 `backup-oci.py`(14일)가 다르다 — 대장 T-171(백업 보관 기간 정리)을 끝내 운영에 배포하고 처리방침에 적기 전에는 운영 AI 키를 넣지 않는다(3단계).

## 7-9-1. 규정 질문을 무료 제공사 묶음으로 켜기 (T-208, ADR-0028)

Anthropic 키 없이 규정 질문을 무료 AI 제공사 묶음(freellmapi — 같은 서버의 내부 컨테이너, 호스트 포트 없음)으로 연다. 질문·조 목차·관련 조문·연결된 법령 조문이 **Google(Gemini API 무료 등급)·Groq** 로 간다. Google 무료 등급은 보낸 내용을 제품 개선·학습에 쓰고 사람이 검토할 수 있다 — 고객 데이터가 없는 시연·시험 회사로 먼저 쓰고, 실제 고객사를 받기 전에 유료 제공사로 돌아갈 시점은 D-26 에서 정한다. 고지는 제공사별이라(무료 = 판 2) 켜는 순간 이전 고지에 동의한 회사는 관리자가 다시 확인할 때까지 꺼진다.

1. 7-9 의 1·2단계(이미 나간 것이 없는지, 질문 기록 파기 cron)를 먼저 마친다.
2. 새 코드를 배포한다(4절·deploy.sh — 무료 제공사는 아직 꺼진 채라 배포에 영향이 없다).
3. Mac 에서 한 번 실행한다(키는 Mac `.env` 의 `FREELLMAPI_GOOGLE_KEY`·`FREELLMAPI_GROQ_KEY` 를 표준 입력으로만 넘기고 화면에 찍지 않는다):
   `ORACLE_SSH=ubuntu@<서버주소> bash scripts/oracle/ai-free-setup.sh`
   - 서버 `.env.oracle` 에 `COMPOSE_PROFILES=ai`·`AI_QA_PROVIDER=freellmapi`·제공사 키를 넣고, 암호화 키와 freellmapi 관리자 비밀번호는 없을 때만 새로 만든다(이전 파일은 `.env.oracle.bak-<시각>`).
   - 운영 설정 검사(validate-config.py — 암호화 키 64자리 16진수, 관리자 비밀번호 16자 이상, 제공사 키 하나 이상, 이미지 digest 고정) → `freellmapi` 기동 → api·web 다시 만들기.
   - 끝에 `freellm-init: 켠 제공사 google,groq · 통합 키를 공유 볼륨에 씀` 과 `api 제공사: freellmapi · 고지 판: 2` 가 보여야 한다. freellmapi 가 뜰 때 허용 제공사(Google·Groq) 밖의 키를 모두 끄고 통합 키를 api 와 함께 쓰는 볼륨에 쓴다 — 대시보드에서 키를 옮겨 적지 않는다.
4. 시험 회사에서 확인한다(7-9 의 4단계 3·4번과 같다): 관리자로 "바뀐 고지 확인하고 켜기" → 무료 제공사 고지(받는 곳 Google LLC·Groq, Inc., 학습·사람 검토, 민감·기밀 주의)를 확인하고 켠다 → 질문하면 직답·검토 표·우선 개정 권고·종합 의견·근거가 나와야 한다. 답한 모델은 질문 기록의 `model`(예: `google/gemini-3.8-flash`)에 남는다.
5. 한도: 무료 등급은 모델마다 하루 한도가 작다(카탈로그 기준 Gemini 3.5~3.7 Flash 는 하루 20회). 질문 하나가 고르기·답하기 두 번을 부르고, 한도에 걸리면 다음 허용 모델로 넘어간다. 모두 걸리면 "무료 AI 사용량이 지금 모두 찼습니다"로 끝난다 — 약한 모델로 내리지 않는다. 시연 날에는 개발·시험 호출로 한도를 쓰지 않는다.
6. 키 교체: `.env.oracle` 의 `FREELLMAPI_GOOGLE_KEY`·`FREELLMAPI_GROQ_KEY` 를 편집기로 바꾸고 `bash scripts/oracle/compose.sh up -d --wait --force-recreate freellmapi`(뜰 때마다 설정을 다시 적용한다). 암호화 키는 바꾸지 않는다.
7. 되돌리기: `.env.oracle` 에서 `AI_QA_PROVIDER=` 를 비우고 `COMPOSE_PROFILES` 에서 `ai` 를 뺀 뒤, 먼저 `COMPOSE_PROFILES=ai bash scripts/oracle/compose.sh stop freellmapi`, 이어서 `bash scripts/oracle/compose.sh up -d --wait --force-recreate api web`. 규정 질문은 "설정 안 됨"으로 돌아간다. 데이터 볼륨(`freellmapi_data` — 암호화된 제공사 키)은 남는다.
8. 고장 확인: `bash scripts/oracle/compose.sh logs --tail=50 freellmapi`(부팅 정책 실패면 `freellm-init: 실패 — …`), api 로그의 `AskFreeLlm` 줄(모델·사유만 남고 질문 내용은 남지 않는다). `허용하지 않은 제공사가 답함` 이 보이면 더 보내지 않고 멈춘 것이다 — freellmapi 키 목록을 점검한다.

## 7-10. 놓친 개정 후보 보충 (한 번, T-149)

T-149 부터 법령 관계를 확정하면, 그때 이미 들어와 있던 변경(최근 30일 안에 시행됐거나 앞으로 시행될 것)으로 그 조문의 개정 후보를 바로 만든다. 그 전에 놓친 두 가지는 T-149 를 운영에 낸 뒤 **한 번** 이 명령으로 만든다 — ㉠ 위 조항(조·항) 연결로만 닿는데 T-148 반영(2026-10-31 11:12:12Z) 전에 처리된 변경, ㉡ 처리한 뒤에 확정한 연결. 이 명령도 같은 창(법령 시행일이 실행일 − 30일 이후)만 보고 기능 도입 전 변경은 빼므로, 더 오래된 놓친 후보는 법령 화면의 '개정 후보 만들기'로 만든다. 저절로 돌지 않는다.

명령은 서버의 `~/policy_manager` 에서 `scripts/oracle/amendment-catchup.sh`(compose.sh 경유)로만 돌린다. 출력은 tee 로그로 서버에 남긴다 — 로그에는 운영 회사 id·연결 id 가 찍히므로 대장(공개 저장소) T-187 에는 요약 줄(실행 시각·합계·회사 수·잘못된 행 수·'일치합니다' 여부)만 옮긴다. tee 를 쓰면 종료 코드 대신 마지막 요약 줄로 판단한다. 다른 인자는 받지 않는다(`--paln` 같은 오타는 쓰지 않고 1 로 끝난다).

1. 계획을 본다(DB 에 쓰지 않는다): `bash scripts/oracle/amendment-catchup.sh --plan 2>&1 | tee ~/amendment-catchup-plan-$(date +%Y%m%d%H%M).log`
   - 회사마다 `만들 후보 N건(변경·조문)`과 대상 조문의 까닭(㉠·㉡)이(대상 가운데 기준 본문 없음·폐지·본문 변화 없음으로 만들지 않을 것이 있으면 그 수도), 합계 줄에 `확정 시각이 빈 확정 연결`(DB 에 직접 넣은 행 — 생성 시각으로 봤다)과 `잘못된 행` 수가 찍힌다.
   - **잘못된 행**(연결의 회사 ≠ 조문의 회사 — 어느 회사 화면에도 안 보이고 API 로 지울 수 없는데 법령 추적 해제는 막는다)이 있으면 id 와 지울 SQL 이 함께 찍힌다. 코드는 지우지 않는다. PM 이 id 를 확인한 뒤 서버에서 백업을 뜨고(`bash scripts/oracle/backup-local.sh`), 로그의 SQL 을 `~/delete-invalid-links.sql` 로 저장해 `bash scripts/oracle/compose.sh exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -1 -f -' < ~/delete-invalid-links.sql` 로 돌린다(7-6 의 점검 경로는 읽기 전용이라 DELETE 가 거부된다). 그 연결을 가리키던 후보의 `law_link_id` 는 비워지고 근거 스냅샷은 남는다.
2. 합계가 100건 이하이고 어느 회사도 20건을 넘지 않으면 실행한다: `bash scripts/oracle/amendment-catchup.sh 2>&1 | tee ~/amendment-catchup-$(date +%Y%m%d%H%M).log` — 마지막 줄이 `만든 후보 N건 / 계획 N건 — 일치합니다` 여야 한다. 후보를 만든 회사마다 관리자·편집자에게 알림 하나가 간다(개정 후보 목록으로 이동).
   - 상한을 넘으면 명령이 만들지 않고 `상한을 넘었습니다` 로 끝난다(종료 코드 2). PM 에게 계획 로그를 보이고, 승인하면 그 값을 `--max-total N --max-per-tenant N` 으로 적어 다시 돌린다 — 첫 줄에 쓴 상한과 `(기본값 아님 — PM 승인 없이 쓰지 않는다)` 가 찍혀 로그에 남는다. 값은 숫자만 받는다.
   - `어긋납니다`·`세지 못한 변경` 으로 끝나면(종료 코드 1) 같은 tee 로그에서 `개정 후보 생성 실패(catchup)` 줄(변경 id 와 사유)을 찾고 `--plan` 을 다시 본다 — 명령은 api 컨테이너 안에서 따로 도는 프로세스라 그 줄은 `compose.sh logs api` 가 아니라 명령 출력에 남는다. 다시 돌려도 이미 만든 후보는 건너뛴다.
   - 회사 줄에 `알림을 보내지 못했다` 가 찍히면 후보는 만들어졌고 알림만 빠진 것이다(다시 돌려도 알림은 다시 가지 않는다) — PM 이 그 회사 관리자에게 개정 검토 화면을 보라고 따로 알린다.
3. 같은 명령을 한 번 더 돌려 `만든 후보 0건 / 계획 0건` 인지 본다.

- `--tenant <회사 id>` 는 시험·점검용이다(그 회사만). 운영 실행은 범위 없이 돌린다.
- 시연 전에 볼 것: 시연 법령의 변경은 법령 시행일이 오늘 − 30일보다 오래되면 연결을 확정해도 후보가 생기지 않는다(창 밖) — 그때는 법령 화면의 '개정 후보 만들기'로 시연한다.

## 7-11. 시연 준비 — 시연 규정과 개정 검토 대기 후보 채우기 (T-216, ADR-0029)

시연 전용 고객사에 직접 쓴 예시 규정 6개(취업규칙·직장 내 성희롱 예방·퇴직급여·이사회 운영·개인정보 보호·안전보건관리, `scripts/demo/policies`)를 넣고, **그 서버가 법제처 동기화로 감지한 실제 법령 개정**에 법령 연결을 확정해 개정 검토 대기 후보를 만든다. 시연에서 후보를 처리한 뒤에는 다시 채운다. 스크립트는 고객사 관리자 계정으로 **공개 API 만** 부른다 — DB 에 직접 쓰지 않고, 법령 동기화·후보 승인은 하지 않는다. 운영 실행은 PM 이 Mac(저장소, Node 20 이상)에서 한다 — 서버 동결 중이면 동결이 풀린 뒤.

- **먼저 정할 것**: D-27(어느 고객사에 채울지·시연 규정 원문·요금제). T-187 시연이 끝나기 전에는 T-187 시연 회사에서 돌리지 않는다(리허설한 배너·배지 숫자가 바뀐다).
- 명령 예는 자리표시자다. 서버 주소·계정은 환경변수로만 넘기고(기본값 없음), 비밀번호는 `VEDA_DEMO_PASSWORD` 를 비워 두면 터미널에서 숨김 입력을 받는다. 셸 기록에 남지 않게 값은 `read` 로 받아 넘긴다: `read -r VEDA_DEMO_URL; read -r VEDA_DEMO_TENANT; read -r VEDA_DEMO_EMAIL; export VEDA_DEMO_URL VEDA_DEMO_TENANT VEDA_DEMO_EMAIL`. 스크립트는 이 값들을 출력하지 않고, 주소에 계정을 넣으면(`https://이름:비밀번호@…`) 받지 않으며, 넘겨주기(3xx)를 따라가지 않는다.
- **시연 전용 고객사에서만** 돌린다 — '개정 후보 만들기'(서버)는 그 고객사에서 그 변경이 닿는 **모든** 확정 연결의 조문에 후보를 만든다. 그래서 스크립트는 만들기 전에 서버의 영향 판정으로 그 변경이 닿는 조문을 보고, 시연 규정이 아닌 규정에도 닿는 변경은 만들지 않고 알린다(`다른 규정에도 닿아 …`) — 실제 규정이 있는 고객사에서는 그만큼 시연 후보가 덜 생긴다.
- 결과를 대장·런북에 옮길 때는 **법령명과 건수만** 적는다 — 회사 id·연결 id·계정 이메일은 적지 않는다(T-187 선례).

1. **시연 전용 고객사**를 통합 관리자 화면에서 연다(7-7) — 요금제 **Pro 이상**(Starter 는 규정 5개까지라 6개를 넣지 못한다). 첫 관리자로 화면에서 한 번 로그인해 임시 비밀번호를 바꾼다. 바꾼 비밀번호는 저장소·대장에 적지 않는다.
2. **계획을 본다**(쓰지 않는다). 주소·기관 코드·관리자 이메일은 명령줄에 적지 않고(셸 기록에 남는다) 하나씩 붙여 넣는다:
   ```bash
   read -r VEDA_DEMO_URL; read -r VEDA_DEMO_TENANT; read -r VEDA_DEMO_EMAIL   # https://<도메인>, <기관 코드>, <관리자 이메일>
   export VEDA_DEMO_URL VEDA_DEMO_TENANT VEDA_DEMO_EMAIL
   node scripts/demo/seed-demo.mjs --plan
   ```
   - 첫 줄의 **대상 고객사** 이름이 시연 전용 고객사인지 확인한다.
   - **새로 등록할 법령**: 서버 법령 목록에 없는 인용 법령(법제처에서 찾은 것). 등록한 법령은 **모든 고객사의 공용 목록**에 남고, 연결·후보가 남는 한 누구도 해제할 수 없다(LAW-18) — 운영에서는 PM 이 이 목록을 먼저 보고 실행한다.
   - **같은 코드의 다른 규정**이 있으면 아무것도 쓰지 않고 멈춘다(까닭을 함께 적는다). 이 스크립트가 넣은 규정은 가져오기 이력에 표시(`veda-demo-seed:<코드>`)가 있고 내용(제목·설명·부서·분류)이 시연 문서와 같은 것**뿐**이고, 스크립트는 이렇게 확인한 규정만 지우거나 잇는다. 까닭은 셋이다 — `내용이 시연 규정과 다름`(화면에서 고쳤다), `이 스크립트의 가져오기 표시 없음`, `… 확인할 수 없음`(가져오기 이력은 최근 30건만 보여, 다른 가져오기가 쌓이면 표시가 밀려났을 수 있다). 시연 규정이 맞으면 화면에서 그 규정을 지운 뒤 `--reset` 없이 다시 실행한다. 저장소의 시연 문서에서 제목·설명·부서·분류를 고친 뒤에도 이미 넣은 시연 규정이 모두 `내용이 다름` 으로 멈춘다 — 같은 방법으로 지우고 다시 넣는다.
   - **쓸 법령 변경**: 법령·판·공포일·시행일과 '창 안(연결하면 바로 후보)' / "창 밖('개정 후보 만들기'로)", 닿는 조문 수, 새 후보 수(최대 — 서버가 실질 변경 없음·시행 본문 없음은 건너뛴다. 이미 이 변경의 후보가 있는 조문은 상태와 관계없이 '이미 있음'), `다른 규정에도 닿아 만들지 않음`, `예전 시연 규정에 닿아 만들지 않음`, `일부 조문에만 후보가 있어 만들지 않음`. 후보 수는 실행과 같은 규칙으로 센다 — 이미 넣은 시연 규정은 서버의 지금 영향 판정(화면에서 손으로 더 건 연결 포함)에 이번에 잇는 연결을 더한다. 창은 '법령 시행일 ≥ 오늘 − 30일'이라 날마다 움직인다 — 시연 직전에 한 번 더 본다. 변경이 100건을 넘는 법령은 서버가 가장 늦게 감지한 100건만 주어 그렇다고 적는다.
   - 후보가 없을 인용 법령은 실행 결과와 같은 묶음으로 적는다 — `닿는 변경은 있지만 후보가 생기지 않을 법령`(반려된 연결·법령에 없는 조항·규정에서 찾지 못한 행·다른 규정에도 닿음·예전 시연 규정에 닿음·시행 본문 없음 — 반려된 연결과 찾지 못한 조항·행은 위에 `!` 줄로 나온다), `시연 조문에 닿는 변경이 없는 인용 법령`. 처리 대기가 0건으로 끝날 계획이면 마지막 줄이 PM 에게 올릴 것을 알린다(아래 3의 마지막 줄 규칙, 완료 정의 ③). `규정에서 그 행을 찾지 못해 잇지 않음` 은 남아 있는 시연 규정에서 화면으로 조문을 지우거나 번호를 바꾼 것이다(처음 시연 규정으로 되돌리려면 6). `예전에 이 스크립트가 넣은 것으로 보이는 규정` 은 시연 문서에서 빼거나 코드를 바꾼 뒤 남은 규정이다 — 스크립트는 지우지 않는다. 남아 있으면 그 규정에 닿는 변경은 만들지 않는다 — 그 규정에만 닿으면 `예전 시연 규정에 닿아 …` 로 알리고 화면에서 지우면 풀리며(일부 시연 조문에 그 변경의 후보가 있거나 이번 연결로 생기면 지운 뒤 6 의 `--reset` 까지 — 지우기만 하면 `일부 조문에만 후보` 로 다시 막힌다), 다른 규정에도 닿으면 `다른 규정에도 닿아 …` 로 알린다(지워도 막힌다 — 실행 결과의 그 줄에는 `(다른 규정 N개 · 예전 시연 규정 N개)` 가 붙는다). `법령 연결` 줄은 실행과 같은 셈이다 — 새로·이미 있음·`추천을 확정`(반려된 연결은 `!` 줄로만 나오고 잇지 않는다). `만든 후보 N건을 모두 처리(승인·반려)했습니다` 는 변경이 없어서가 아니라 시연에서 처리했기 때문이다 — 6(다시 채우기)으로 간다. 법제처에서 **현행** 판을 찾지 못한 법령은 등록하지 않고 `법제처에서 찾지 못한 법령` 으로 알린다. `비어 있는 날짜를 채울 시연 규정` 은 앞 실행이 넣은 뒤 날짜를 채우다 멈춘 규정이다(비어 있는 칸만 채운다).
3. **실행한다**: 같은 명령에서 `--plan` 을 뺀다. 요청 한도(운영 분당 100) 안에서 천천히 보내므로 몇 분 걸린다. 끝에 넣은 규정·등록한 법령·법령 연결·개정 후보·검토 요청 건수와 **처리 대기 후보(법령별)** 가 찍히고, 후보가 하나도 없는 인용 법령은 까닭별로 적는다 — `새로 등록해 아직 변경이 없는 법령`(4로), `등록했지만 목록에서 이름으로 찾지 못해 잇지 못한 법령`(개발팀에 알린다), `닿는 변경은 있지만 후보가 생기지 않은 법령`(실질 변경 없음·시행 본문 없음·다른 규정에도 닿음·예전 시연 규정에 닿음·잇지 않은 인용, 곧 반려된 연결·법령에 없는 조항·규정에서 찾지 못한 행), `시연 조문에 닿는 변경이 없는 인용 법령`(처리 대기가 끝내 0건이면 PM 에게 올린다), `등록되지 않은 인용 법령`(법제처에서 현행 판을 찾지 못해 등록하지 않았다). 시행 본문이 없어 후보를 만들 수 없는 시연 조문은 `건너뜀` 으로 센다. 개정 후보 줄의 `새로 N건(연결하면서 생김 A · 만들기 B)` 은 계획의 `연결하면 바로 A · 만들기 B` 와 같은 셈이다(연결을 확정할 때 서버가 바로 만든 후보도 새로 센다 — 실행 전에 없던 후보만 세므로, 화면에서 지운 시연 연결을 다시 이어 옛 후보가 다시 보이는 조문은 `이미 있음` 이다). 만들지 않은 수(`다른 규정에도 닿아`·`예전 시연 규정에 닿아`·`일부 조문에만 후보가 있어`)도 계획처럼 후보(조문) 수로 적는다. 실행하는 동안에는 화면에서 같은 시연 규정의 연결·후보를 고치지 않는다 — 고치면 `새로`·`이미 있음` 의 셈이 틀릴 수 있다(처리 대기 수는 맞다). 다시 돌려도 이미 있는 규정·연결·후보는 다시 만들지 않는다 — '개정 후보 만들기'는 닿는 시연 조문에 이 변경의 후보가 하나도 없을 때만 부른다. 서버의 후보 중복 판정에는 예정 시행일(시행일이 지난 변경은 그날)·발행 이력·공통 기준값 지문이 들어 있어, 이미 후보가 있는 조문에 부르면 다른 날이거나 승인으로 판이 늘었을 때 같은 변경의 후보가 또 생긴다. 일부 조문에만 후보가 있으면 만들지 않고 `일부 시연 조문에만 후보가 있어 …` 로 알린다 — 그 조문까지 채우려면 6(`--reset`). 다른 규정에도 닿는 변경은 일부 조문에 후보가 있어도 `다른 규정에도 닿아 …` 로 알린다 — `--reset` 으로는 풀리지 않는다(그 규정의 연결은 남는다).
   - 계획과 실행의 마지막 줄은 같은 규칙이다(처리 대기 후보가 없을 때만 나온다). 0건이면 완료가 아니므로 어느 갈래든 끝내 PM 에게 올리는 길을 적는다. 만든 후보를 모두 처리했으면 `--reset` 을 알린다. 위 법령 줄에 까닭이 있으면(닿는 변경은 있지만 후보가 생기지 않음·등록 뒤 못 찾음) `위 법령 줄의 까닭을 보세요` 를 알린다. 다른 규정이나 예전 시연 규정에 닿아 막힌 변경의 법령도 '닿는 변경은 있지만 후보가 생기지 않음'에 든다. 반려된 연결과 예전 시연 규정은 화면에서, 규정에서 찾지 못한 행은 `--reset` 으로, 다른 규정에도 닿는 변경은 시연 전용 고객사에서 풀고, 풀 수 없는 까닭(실질 변경 없음·시행 본문 없음·법령에 없는 조항·등록 뒤 못 찾음)이면 그 목록을 까닭과 함께 PM 에게 올린다. 새로 등록한 법령이 남았으면 그 법령은 공포됐지만 시행 전인 판이 있을 때만 다음 동기화 뒤에 변경이 생긴다(스크립트는 알 수 없다) — 닿는 변경이 없는 다른 인용 법령이 있으면 그 목록은 바로 PM 에게 올리고 동기화 뒤 다시 실행하며, 없으면 동기화 뒤 다시 실행하고 그래도 없으면 PM 에게 올린다. 인용 법령에 닿는 변경이 하나도 없으면 `감지한 변경이 없습니다 … PM 에게`.
   - 멈추는 경우(종료 코드): 비밀번호 변경 요구·관리자 아님·로그인 실패 3 — 로그인 실패는 까닭을 적는다(고객사를 찾지 못함·이메일과 비밀번호가 틀림·비밀번호가 설정되지 않은 계정·형식 오류). 법제처 연동 없음·이 스크립트 것으로 확인할 수 없는 같은 코드의 규정·규정 자리 부족 4, 환경변수·주소 2, 그 밖의 실패 1 — 서버 거절(경로·상태 번호), 연결 실패(까닭 코드 — 넘겨주기(3xx)면 따로 적는다), 주소가 VEDA API 가 아님(성공인데 JSON 이 아니다, 로그인 응답이 JSON 이 아니고 성공·401·403·404·405 다 — 다른 서비스나 앞단 관문, 넘겨주기(3xx) — 주소를 고친 뒤 다시), 예상하지 못한 오류(오류 이름과 글). 실패 글의 경로에서 규정·연결·후보 id 는 `:id` 로 가린다. 로그인이 503 같은 서버 장애로 실패해도 비밀번호를 다시 넣지 말고 서버를 확인한다 — 앞단이 낸 그 밖의 화면(429·5xx 등)은 그 상태 번호로 알리고, 5xx 는 로그인이든 다른 경로든 `VEDA 서버(api)가 떠 있는지 확인하세요` 를 붙인다.
   - **중간에 실패하면**(종료 1) 출력의 안내를 따른다 — 서버 거절·연결 실패면 같은 명령을 다시 실행한다(이미 넣은 규정·연결·후보는 건너뛰고 이어서 채운다). `--reset` 중이면 어디서 멈췄는지에 따라 다르다 — 옛 시연 규정을 다 지운 뒤면 `--reset` 없이(이어서 넣는다, `--reset` 은 다시 지운다), 다 지우기 전이면 `--reset` 을 붙여 다시(남은 옛 규정을 지운다). '예상하지 못한 오류'면 다시 돌리기 전에 그 출력을 개발팀에 알린다(같은 곳에서 다시 멈출 수 있다).
4. **새로 등록한 법령이 있었으면** 다음 동기화(매일, 7-5 — 또는 통합 관리 › 법령 동기화 '지금 실행') 뒤에 3을 다시 돌린다. 등록한 법령은 현행 판이 기준이라 그때까지 변경이 없다 — 공포됐지만 시행 전인 판이 있는 법령만 동기화 뒤에 변경이 생긴다.
5. **볼 화면**(시연 고객사 관리자로): 대시보드(지표 카드·법령 개정 구역·처리할 개정), 개정 검토 목록(검토 중 하나·작성 중), 후보 상세(신구 비교·법령 변경), 규정 상세의 신구조문대비표·3단비교, 개정안 PDF.
6. **시연 뒤 다시 채우기**: `node scripts/demo/seed-demo.mjs --reset`(같은 환경변수). 2에서 이 스크립트가 넣었다고 확인한 시연 규정(표시와 내용이 맞는 것)만 지우고 다시 넣는다 — 확인할 수 없는 같은 코드의 규정이 있으면 아무것도 지우지 않고 멈춘다(2의 까닭과 같다). 규정을 지우면 그 조문의 법령 연결·개정 후보가 함께 지워지고, 다시 넣으면 새 조문으로 후보가 다시 생긴다. 승인한 후보로 바뀐 본문도 처음 시연 규정으로 돌아간다. `--reset` 없이 다시 돌리면 이미 후보가 있는(승인·반려한 것 포함) 조문에는 새로 만들지 않아, 처리 대기는 그대로 0건이고 `--reset` 을 알린다.
