# 법령 개정 연계 설계안

작성일: 2026-09-21
근거: 특허 명세서 `26PD0271KR_명세서_수정안rev1.docx` (발명의 명칭 「법령 개정 연계형 사내 규정 개정 관리 방법, 시스템 및 컴퓨터 판독가능한 기록매체」) + 현재 코드베이스 실측

## 0. 이 문서가 생긴 이유

2026-09-21까지 이 저장소의 어떤 문서에도 **"법령이 바뀌면 사내 규정을 고쳐 준다"** 는 요구사항이 없었다.
요구사항 대조를 두 번(9/2, 9/13) 했는데도 나오지 않았다. 없는 게 아니라 **개발문서가 아닌 특허 명세서에 있었기 때문**이다.

명세서는 "이미 만든 것"이 아니라 **"만들 것"** 을 쓴 것이라고 대표가 확인했다(2026-09-21).
따라서 명세서는 곧 이 제품의 로드맵이고, 이 문서는 그 청구항을 **데이터 모델·처리 흐름·API·화면**으로 옮긴 것이다.

> 특허 청구항과 이 설계가 어긋나면 **특허 쪽이 기준**이다. 구현이 청구항 밖으로 나가면 방어 범위가 줄어든다.
> 어긋나는 걸 발견하면 고치지 말고 먼저 기록하고 변리사에게 확인할 것. 8절에 현재 발견된 불일치를 모아 뒀다.

## 1. 한 문장 요약

> 상위 법령의 조항이 바뀌면, **그 조항에 연결해 둔 사내 조문**을 찾아, **고쳐 쓴 초안과 그렇게 고친 근거**를 만들어
> **사람에게 보여 주고**, **사람이 승인했을 때만** 기존 조문 번호를 유지한 채 다음 버전으로 발행한다.

핵심은 **자동 개정이 아니라 추천 + 사람 승인**이다. 이건 취향 문제가 아니다:

- **법적 이유**: 사내 규정은 취업규칙·이사회 의결 등 사내 절차를 거쳐야 효력이 생긴다. 시스템이 임의로 바꾸면 그 규정은 효력이 없다.
- **특허 이유**: 청구항 1의 마지막 구성요소가 *"검토 단말로부터 제2 조문에 대한 승인 정보를 수신한 것에 응답하여"* 다.
  **사람의 승인이 청구항의 구성요소**라서, 승인을 건너뛰면 청구항 1을 실시하지 않는 게 된다.

## 2. 용어 — 명세서 용어 ↔ 코드 이름

명세서 용어를 그대로 코드에 쓰지 않는다(길고 한글이다). 대신 **1:1로 고정**해 둔다.
이 표가 특허와 코드를 잇는 유일한 사전이다. 이름을 바꾸려면 이 표부터 고칠 것.

| 명세서 용어 | 코드 이름 | 설명 |
|---|---|---|
| 사내 조문 | `Article` | 기존 |
| 조문 식별자 | `Article.id` | 기존. **개정되어도 바뀌지 않는다** — 이게 발명의 축 |
| 조문 버전 | `ArticleVersion` | 기존 |
| 제1 조문 | 영향 분석 기준일에 유효한 `ArticleVersion`(published) | 기존 조회 로직 재사용 |
| 제2 조문 | `AmendmentCandidate.candidateContent` | **신규** |
| 법령원 | `LawSource` | **신규**. 법제처 DRF 등 |
| 법령 | `Law` | **신규** |
| 법령조항 / 법령조항 식별자 | `LawArticle` / `LawArticle.id` | **신규** |
| 법령 관계 정보 | `LawLink` | **신규**. 법령조항 ↔ 사내 조문 |
| 변경 이벤트 | `LawChangeEvent` | **신규** |
| 영향 조문 | `LawLink`로 도달한 `Article` | 조회 결과이지 테이블이 아님 |
| 후보 레코드 | `AmendmentCandidate` | **신규** |
| 변경 근거 정보 | `AmendmentCandidate.rationale` | **신규** |
| 변경 전후 비교 정보 | `AmendmentCandidate.diff` | 생성기는 기존 `policy-compare.ts` 재사용 |
| 검토 단말 | 웹 UI (`/amendments`) | **신규 화면** |
| 변수 마스터 | `Variable` + `VariableValue` | `VariableValue` **신규**(T-109 ①) |
| 변수 바인딩 정보 | `VariableBinding` | **신규**(T-109 ① — 옛 `VariableUsage` 를 위치를 가진 연결로 바꿈) |
| 법령 시행일 | `LawChangeEvent.lawEffectiveDate` | **신규** |
| 발행일 | `ArticleVersion.publishedAt` | **신규 필드** |
| 사내 규정 시행일 | `ArticleVersion.effectiveDate` | 기존 |

## 3. 이미 있는 것 / 없는 것

청구항 1을 7단계로 쪼개 현재 코드와 대조했다.

| # | 청구항 1의 단계 | 현재 |
|:--:|---|---|
| ① | 규정 문서 파싱 → 조문별 본문·계층 → 조문 버전 저장 | ✅ `regulation-parse` + `Article`/`ArticleVersion` |
| ② | **법령조항 식별자 ↔ 조문 식별자 연결(법령 관계 정보) 저장** | ❌ **없음.** `Article.relatedLawNote`는 자유 텍스트 메모라 기계가 따라갈 수 없다 |
| ③ | **변경 이벤트 수신** (변경 법령조항 id·전후 본문·법령 시행일) | ❌ **없음.** `lawgokr` 모듈은 요청이 올 때만 조회하는 프록시이고 아무것도 저장하지 않는다 |
| ④ | 영향 조문 식별 | ❌ 없음 (②가 없으면 성립 불가) |
| ④ | 기준일에 유효한 발행 버전(제1 조문) 취득 | ✅ 시점 조회(as-of, T-72) |
| ⑤ | **개정 후보 본문(제2 조문) + 변경 근거 정보 생성** | ❌ **없음** |
| ⑤ | 변경 전후 비교 정보 생성 | ✅ 대비표(T-56)의 낱말 단위 diff |
| ⑥ | 검토 단말 제공 | ⚠️ 워크플로(draft→review)는 있으나 **후보를 보여 주는 화면이 없다** |
| ⑦ | 승인 시 **조문 식별자 유지**하며 후속 버전 저장 + 사내 시행일 부여 + 발행 | ✅ 버전 승인(T-10)이 이미 `articleId`를 유지한다 |

**결론: 빠진 것은 하나의 사슬이다 — 연결(②) → 감지(③) → 영향분석(④) → 후보생성(⑤).**
나머지는 이미 만들어 둔 것 위에 얹힌다.

종속항 대조는 [7절](#7-종속항-대조)에 있다.

## 4. 데이터 모델

### 4.1 설계 결정: 법령은 `Policy`가 아니다

전부터 열려 있던 질문 — *"법제처에서 가져온 법령을 사내 규정과 어떻게 구분하나"* — 이 여기서 닫힌다.

선택지는 셋이었다: ① `Policy`에 플래그를 달아 같이 담는다 ② 테넌트별로 복사해 담는다 ③ **별도 엔티티로 분리하고 참조만 한다.**

**③으로 확정한다.** 근거는 취향이 아니라 청구항이다.

- 청구항 1은 *법령조항 식별자*와 *조문 식별자*를 **서로 다른 것으로 전제**하고 그 사이에 관계 정보를 둔다. 같은 테이블에 담으면 이 구조가 표현되지 않는다.
- 청구항 3은 영향 조문 식별이 *"복수의 사내 규정에 속한 사내 조문 노드들"* 에 도달한다고 한다. 즉 **법령 1건 : 사내 조문 N건(여러 규정·여러 테넌트)** 이다. `Policy`로 담으면 테넌트별 복사본이 생겨 N:M이 깨진다.
- 실무적으로도, 근로기준법은 모든 고객사에 대해 같은 내용이다. 테넌트마다 복사하면 같은 법을 고객사 수만큼 폴링하게 된다.

→ [ADR-0020](../10_ADR_의사결정기록/ADR.md) 참고.

### 4.2 테넌트 경계

이 설계에서 **가장 틀리기 쉬운 부분**이다. 새 테이블 6개 중 3개는 테넌트 공용이고 3개는 테넌트별이다.

| 테이블 | `tenantId` | 이유 |
|---|:--:|---|
| `LawSource` | ❌ 없음 | 법제처는 모두에게 하나다 |
| `Law` | ❌ 없음 | 근로기준법은 모든 고객사에 같다 |
| `LawArticle` | ❌ 없음 | 위와 같음 |
| `LawChangeEvent` | ❌ 없음 | 법이 바뀐 사실 자체는 공용. **누가 영향받는지는 `LawLink`가 정한다** |
| `LawLink` | ✅ **필수** | *우리 회사의* 어느 조문이 이 법에 걸리는지. **회사 기밀이다** |
| `AmendmentCandidate` | ✅ **필수** | 우리 회사 규정의 개정 초안 |

> ⚠️ **`LawLink`와 `AmendmentCandidate`에 `tenantId` 필터를 빠뜨리면 다른 회사의 규정 구조가 노출된다.**
> 이 저장소는 DB Row-Level Security를 쓰지 않고 애플리케이션이 매 쿼리에 필터를 건다([ADR-0002](../10_ADR_의사결정기록/ADR.md)).
> T-41 감사에서 찾은 2건이 전부 **"부모를 안 보고 자식만 확인한"** 경우였다. 여기서도 같은 실수가 가능하다:
> `LawArticle`에는 `tenantId`가 없으므로, **법령조항 id로 시작하는 조회는 반드시 `LawLink.tenantId`에서 경계를 걸어야 한다.**
> 청구항 3도 같은 것을 요구한다 — *"애플리케이션의 테넌트 조건이 적용되는"*.

### 4.3 신규 테이블

```prisma
/// 법령원 — 법령 데이터를 제공하는 외부 출처 (청구항 3의 "법령원 식별자")
model LawSource {
  id        String   @id @default(uuid())
  code      String   @unique          /// "law.go.kr"
  name      String                    /// "국가법령정보센터 DRF"
  baseUrl   String
  isActive  Boolean  @default(true)
  laws      Law[]
}

/// 법령 — 테넌트 공용
model Law {
  id             String   @id @default(uuid())
  sourceId       String
  externalId     String                  /// 법제처 MST(법령일련번호)
  lawName        String
  lawNo          String?                 /// 법령번호
  promulgatedDate DateTime? @db.Date     /// 공포일
  effectiveDate  DateTime? @db.Date      /// 법령 시행일
  versionKey     String?                 /// 현재 수신본의 지문. 이 값이 바뀌면 개정이다
  lastCheckedAt  DateTime?               /// 마지막 폴링 시각
  articles       LawArticle[]

  @@unique([sourceId, externalId])
  @@index([lastCheckedAt])               /// 폴링 대상 선정
}

/// 법령조항 — 청구항의 "법령조항 식별자"는 이 레코드의 id
model LawArticle {
  id           String   @id @default(uuid())
  lawId        String
  articleNo    Int                       /// 조
  clauseNo     Int?                      /// 항
  itemNo       Int?                      /// 목
  title        String?
  content      String   @db.Text
  versionKey   String                    /// 내용 지문. 변경 감지의 기준
  effectiveDate DateTime? @db.Date
  links        LawLink[]
  changeEvents LawChangeEvent[]

  @@unique([lawId, articleNo, clauseNo, itemNo])
  @@index([lawId])
}

/// 법령 관계 정보 — 청구항 1 ②, 청구항 3
/// 법령조항 노드와 사내 조문 노드를 잇는 그래프의 간선(edge)이다.
model LawLink {
  id            String   @id @default(uuid())
  tenantId      String                     /// ⚠️ 테넌트 경계. 누락 금지
  lawArticleId  String
  articleId     String                     /// 사내 조문 (Article.id)
  relationType  LawRelationType            /// 관계 유형
  scope         String?                    /// 적용 범위 (예: "정규직에 한함")
  evidenceText  String?  @db.Text          /// 관계의 근거 문구
  confidence    Float?                     /// 신뢰도 0.0~1.0 (자동 추천일 때)
  confirmState  LawLinkState @default(suggested)  /// 사용자 확정 상태
  confirmedBy   String?
  confirmedAt   DateTime?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@unique([tenantId, lawArticleId, articleId])
  @@index([tenantId, articleId])           /// 조문 상세에서 "이 조문이 걸린 법" 보기
  @@index([lawArticleId, confirmState])    /// 영향 분석의 진입 경로
}

enum LawRelationType {
  delegation   /// 위임 — 법이 규정에 위임한 사항
  application  /// 준용
  citation     /// 인용 — 규정이 법 조항을 직접 인용
  obligation   /// 의무 — 법이 정한 의무를 규정이 구체화
  reference    /// 참고
}

enum LawLinkState {
  suggested    /// 자동 추천 (사람이 아직 안 봄)
  confirmed    /// 사용자 확정
  rejected     /// 사용자가 아니라고 판단
}

/// 변경 이벤트 — 청구항 1 ③, 청구항 3
model LawChangeEvent {
  id              String   @id @default(uuid())
  lawArticleId    String
  beforeContent   String?  @db.Text        /// 변경 전 법령조항 본문
  afterContent    String   @db.Text        /// 변경 후 법령조항 본문
  beforeVersionKey String?
  afterVersionKey String
  promulgatedDate DateTime? @db.Date       /// 공포일
  lawEffectiveDate DateTime? @db.Date      /// 법령 시행일 (≠ 사내 규정 시행일)
  receivedVia     LawEventChannel          /// 수신경로
  detectedAt      DateTime @default(now())
  candidates      AmendmentCandidate[]

  @@index([lawArticleId, detectedAt])
  @@index([lawEffectiveDate])
}

enum LawEventChannel {
  poll     /// 주기 조회로 발견 (청구항 3)
  manual   /// 담당자가 직접 등록
  webhook  /// 외부 통지 (미사용, 확장 여지)
}

/// 후보 레코드 — 청구항 6
model AmendmentCandidate {
  id              String   @id @default(uuid())
  tenantId        String                    /// ⚠️ 테넌트 경계
  articleId       String                    /// 영향 조문의 조문 식별자
  baseVersionId   String                    /// 제1 조문 — 발행 버전의 식별자
  changeEventId   String
  candidateContent String  @db.Text         /// 제2 조문 — 개정 후보 본문
  rationale       Json                      /// 변경 근거 정보 (아래 4.4)
  diff            Json                      /// 변경 전후 비교 정보
  generationMethod AmendmentMethod          /// 생성 방식 (청구항 4)
  generationMeta  Json?                     /// 규칙·템플릿 id 또는 입력 원천·모델 정보
  confidence      Float?
  reviewState     AmendmentState @default(draft)
  reviewNote      String?  @db.Text         /// 반려 사유
  reviewedBy      String?
  reviewedAt      DateTime?
  resultVersionId String?  @unique          /// 승인 후 만들어진 ArticleVersion
  createdAt       DateTime @default(now())

  @@index([tenantId, reviewState, createdAt])
  @@index([tenantId, articleId])
  @@index([changeEventId])
}

enum AmendmentMethod {
  rule   /// 제1 생성 방식 — 개정 규칙 + 문장 템플릿
  llm    /// 제2 생성 방식 — 언어모델
}

enum AmendmentState {
  draft      /// 작성
  review     /// 검토 요청됨
  approved   /// 승인 → 후속 버전 발행됨
  rejected   /// 반려 (발행 보류)
}
```

> **구현 (2026-10-08, T-106)** — `AmendmentCandidate` 는 위 설계에서 이렇게 달라졌다(마이그레이션 `20261008120000_amendment_candidates`).
> - `confidence` 는 실수가 아니라 **단계**(`high`·`medium`·`low`)다. 비율은 처리 범위일 뿐 정확도가 아니라서, 반영률(`applied/total`)과 판정 이유는 `generationMeta.confidence` 에 따로 둔다.

> - 원천 판은 **연결할 때(근거 문구를 고칠 때) 근거 문구를 담고 있던 판**이다. 그 뒤 초안이 고쳐져도 다시 고르지 않는다(판 본문을 고치는 경로마다 연결을 손보지 않는다) — 대신 화면 알림을 판 번호가 아니라 **근거 문구가 지금 본문에 있는가**로 띄운다. 목록은 서버가 오늘 시행 판 본문으로 `hasEvidence` 를 재고, 개정 후보는 만들 때 기준 본문(발행본이라 바뀌지 않는다)으로 잰 `evidenceInBase` 를 스냅샷에 남긴다. 판 번호로 견주면 개정을 승인할 때마다 문장이 그대로인 연결에도 알림이 뜨고, 원천 초안이 문구 없이 고쳐져 시행되면 알림이 사라진다(T-177 검토).
> - 시행 판을 먼저 고르는 까닭 — 같은 문장이 시행 판과 초안에 모두 있을 때 초안을 원천으로 남기면 초안이 고쳐지거나 지워질 때 원천이 흔들린다.
> - 쓰기(만들기·근거 문구 고치기·자동 추천)는 한 트랜잭션에서 **조문 행과 그 판들을 먼저 잡고**(`holdArticleVersions` — FOR KEY SHARE, 조문 → 판(id 순) → 연결) 잡은 판들로 원천을 고른다. 조문·장·규정 삭제(조문 FOR UPDATE → 판 → 연결)·재파싱 반려(판을 지운 뒤 연결)와 잠금 순서가 같아 교착하지 않는다 — 처음 고친 판(고른 판만 먼저 잡기)은 연결의 FK 확인에서 조문을 기다려 조문 삭제와 교착했다(검토). 판을 지우는 중이면 끝나길 기다렸다가 남은 판들로 고르고(지워질 판을 원천으로 쓰지 않는다), 조문이 그 사이 지워졌으면 404. 자동 추천은 인용 전부를 한 트랜잭션에 한꺼번에(법령조항 id 순 — 같은 조문에 추천이 겹쳐도 같은 순서로 유일 색인을 잡는다) 넣어 반쪽 저장이 없고, 그 사이 같은 조합이 생겼으면 그것만 건너뛴다. 조문·판 두 잠금 문장은 기다림 한도 하나(3초)를 나눠 쓴다. 고치기는 근거 문구를 보낼 때 문구와 원천을 함께 쓴다(같은 문구면 읽어 둔 원천 — 잡은 판들에 없으면 비움) — 동시에 고쳐도 짝이 어긋나지 않는다. 트랜잭션 제한은 기다림 둘(판 묶음·쓰기)을 견디게 9초. 목록·스냅샷의 원천 요약은 연결의 조문 판일 때만 싣는다(잘못 들어간 행 방어).
> - `evidenceFromBody` — 근거 문구를 본문에서 찾았는가. 원천 판이 그 뒤 지워져도(SetNull) 남아, 본문에서 찾은 근거가 지금 본문에서 사라지면 계속 알린다. 처음부터 본문 밖 문구(메모 인용·직접 쓴 설명)는 늘 "없음"이라 알림이 헛돌므로 재지 않는다(`hasEvidence`·`evidenceInBase` null).
> - 채우기 SQL 은 연결마다 그 조문의 판만 조문 색인으로 읽는다(지금 판도 연결별 하위 질의) — 개발 DB(연결 41·판 71,066)에서 2.7ms.
> - 화면: 연결 목록(규정 상세 "걸린 법", 법령 상세 "영향받는 우리 조문")과 개정 후보 근거가 "출처 vN"(없으면 "출처 버전 없음")을 보이고, 본문에서 찾은 근거 문구가 시행중인 버전(후보는 기준 본문)에 없으면 알린다(원천 판이 지워졌어도). 시행중인 버전이 없으면(초안뿐·폐지) 견줄 본문이 없어 알리지 않는다. "걸린 법"은 조문의 지금 시행 버전이 바뀌면 다시 불러온다. 영향 분석 패널은 기준 본문을 이미 보이므로 넣지 않았다.

### 4.4 `rationale`(변경 근거 정보)의 형태

청구항 3이 내용물을 지정한다 — *관계 유형, 근거 문구, 사용자 확정 상태, 법령조항 노드에서 각 영향 조문까지의 연결 관계*.

```jsonc
{
  "law": { "lawName": "근로기준법", "articleLabel": "제60조제1항", "lawArticleId": "…" },
  "link": {
    "relationType": "delegation",
    "evidenceText": "제60조제1항의 연차휴가 일수를 회사 규정에서 정한다",
    "confirmState": "confirmed",
    "confidence": 0.92
  },
  "path": [                                  // 연결 관계 = 그래프 경로
    { "type": "lawArticle", "id": "…", "label": "근로기준법 제60조제1항" },
    { "type": "article",    "id": "…", "label": "취업규칙 제28조제2항" }
  ],
  "generation": { "method": "rule", "ruleId": "NUM_CHANGE_V1", "templateId": "…" },
  "variables": [ { "key": "ANNUAL_LEAVE_DAYS", "resolvedValue": "15", "validFrom": "2026-01-01" } ]
}
```

> **구현 (T-106)** — 위 모양에 더해 `lawChanges`(법령 변경 부분: 종류 value·term·sentence·insert·delete·reference, 전후 문구, 문맥), `applications`(적용한 규칙·템플릿과 버전, 반영한 법령 변경, 제1 조문·후보 쪽 위치), `unmapped`(반영하지 못한 법령 변경과 이유), `conflicts`(같은 자리에 다른 문구를 낸 규칙 제안), `base`(기준 발행본·기준일)를 싣는다. `link.evidenceVersion`(T-177)은 근거 문구의 원천 판 `{id, versionNum, status, effectiveDate}`, `link.evidenceInBase` 는 근거 문구가 기준 본문에 있는가 — 후보를 만들 때의 값이고, 그 전에 만든 후보에는 없다. `generation`·`variables` 는 `generationMeta` 와 T-109 로 갔다. 비교 정보 `diff` 는 규칙 기록과 **따로 계산한** 실제 차이(`changes[]` 의 문자 구간마다 근거 `rationaleRefs`, 근거 없는 구간 수 `unexplained`)다.

**근거 정보는 화면에 그대로 보여 주기 위한 것이다.** 청구항 6이 *"변경된 부분을 후보 레코드에 대응하는 변경 근거 정보와 함께 표시"* 하라고 한다.
사람이 승인 버튼을 누르려면 **왜 이렇게 고쳤는지**를 같이 봐야 한다. 근거 없이 초안만 내놓으면 검토가 형식이 된다.

/// 변수 값 — 청구항 5·9의 "변수 값, 유효기간, 테넌트 범위"
model VariableValue {
  id         String   @id @default(uuid())

> 겹침을 조용히 허용하면 "어느 값이 적용됐는지 알 수 없는" 상태가 되고, 그건 개정 초안의 신뢰를 통째로 무너뜨린다.

> **구현 (2026-10-09, T-109 ①)** — 위 스케치에서 바꾼 것(사용자 지시로 코덱스 자문):
> - **값**: `tenantId` 필수(범위 = 그 회사, 전역·조직 범위는 미룸), 시작 없음 = 처음부터, 기간 겹침은 저장하되 "검토 필요"이고 그날 맞는 값이 **정확히 하나**일 때만 쓴다("나중에 시작한 값이 이긴다"는 버림). 옛 `defaultValue` 는 `periodConfirmed = false`(기간 미확정)로 옮겨 기간을 정하기 전에는 쓰지 않는다 — "처음부터"와 "모름"은 다르다.
> - **연결(`VariableBinding`)**: 발행 본문은 실제 문구이고 연결이 그 구간을 가리킨다 — 조문·기준 버전·UTF-16 [start, end)·당시 문구·앞뒤 문맥·출현 순번. 본문의 `{{KEY}}` 표식은 입력용이라 **검토 요청 때** 오늘 값으로 바꿔 저장하고 그 자리를 연결로 남긴다(검토자가 실제로 발행될 문구를 본다). 표식이 남은 본문은 어느 경로로도 발행하지 않는다. 승인 때 그 시행일 값이 검토 요청 때와 다르면 승인하지 않는다.
> - **위치 옮기기**: 초안을 고치거나 새 버전을 발행하면 글자 단위 차이로 위치를 옮기고, 옮긴 자리의 문구가 그대로일 때만 확정한다 — 아니면 "다시 이어야 함". 발행 때는 옛 행을 이력으로 두고 새 버전에 새 행을 만들어 `parentId` 로 잇는다(일반 승인·후보 승인·한꺼번에 시행 모두, 같은 트랜잭션).
> - **잠금**: 값 고치기는 변수 행을 잠그고, 승인의 값 재확인은 그 행을 공유 잠금으로 읽는다. 연결 만들기는 조문을 잠가 발행과 줄 세운다.

### 5.2 변경 감지 (청구항 3)

주기 실행은 **API 컨테이너 안의 스케줄러가 아니라 별도 트리거**로 둔다.
현재 배포는 단일 호스트 docker-compose이고 API를 2대로 늘리면 스케줄러가 두 번 돈다. 지금 그걸 막는 장치가 없다.

→ `POST /admin/law-sync/run` (global_admin 전용)을 만들고 **cron이 호출**한다. T-92 백업과 같은 방식이다.
(API 다중화가 확정되면 분산 락을 검토한다. 지금 넣으면 쓰지 않는 코드가 된다.)

감지 절차:

1. `lastCheckedAt`이 오래된 `Law`부터 N건 선택
2. **법령ID 로 지금 판의 MST 를 찾는다** — 법령명 검색(`lawSearch.do`) 결과에서 법령ID 가 같은 것 중 MST 가 가장 큰 판. 저장된 MST 와 같으면 본문을 받지 않고 끝(아래 정정 참고). 다르면 그 MST 로 `lawService.do` 본문 조회
3. 조항별 `versionKey` 계산 → 저장된 값과 비교
4. 다른 조항마다 `LawChangeEvent` 1건 생성 (전후 본문·공포일·법령 시행일·수신경로 `poll`)
5. `LawArticle.content`/`versionKey` 갱신, `Law.lastCheckedAt` 갱신 — **같은 `Law` 행의 MST 를 바꾼다.** 새 MST 로 등록 경로를 타면 별도 법령 행이 생겨 `LawLink` 가 옛 판에 남는다

> **정정 (2026-10-07, T-104 구현 중 발견)**
> - **저장된 MST 로 다시 조회하면 개정을 영원히 못 잡는다.** MST(법령일련번호)는 **판마다 새로 발급**되고 한 MST 의 본문은 바뀌지 않는다. 위 2단계처럼 바뀌지 않는 법령ID 로 지금 판을 찾아야 한다. 법령ID 로 본문을 직접 받는 조회(`lawService.do?ID=`)도 있지만 **응답에 MST 가 없어** 저장 키로 쓸 수 없다 — 검색으로 MST 를 찾고, 제명이 바뀌어 검색에 안 걸리면 그 조회로 지금 이름만 받아 다시 찾는다.
> - **cron 은 HTTP 가 아니라 컨테이너 안 CLI 를 부른다**(`scripts/oracle/law-sync.sh` → `node dist/laws/law-sync.cli.js`). global_admin 토큰은 15분이면 만료돼 cron 이 쥘 수 없고, 관리자 비밀번호를 서버 파일에 두는 것은 더 나쁘다. HTTP 는 플랫폼 관리자의 수동 실행·이력 조회용으로 남겼다.
> - 경로는 `/api/admin/…` 이 아니라 **`/api/platform-admin/law-sync/…`** — `/admin` 컨트롤러는 회사 관리자(`admin` 역할) 전용이다.
> - 같은 법령ID 가 둘 이상 보이면 MST 가 가장 큰 판을 고른다. **공포됐지만 아직 시행 전인 개정**도 잡히며, 이벤트의 `lawEffectiveDate` 로 시행일을 구분한다. ⚠️ **틀린 전제였다(2026-10-14)** — 현행 목록은 현행만 준다. 판을 고르는 일은 5.2-1(판 걷기, T-151)이 한다.

> **`versionKey`는 본문 해시로 만든다.** 법제처가 조항 단위 버전 번호를 주지 않기 때문이다.
> 정규화(공백·제어문자 정리) 후 SHA-256. **정규화 규칙이 바뀌면 전체가 "변경됨"으로 보인다** — 규칙을 바꿀 때는 재계산 마이그레이션을 같이 낸다.

> **실패는 조용히 넘어가면 안 된다.** 법제처 API는 실패해도 HTTP 200에 에러 본문을 준다(기존 `lawgokr.service.ts`가 이미 이걸 처리한다).
> 폴링이 조용히 실패하면 "개정이 없었다"와 구별되지 않는다. 동기화 결과는 `LawSyncRun` 로그로 남기고 실패 시 종료 코드로 알린다.

### 5.2-1 판을 차례로 반영 (도 7 S770, T-151 — PAT-07)

> **실호출(2026-10-14, 근로기준법 법령ID 001872)이 5.2 의 전제를 바꿨다.**
> - 동기화가 쓰던 **현행 목록(`lawSearch target=law`)은 현행만 준다** — 위 정정의 "시행 예정 판도 함께 보인다"는 틀렸다. 그래서 공포됐지만 시행 전인 개정(예: 06-09 공포·12-10 시행 286771)을 **현행이 될 때까지 감지하지 못했다**.
> - **시행일법령 목록(`target=eflaw`)은 연혁·현행·시행예정을 모두 준다.** 같은 판(MST)이 단계 시행일마다 따로 나오고(285279 → 10-08·12-08·2027-01-01), 공포 순서와 시행 순서가 다르다(290781 은 08-04 공포·10-02 시행, 285279 는 04-07 공포·10-08 시행).
> - 판 본문(`lawService target=law MST=`)은 **그 판까지 공포된 개정을 모두 담는다**(시행 전 조문 포함). 그래서 공포 순으로 이웃한 두 판의 차이가 곧 뒤 판의 공포가 바꾼 조다(283457→284443 제43조의6, 285279→286771 제54·60·61·110·114조 — 시스템 지문 기준).
>
> **결정**(설계안 3개를 심사·종합하고 코덱스에 자문 — 사용자 지시)
> - **판 목록**: 시행일법령 목록을 **법령ID(`LID`)로** 공포일 내림차순 100건씩 받아 MST 별로 묶는다(단계 시행일은 모으고, 다른 법령ID 행은 버린다). 이름으로 찾지 않는다 — 제명이 바뀐 판을 놓치고 이름이 겹치는 시행령이 섞인다(검토 지적, 실호출 `LID=001872` → 근로기준법 54행만). 저장 판의 공포일보다 오래된 행이 나온 쪽에서 멈추고(같은 날은 더 받는다), 다음 쪽이 있는지는 행 수가 아니라 전체 건수로 본다. 10쪽을 넘거나, 저장 판 공포일 뒤(같은 날 포함)에 법령ID·MST 가 빈 행이 있거나, 공포일이 없는 판이 있으면 일부 목록으로 판단하지 않고 실패한다(조용히 버리면 그 판의 변경이 다음 판 날짜로 묶이고, 공포일 없는 판이 맨 앞에 서면 옛 판을 다시 반영한다). 기준일(쪽 넘김·빈 행 가르기)은 목록 안 저장 판의 공포일이고, 공포일 없는 행은 시행일이 그보다 **한 해 넘게** 앞일 때만 옛 판으로 보고 넘어간다(보통 공포 ≤ 시행이지만 소급 시행일 수 있어 여유를 두고, 애매하면 멈춘다 — 안전 쪽). 2026-10-14 실데이터(인사·노무 법령 등 19개, 1,244행)에는 공포일·MST·법령ID 가 빈 행이 없었다.
> - **순서·범위**: 공포 순(공포일 → 공포번호 → MST) — MST 번호 순서는 2001년 이전 자료에서 어긋난다. 저장 판 **뒤에 공포된 판 전부**(연혁·현행·시행 예정)를 반영한다(LAW-15 "예정 판은 동기화가 변경 이벤트로", T-104 의 원래 의도). 저장 판을 목록에서 못 찾으면 공포일로 자리를 짐작하지 않고 실패한다.
> - **판 하나 = 트랜잭션 하나**: 법령 행이 직전 판을 가리킬 때만 바꾸며 잠그고(비교·교체) → 잠근 뒤 이전 표기 규칙을 읽고 → 판 기록(`law_versions`)을 넣고 → 서지를 고치고 → 조항을 갱신하며 생긴 이벤트가 그 판을 가리킨다. 셋이 함께 커밋되지 않으면 판은 확정되지 않는다(특허 "이벤트 저장이 끝나야 변경 후 버전으로 확정").
> - **중복 방지**: 비교·교체 + (법령, MST) 유일 + (판, 조항) 유일. 판 행이 법령·직전 판·이 판을 정하므로 (판, 조항) 유일이 특허의 "법령·조항·변경 전후 버전 조합으로 같은 변경 판단"을 DB 에서 한다. 같은 판 재등록 이벤트와 옛 이벤트는 판 칸이 null 이라 걸리지 않는다.
> - **실패·이어 가기**: 중간에 실패하면 앞 판까지 확정하고 멈춘다 — **실패한 판을 건너뛰지 않는다**(건너뛰면 그 판의 변경이 다음 판 이벤트에 섞인다). 다음 실행이 목록을 다시 받아 저장 판 다음부터 잇는다. 다른 경로가 먼저 판을 바꿨으면(경합) 실패로 세지 않는다. 폐지 판(제개정구분 폐지·타법폐지·일괄폐지 — 폐지제정은 본문이 있어 아니다)에서는 멈추고 추적 해제를 검토하라고 남긴다.
> - **상한**: 법령당 한 번에 5판(`LAW_SYNC_MAX_VERSIONS`), 실행 전체 20분(`LAW_SYNC_BUDGET_MS`, 30분 "중단됨" 판정보다 짧게). 판이 남으면 오류만 지우고 확인 시각은 그대로 둬 다음 실행 앞에 세운다. 판 반영은 확인 시각을 찍지 않고, 법령의 판을 다 걷은 끝에서 한 번 찍는다(일부만 반영한 법령이 "확인 성공"처럼 보이지 않게).
> - **이벤트 날짜**: 공포일·법령 시행일은 그 판의 값(본문 기본정보) — 중간 판의 변경이 마지막 판의 날짜로 묶이지 않는다. 계획용 날짜 규칙은 T-144 그대로이고, 판 기록에 단계 시행일을 모두 남겨 둔다. 기본정보.시행일자가 판마다 가장 이른 단계(285279)이기도, 가장 늦은 단계(286771 → 2027-06-10, 일부는 2026-12-10)이기도 한 문제는 **D-17**(사람 결정).
> - **후보·알림은 그대로**: 판별 이벤트마다 회사·조문별 후보가 생긴다. 판마다 커밋이 따로라 앞 판 이벤트가 먼저 생기고 후보도 그 순서다. 같은 사내 조문에 판별 후보가 둘이면 한쪽 승인 뒤 다른 쪽은 지금처럼 409 로 막힌다(조용히 덮어쓰지 않는다) — 정리는 **D-18** ③.
> - **등록**: 등록한 판을 기준판(`kind=baseline`)으로 남긴다. 이미 등록된 법령은 마이그레이션이 지금 판을 기준판으로 옮겨 적었고, 순서 키·단계 시행일은 첫 동기화가 채운다. **같은 법령ID 를 이미 다른 판으로 추적 중이면 새 행을 만들지 않고 그 법령을 돌려준다**(`alreadyTracked`) — 동기화가 법령 행을 시행 예정 판으로 옮긴 뒤 현행 판을 등록하면 같은 법령의 둘째 행이 생기고, 그 행의 동기화는 첫째 행이 가진 판에서 막혔다(검토 H1). 등록은 법령 행을 잠가 판 반영과 차례로 서고, 아직 행이 없는 법령의 첫 등록끼리는 법령ID 열쇠로 줄 선다(`common/row-locks`, 두 기다림이 30초 한도 하나를 나눠 쓴다). 응답에 법령ID 가 없으면 같은 판 다시 등록만 받고 새 행은 만들지 않는다(502) — 만들면 동기화가 판 목록을 찾지 못하는 둘째 행이 된다. 법령ID 없이 등록된 옛 행은 동기화하지 않는다 — 저장 판 본문에서 짐작으로 채우면 같은 법령의 옛 중복이 있을 때 채운 행이 다른 행의 판에 걸려 멈추고 등록이 그 행을 돌려받는다(검토 4~6차에서 막을 길을 거듭 찾다 거둠). 운영 반영 전 점검(런북 7-5)과 T-154 정리로 다룬다. 같은 판 다시 등록은 본문의 법령ID 를 채운다. MST·법령ID 로 찾은 행이 둘 이상이면(같은 법령의 옛 중복) 어느 행이 판을 따라가는지 짐작하지 않고 409 로 거절한다 — 뒤처진 행은 앞선 행의 판에 걸려 멈춰 있기 쉽고 거기 건 새 연결은 개정을 받지 못한다(검토 6~9차에서 고를 규칙을 거듭 찾다 거둠). 법령ID 없는 행·옛 중복은 운영 반영 전 점검 SQL(`scripts/oracle/sql/t151-law-id-check.sql`, 런북 7-5)로 찾는다.
> - **점검**: CLI `--plan`(DB 에 쓰지 않음 — 법제처 응답 캐시만)으로 법령별 반영할 판을 미리 본다 — 운영 첫 반영 전에 쓴다(런북 7-5). `--law <id>` 로 한 법령만 돈다.
>
> **뺀 것·넘긴 것**: 이벤트·후보 화면의 판 표기("법률 제N호")와 현행/예정 구분 화면 → T-150 ②. 판 하나당 회사별 알림 1건 → T-159(`law_version_id` 가 묶음 열쇠). 같은 조문의 판별 후보 묶기·대체 → D-18 ③·T-169. 표기만 달라진 판 → T-145(`law_versions.version_key` 가 출발점). 같은 법령ID 의 다른 판 등록은 위 '등록'처럼 기존 법령을 돌려준다 — 이미 쌓인 중복 행 정리와 회사 경계(해제·감사)는 T-154.

resolveImpact(changeEvent, asOfDate) → ImpactedArticle[]
  · LawLink where lawArticleId ∈ {event.lawArticleId, 같은 법령의 상위 조항(조·항)}   ← T-148
                  and confirmState = confirmed       ← rejected·suggested 제외
  · 같은 조문이 여러 단계에 걸려 있으면 바뀐 조항에 가장 가까운 연결 하나 (T-148)

```

> **구현 (2026-10-07, T-105)** — `LawChangesService.impact()` / `GET /api/law-changes/:id/impact`.
> - **asOfDate 를 정하는 규칙**(설계에 없던 부분): 생략하면 **법령 시행일과 오늘 중 늦은 날**. 시행 전 개정이면 그날 시행될 우리 본문(미리 승인해 둔 개정본 포함)이 기준이고, 이미 시행된 개정을 늦게 봤다면 지금 본문이 기준이다 — 시행일 시점의 옛 본문으로 초안을 만들면 그 사이 회사가 이미 고친 내용을 되돌리는 초안이 나온다.
> - "없으면 건너뛴다"를 **응답에서는 건너뛰지 않는다** — `baseVersion: null`(`not_in_force`)로 돌려준다. 조용히 빠지면 화면에서 "영향 없음"으로 읽힌다. 후보 생성(T-106)이 이 항목을 건너뛴다.
> - 제1 조문 선택은 규정 시점 조회와 **같은 규칙**을 공용 함수(`common/as-of.ts`)로 쓴다. 고른 버전의 폐지 시행일이 기준일 이하면 "폐지됨"(`repealed`, 폐지일과 함께)으로 보고 옛 버전으로 되돌아가지 않는다 — 목록에는 남기고 후보는 만들지 않는다(T-126).
> - 법령에서 조문이 통째로 사라진 이벤트(`lawArticleId` 가 null)는 거기 걸린 `LawLink` 도 함께 지워져 영향을 찾을 수 없다 — 사유(`unresolvable`)를 실어 보낸다. 법제처는 삭제 조문도 "삭제 <날짜>" 본문으로 남겨 주므로 보통은 `modified` 로 잡혀 연결이 유지되고, 이 경우는 전부개정 같은 구조 변경에서만 생긴다.

> **구현 (2026-10-14, T-148) — 상위 조항에 건 연결도 영향으로.** 처음 정의(`lawArticleId = event.lawArticleId`)로는 가장 흔한 연결이 실제 개정을 받지 못했다. 인용 자동 찾기는 '제60조'를 조 머리 행(`60//`)에 잇는데, 항이 여럿인 조의 머리 행은 본문이 비어 있어 항 개정 이벤트가 항(`60/1/`)에만 생기기 때문이다(실행 확인).
> - 범위는 바뀐 조항과 **같은 법령의 상위 조항(호 → 항 → 조)** 이다. 아래로는 넓히지 않는다 — 항에 건 연결은 조 머리 행의 변경과 무관하다. 범위 계산은 `laws/law-node-key.ts`(순수 함수)와 `law-changes/law-link-reach.ts`(바뀐 조항 → 닿는 법령조항 id, 회사 찾기·거르기·개수)에 두고 영향 조회·자동 생성의 회사 찾기·변경 목록(거르기·개수)·추천 수가 모두 그것을 쓴다. 회사 경계 조건은 `law-links/our-links.ts` 하나다.
> - 같은 조문이 조·항에 둘 다 걸려 있으면 바뀐 조항에 가장 가까운 연결 하나를 쓴다. 개수는 연결 수가 아니라 조문 수다.
> - 상위 조항으로 찾은 후보에는 `parent_link` 표시를 붙이고 신뢰도를 '보통'까지로 둔다 — 바뀐 항·호가 이 조문에 해당하는지 사람이 본다. 근거 경로(`rationale.path`)에는 바뀐 조항과 연결이 걸린 조항을 둘 다 남긴다.
> - 회사 경계: 조문을 먼저 확인하지 않고 연결을 찾는 조회는 모두 연결의 회사와 조문의 실제 소속을 함께 건다 — 조건 함수 `law-links/our-links.ts`(`ourLinks`) 하나를 영향 조회·자동 생성의 회사 찾기·변경 목록(거르기·개수)·추천 수·법령조항별 연결 목록·연결 수정·삭제가 쓴다(T-148 전에 조문 소속까지 보던 것은 영향 조회 하나뿐이었다). 잘못 들어간 행은 그 회사에 "없는" 연결이라 수정·삭제도 404 다. 예외 둘 — 추적 해제 차단(`laws.service.ts`)은 일부러 회사와 무관하게 연결이 하나라도 있으면 막는다(회사 조건을 걸면 다른 회사의 연결이 cascade 로 지워진다). 자동 생성의 회사 찾기는 회사 조건 없이 후보 회사를 뽑은 뒤 회사마다 `ourLinks` 로 다시 본다.
> - 자동 생성끼리는 (회사, 변경, 조문)마다 한 번이다 — 다시 처리할 때 이미 후보가 있는 조문은 상태와 상관없이 건너뛴다. 사람이 누르는 '개정 후보 만들기'·'다시 만들기'는 그대로다.
> - 이미 처리한 시행 전 이벤트를 다시 돌리지 않는다. 처리 표시를 지우는 일괄 재처리는 기능 도입 전 이벤트(T-106 이 일부러 뺀 것)와 직접 연결 조문까지 되살려 알림이 쏟아진다(적대적 검토로 확인). 새로 닿은 조문은 T-149 의 '나중에 확정한 연결' 경로가 한 번에 처리하고, 그 전에는 법령 화면의 '개정 후보 만들기'로 만든다.
> - 알려진 한계: 한 개정이 한 조의 항 여러 개를 바꾸면 조 단위 연결 하나에 후보와 알림이 항마다 생긴다(T-169·T-159).

**`suggested`(자동 추천 상태)는 후보를 만들지 않는다.** 사람이 확정하지 않은 관계로 초안을 만들면,
틀린 연결이 그럴듯한 개정안을 만들어 낸다. 추천 관계는 화면에서 "확인해 주세요"로만 뜬다.

후보 생성은 청구항 4가 두 방식을 허용한다. **규칙 기반(제1 방식)부터 만든다.**

| | 제1 방식 (rule) | 제2 방식 (llm) |
|---|---|---|
| 방법 | 법령 전후 diff → 개정 규칙 매칭 → 문장 템플릿 반영 | 전후 법령·제1 조문·근거 문구를 입력으로 언어모델 호출 |
| 잘하는 것 | 숫자·기간·명칭 치환 (예: "15일" → "16일") | 문장 구조가 바뀌는 개정 |
| 못하는 것 | 규칙에 없는 형태 | 검증 불가능한 문장을 지어낼 수 있음 |
| 저장 | `generationMeta.ruleId`, `templateId` | `generationMeta.model`, `inputSources` |
| 순서 | **먼저** | 나중 |

> 규칙 기반을 먼저 하는 이유: **규칙은 왜 그렇게 고쳤는지 설명할 수 있다.**
> LLM 초안은 근거를 만들어 내기 어렵고, 근거 없는 초안은 청구항 6이 요구하는 "근거와 함께 표시"를 못 한다.
> 규칙이 먼저 자리를 잡으면 LLM 출력도 같은 근거 형식에 맞출 수 있다.

> **구현 (2026-10-08, T-106)** — `amendments/amendment-rules.ts`(규칙 엔진, DB 없는 순수 함수)·`amendment-text.ts`(법령 전후 비교)·`amendment-diff.ts`(실제 차이).
> - **법령 전후 비교**는 개정 연혁 표기(`<개정 …>`·`[본조신설 …]`)를 먼저 뗀다 — 표기만 바뀐 개정에 후보를 만들지 않는다. 바뀐 곳을 기준값(숫자+단위, "100분의 50" 같은 분수, "5천만원"), 용어(조사를 뗀 낱말 — 받침 때문에 짝이 바뀐 조사도 뗀다), 문장 변경, 추가, 삭제, 조문 번호 참조로 나눈다.
> - **규칙 3개**: 기준값 변경·용어 변경(템플릿 `INLINE_REPLACE` — 우리 문장 구조는 그대로 두고 대응 문구 자리에만), 인용 문장 교체(`SENTENCE_REPLACE` — 우리 조문이 법 문장을 그대로 옮겨 적었을 때, 완결 문장끼리의 1:1 대체만). 용어는 새 용어의 받침에 맞춰 우리 조문의 조사를 고친다("사업주는"→"사용인은").
> - **설계에 없던 결정**(사용자 지시로 코덱스 자문): 같은 문구가 여러 곳이면 연결의 근거 문구가 가리키는 문장으로 좁히고, 그래도 하나가 아니면 고치지 않는다 / 용어 뒤가 조사가 아니면(합성어) 고치지 않는다 / 참고 관계·적용 범위가 적힌 연결은 자동으로 고치지 않는다 / 법 문장의 추가·삭제와 "삭제 <날짜>" 는 본문을 건드리지 않고 '반영하지 못한 변경'으로 남긴다 / 규칙끼리 같은 자리에 다른 문구를 내면 그 자리는 고치지 않고 제안을 모두 남긴다 / **하나도 반영하지 못해도 후보는 만든다**(본문은 제1 조문 그대로, `manual_draft_required`) — 이벤트→검토→후속 버전의 추적을 유지하려고. 승인(T-108)은 본문이 바뀌어야 하고, 개정이 필요 없으면 반려로 닫는다.
> - **생성 시점**: 법령 동기화가 끝날 때 처리하지 않은 이벤트를 회사별로 자동 생성(회사별 실패 격리, 실패한 이벤트는 다음 실행에서 재처리, 새 후보가 있으면 관리자·편집자에게 알림 한 건) + 법령 화면의 "개정 후보 만들기"(연결을 나중에 확정했거나 시행일을 보정한 뒤). 기능 도입 전 이벤트는 마이그레이션이 처리 완료로 표시했다.
> - 제1 조문이 없으면 후보를 만들지 않고 이유를 가른다 — `effective_date_missing`(T-123 이전에 가져와 시행일이 없는 시행본, 임의 날짜로 기준 본문을 만들지 않는다) / `not_in_force`.

   · 지금 문구와 같으면 그대로 / 다르면 넣기 제안 / 값 없음·기간 겹침·기간 미확정·문구 불일치면 보류
3. 넣기 제안을 법령 규칙의 고침과 한 번에 맞춘다 — 같은 자리면 원문을 두고 양쪽 제안(충돌)
4. 앞에서부터 이어 붙인다(겹치지 않는 구간만 남으므로 위치가 밀리지 않는다)
```

### 5.4 승인 (청구항 1 ⑦, 청구항 6)

**한 트랜잭션**이다. 중간에 끊기면 "후보는 승인됐는데 버전이 없는" 상태가 된다.

```
approve(candidateId, 사내규정시행일):
  · 권한 확인 — admin 또는 editor (청구항 6: "역할을 이용하여 승인 권한을 확인")
  · candidate.tenantId === 요청자 tenantId 확인        ⚠️
  · ArticleVersion 생성
      articleId       = candidate.articleId          ← 조문 식별자 유지. 발명의 핵심
      versionNum      = 직전 + 1
      content         = candidate.candidateContent
      status          = published
      effectiveDate   = 입력받은 사내 규정 시행일
      publishedAt     = now()
      changeEventId   = candidate.changeEventId
      sourceCandidateId = candidate.id
  · 직전 published 버전 → archived
  · candidate.reviewState = approved, resultVersionId 연결
  · AuditLog 기록 — 청구항 6이 지정한 5개를 한 줄에 묶는다:
      발행 버전 본문 · 변경 이벤트 · 개정 후보 · 비교 정보 · 승인자
  · 알림 발송 (기존 UserNotification 재사용)
```

반려는 `reviewState = rejected` + `reviewNote` 저장, 버전은 만들지 않는다.

> **구현 (2026-10-09, T-108)** — `AmendmentsService.approve()`·`reject()`. 설계와 달라진 점(사용자 지시로 코덱스 자문):
> - 권한은 **관리자만**(일반 조문 승인 `versions/:id/approve` 와 같다). 검토를 요청한 사람이 스스로 승인하는 것은 막지 않는다(관리자 한 명인 회사도 끝낼 수 있게) — 요청자·승인자는 각각 기록된다. 규정별 승인 권한(PAT-19)은 대표 결정 대기.
> - 사내 규정 시행일은 기본값 없이 필수, **소급하지 않는다**(오늘 이후). 법령 시행일보다 이르면 이유 필수.
> - 검토를 요청한 **그 판**의 바뀌지 않는 기록(`AmendmentRevision`)을 그대로 발행한다. 화면이 본 판·잠금 버전이 다르면 409.
> - (T-109 ②) 변수 값도 다시 확인한다 — 승인하는 시행일에 다시 골라 후보가 넣은 값과 다르면 `variable_changed` 409(변수 공유 잠금). 같은 값 행이어도 문구가 다르면 다르다 — 값은 제자리에서 고쳐진다(T-139, 후보 지문 `vf2` 에도 문구). 발행 때 값을 넣은 자리의 연결은 새 값으로 잇는다.
> - 트랜잭션 안에서 **조문 행을 잠그고**(`SELECT … FOR UPDATE` — 일반 승인도 같은 잠금) 다시 확인한다: 시행일 미기록 이력 / 그 시행일의 시점 조회 결과 = 기준 본문 / 그보다 늦은 시행본 없음 / 발행 이력 지문 그대로. 어긋나면 원인(`undated_history`·`repealed`(T-126)·`base_mismatch`·`later_version`·`history_changed`)을 담아 409, 화면은 그 시행일 기준으로 "다시 만들기"를 권한다.
> - 버전 번호는 그 조문의 가장 큰 번호 + 1(초안 포함). 옛 시행본은 바로 내려간 상태(archived — 폐지 시행일 없음) — 시점 조회가 시행일로 가른다(스케줄러 없음).
> - 같은 승인을 다시 보내면(응답 유실) 기존 결과를 돌려주고 다른 시행일·사유면 409. 감사 `amendment.approve` 한 건에 5요소 + 개정 당시 근거(연결 스냅샷·규칙 세트), 알림은 같은 트랜잭션.
> - **알려진 한계**(후속 과제로 올림): ~~"폐지"한 조문도 폐지 상태(archived)라 시점 조회에서 되살아난다(T-126)~~ → **해결(T-126, 10/9)** — 폐지 시행일을 남기고 시점 조회·영향 분석·후보가 함께 뺀다(5.5) / 규정의 "현재" 화면은 시점 조회가 아니라 시행본을 그대로 보여 줘서, 미래 시행일로 승인한 본문이 시행일 전부터 보인다(**T-127**) / (조문, 버전 번호) 유니크 제약은 운영 데이터의 중복을 먼저 확인해야 한다(**T-128**).

### 5.5 날짜 3종 (청구항 7)

| 날짜 | 어디에 | 의미 |
|---|---|---|
| 법령 시행일 | `LawChangeEvent.lawEffectiveDate` | 바뀐 법이 효력을 갖는 날 |
| 발행일 | `ArticleVersion.publishedAt` | 사내에서 개정을 확정·공표한 날 |
| 사내 규정 시행일 | `ArticleVersion.effectiveDate` | 개정된 사내 규정이 효력을 갖는 날 |

셋은 대개 다르다. 법이 2027-01-01 시행인데 사내 규정은 2026-12-15에 발행해 2027-01-01부터 시행하는 식이다.

**시점 조회(as-of)의 기준은 `effectiveDate`(사내 규정 시행일) 하나다.** 이건 이미 그렇게 되어 있다.

> **폐지 시행일(T-126)** — 폐지는 `ArticleVersion.repealedOn` 을 남긴다. 시점 조회는 지금처럼 기준일 이하 마지막 시행분을 고른 뒤, 그 버전의 폐지 시행일이 기준일 이하면 조문을 "폐지"로 본다(`asOfState`) — 옛 버전으로 되돌아가지 않는다. 폐지일을 조회 조건(`where`)에 넣으면 새 버전에 밀려 내려간 옛 버전이 대신 잡혀 폐지한 조문이 되살아난다. 폐지 뒤 다시 시행한 버전은 시행일이 폐지일 이후라 자연히 골라진다(같은 날이면 나중 버전이 이긴다). 폐지 시행일은 오늘(한국 날짜)로 고정한다 — 미래 폐지는 "현재" 화면이 시행 예정을 가르게 된 뒤(T-127). 이 판정을 규정 시점 조회·신구 대비·영향 분석의 제1 조문·후보의 지금 기준 본문·승인 때 기준본 확인이 함께 쓴다. 발행 이력 지문에는 폐지 시행일이 있을 때만 붙는다 — 폐지가 없는 조문의 지문은 T-108 때와 같다.
> **"오늘"은 한국 날짜다(T-126)** — 서버(UTC)를 따르면 한국 시간 0~9시에 하루 이르다. 폐지 시행일·승인 기본 시행일·소급 검사·영향 분석 기준일이 같은 "오늘"을 쓴다(`todayDateOnly`, 화면은 `serviceToday`).
`publishedAt`을 기준으로 바꾸면 "발행은 했지만 아직 시행 전인 개정"이 조회 결과에 섞여 들어간다.

> **구현(T-108·T-111, 사용자 지시로 코덱스 자문)**
> - **기록**: 발행일은 다섯 발행 경로(일반 승인·한꺼번에 시행·가져오기 확정·개정 후보 승인·재파싱 묶음 승인)와 JSON 일괄 등록이 발행하는 순간에 적는다(T-108·T-110). 법령 시행일은 후보 승인 버전의 `changeEventId` 로 이어진 변경 이벤트에서 읽는다 — 버전에 옮겨 적지 않는다. 후보가 이벤트를 Restrict 로 붙잡고 법령 추적 해제도 후보가 있으면 막혀서, 버전이 있는 동안 연결이 사라지지 않는다. 연결이 없는 버전에 그 법령의 최신 시행일을 대신 보이지 않는다.
> - **옛 발행일 보정**(마이그레이션 `20261010010000_published_at_backfill`): 발행 이력(시행본·이전 버전)이고 발행일이 비었으며 승인 시각이 있는 것만 승인 시각으로 채우고 `publishedAtFromApproval` 을 남긴다 — 승인 시각은 처음부터 모든 발행 경로가 발행하는 그 순간에 적어 왔다. 감사 기록은 트랜잭션 뒤에 남거나 묶음 단위라 대신 쓰지 않았다. 승인 시각도 없는 발행 이력(관리자 JSON 일괄 등록 등)은 근거가 없어 비워 둔다 — 생성일·시행일로 메우지 않고 화면은 "발행 기록 없음". 두 시각이 같다는 것만으로는 보정 여부를 가를 수 없어 표시를 따로 둔다.
> - **보이기**: 버전 카드(분절 보기) 머리 아래 한 줄에 사내 시행일(시행본이고 오늘 뒤면 "시행 예정") → 발행일시(한국 시각, 보정이면 "승인 기록으로 보정") → 법령 시행일(법령명·조항, 후보 승인 버전만). 사내 시행일이 법령 시행일보다 이르면 "법령보다 조기 시행" — 오류가 아니라 승인 때 사유를 받은 결정이라 후보 화면의 승인 사유로 잇는다. 같은 표기를 연혁 탭(조문별 시행본), 개정 이력 타임라인, 개정 후보의 승인 결과에 쓰고, 승인 전 후보는 "예정 사내 시행일 · 미발행". 날짜 표시는 "현재" 화면의 의미를 바꾸지 않는다 — 미래 시행본을 현재 본문에서 가르는 일은 T-127.

### 5.5-1 조항별 시행일 구분 (청구항 7·도 7 S760, T-144)

> **실제 법제처 응답 조사(2026-10-12, 본문 조회 법령 38건·조 5,062개)가 설계를 바꿨다.**
> - 구조화된 `조문시행일자` 는 **언제나 그 판의 시행일자와 같았다**(다른 조 0개). 그대로 옮기면 지금 데이터에선 아무것도 달라지지 않는다.
> - 조마다 다른 시행일은 **글자 표기 `[시행일: 2027.1.1]`** 로만 온다 — 조문참고자료 5건·조문내용 1건, 조 6개(0.1%). 조의 **일부**(`제1항 중 … 개정부분`)만 늦게 시행되는 경우가 많고(소득세법 제164조의3), 법령 시행일보다 **앞서는** 조도 있다(중대재해 처벌 등에 관한 법률 제16조, 공포한 날부터).
>
> **결정(사용자 지시로 코덱스 자문 — 날짜별로 이벤트를 쪼개는 안은 과해서 버렸다)**
> - 조 행(`LawArticle.effectiveNotes`)에 `{date, scope, scopeText, source, raw}` 배열을 저장하고(항·호 행은 상위 조의 것), **본문이 바뀐 변경 이벤트**에는 그때의 앞뒤 표기와 판(MST)을 `LawChangeEvent.effectiveInfo` 로 스냅샷한다 — 조문이 이후 판에서 바뀌거나 사라져도 "그때 어땠나"가 남는다. 본문 지문(versionKey)에는 영향이 없다.
> - **범위**: 표기 뒤 문구가 범위를 밝힌 문구(`제N조…`·`[별표 N]…` 로 시작)일 때만 범위로 남기고, 그중 항·호·목(가목~하목)이나 "개정부분"을 가리키며 **대상 조가 하나일 때만** `partial`("일부는 ○일 시행")이다. 대상을 셀 때 괄호 안 한정 문구(겹친 괄호 포함)·따옴표 안의 바뀌는 문구·다른 법률의 조(「…」 제N조)·법령 번호(법률 제N호)는 뺀다. 그 밖에는 `unknown`("범위 확인 필요") — 조 번호로만 끝나거나, 여러 조를 늘어놓았거나, 조문 본문이 이어지는(`…다.`) 경우다. 조 전체라고도, 일부라고도 단정하지 않는 쪽으로 기운다. 항·호·목 본문의 표기도 읽고(조사한 응답에는 없었다), 뒤에 범위 문구가 없으면 그 자리(`제2항제1호의2` — 법령 조항 행 라벨과 같은 꼴)를 범위로 남긴다 — 그 항·호의 일부다. 구조화 조문시행일자가 판 시행일과 다르면(지금은 없다) 그것도 한 건으로 남긴다.
> - **계획용 날짜는 바꾸지 않는다.** 영향 분석 기준일·개정 후보의 예정 시행일·변수 값 고르는 날은 판 시행일 그대로다 — 범위를 잘못 읽어 조 전체의 기준일을 옮기면 후보·변수 선택까지 틀어진다. 표기는 **원문 확인을 돕는 안내**(변경 목록 배지·영향 분석 패널·후보 상세)다. 판 시행일보다 앞서는 조도 후보 대상에서 빼지 않는다(사내 규정에 아직 반영되지 않았을 수 있다).
> - **이미 등록된 법령·읽기 규칙 변경**: 주기 동기화는 같은 판이면 본문을 다시 받지 않는다. 그래서 법령 행에 **표기 읽기 규칙의 판**(`Law.effectiveNotesVersion`, 코드의 `EFFECTIVE_NOTES_VERSION`)을 두고, 이 값이 지금과 다르면(T-144 이전 등록은 null) 같은 판이어도 한 번 읽어 **달라진 조항만** 고쳐 쓴다(같은 값끼리 묶어 쓰기 몇 번). 규칙을 고치면 판을 올리면 된다 — "읽었지만 없음([])"으로 저장된 조항도 다시 읽힌다. 판 올리기를 잊지 않게 대표 입력의 읽기 결과를 판 번호와 함께 고정한 시험(`effectiveNotesRules`)을 두었다 — 결과가 바뀌면 판을 올리라는 문구로 실패한다. 매핑 결과 캐시 키에도 이 판을 넣었다(`lawgokr:law:v2:n1:<MST>`) — 하루짜리 캐시에 남은 옛 규칙의 결과를 읽어 새 판 번호로 찍지 않게. **이벤트는 만들지 않는다**(우리가 다시 읽은 것이지 법이 바뀐 것이 아니다). 등록·새 판 저장과 겹치면: 맞추기는 법령 행의 판을 "같은 MST 이고 아직 옛 판"일 때만 올려 행 잠금을 먼저 잡고, 저장 쪽도 법령 행을 먼저 고치므로 차례로 선다(먼저 끝난 쪽이 지금 규칙으로 썼으면 다른 쪽은 손을 뗀다). 옛 이벤트의 표기는 채우지 않는다("그때 수집 안 함"으로 남는다).
> - **화면**: 변경 목록 배지, 영향 분석 패널·후보 상세의 안내 상자, 법령 상세의 조항 목록(표기가 있는 조 행에 짧은 표시, 고르면 안내 상자). 이번 개정으로 표기가 바뀌거나 없어지면 변경 전 표기도 보인다("이번 개정으로 이 조의 별도 시행일 표기가 없어졌습니다", 목록 배지는 `시행일 표기 없어짐`). 사라진 조의 이벤트는 사라지기 전 표기를 "이번 개정으로 사라진 조에 있던 별도 시행일 표기입니다"로 보인다(`articleGone`). 견주는 것은 날짜와 범위 문구뿐이고, 이벤트 스냅샷의 앞뒤를 **같은 읽기 규칙**으로 읽었을 때만 견준다(`rules`·`beforeRules`) — 규칙이 바뀐 것을 "이번 개정으로 바뀌었다"고 말하지 않는다. 사내 규정 쪽(법제처 가져오기 세션 트리)에는 이 칸을 싣지 않는다.
> - **한계**: ① 본문은 그대로이고 표기만 달라진 판(시행일 연기 등)은 이벤트로 남기지 않는다(후속 T-145) — 판 시행일만 바뀐 경우도 지금 이벤트가 없는 것과 같은 경계다. 조 행의 "지금" 표기는 갱신된다. ② 날짜가 아닌 표기(`[시행일: 대통령령으로 정하는 날]`)는 읽지 않는다(조사한 응답에 없었다). ③ 법령ID 가 없거나 현행 목록에서 사라진(폐지·제명 변경) 법령은 동기화가 판을 확인하기 전에 실패로 끝나 표기를 맞추지 않는다 — 그 실패는 이미 `lastCheckError` 로 보인다.

### 5.6 재파싱 시 조문 동일성 (청구항 2)

규정 문서를 다시 가져올 때 **조문 식별자를 유지**해야 한다. 안 그러면 `LawLink`와 버전 이력이 통째로 끊긴다.

판정 키 2개:
- **계층 키** = `(policyId, chapter.number, section.number, articleNo, clauseNo, itemNo)`
- **지문** = 정규화한 본문의 SHA-256

| 계층 | 지문 | 판정 |
|:--:|:--:|---|
| 일치 | 일치 | **같은 조문, 변경 없음** |
| 일치 | 불일치 | **같은 조문, 내용 개정** → 새 버전 |
| 불일치 | 일치 | **조문 이동** (번호가 바뀜) → 같은 `Article.id` 유지 |
| 불일치 | 불일치 | **신규 조문** |

> 세 번째 줄이 이 설계의 값어치다. 법령 개정으로 조 번호가 밀리는 일이 흔한데,
> 번호만 보면 "제5조 삭제 + 제6조 신설"로 보이고 그 순간 제5조에 걸어 둔 법령 연결이 사라진다.

**충돌 처리**: 지문이 같은 후보가 2개 이상이면 계층 거리가 가까운 쪽을 고르고, 그래도 동률이면 **자동 판정하지 않고 사용자에게 묻는다.**
가져오기 미리보기(T-12) 화면에 "이 조문이 기존 제N조와 같은 조문입니까?"를 띄운다.

> **구현(2026-10-09, T-110 ① — 판정·검토, 사용자 지시로 코덱스 자문)**
> - 입구: 가져오기 화면 3단계를 "새 규정으로 등록 / **기존 규정에 다시 가져오기**"로 나누고, 규정 상세의 `원문 다시 가져오기`가 대상 규정을 골라 둔 채 연다.
>   대상은 파일 이름이 아니라 사람이 고른 규정이다(규정 식별 정보). 문서 제목과 같은 규정이 있으면 미리 골라 둔다.
> - 비교 결과는 **재파싱 검토**(`ReparseReview`·`ReparseReviewItem`)로 남는다. 규정 데이터는 바꾸지 않는다.
> - **지문은 저장하지 않는다** — `Article.fingerprint` 대신 비교할 때 비교 대상 버전(최근 발행본, 발행 이력이 없으면 최신 작업본) 본문으로 계산한다.
>   정규화 `norm/1`: NFC, 너비 없는 문자 제거, 전각 영숫자·기호 → 반각, 가운뎃점·따옴표·줄표·물결 모양만 맞춤, 공백류를 한 칸으로.
>   **NFKC 는 쓰지 않는다**("10⁴"가 "104"가 된다). PDF 줄이 단어 중간에서 나뉜 "관리한 다"는 띄어쓰기를 뺀 비교(숫자 사이 공백은 남김 — "1 2" ≠ "12")로
>   후보만 찾는다. 빈 본문은 지문이 없다(제목으로 대신하지 않는다).
> - 판정 순서(앞 단계에서 맺은 짝은 뒤에서 다시 보지 않는다. 지문의 "유일"은 남은 것이 아니라 전체에서 센다):
>   ① 같은 번호(조·가지·항·목, 양쪽에서 하나뿐) + 같은 본문(띄어쓰기만 다름 포함) → 그대로 ② 본문이 양쪽 전체에서 하나뿐 → 옮김
>   ③ 본문 없는 조 머리 행: 먼저 모두 하위 항·목이 따라간 조로, 그다음에 같은 번호의 빈 머리 행으로 ④ 같은 본문이 여럿인 항·목은 대응된 상위 조 안에서
>   ④-2 띄어쓰기를 빼야 같은 본문이 양쪽 전체에서 하나뿐 → 짝(추천 안 함) ⑤ 같은 자리·다른 본문: 먼저 모두 대응된 상위 조 안의 같은 항·목 번호로,
>   그다음에 같은 번호로 → 본문 바뀜 ⑥ 남은 본문에 후보가 있으면 판정 보류(폐지된 조문은 여기서만) ⑦ 새 조문 후보 / 원문에 없음.
>   ③·⑤를 둘로 나눈 까닭: 앞에 끼어든 새 조의 행이 번호만 보고 옮겨 간 조의 행을 먼저 차지하지 않게(단위 시험으로 고정).
> - 추천(결정을 미리 골라 둠): 번호로 맺은 짝·하위 항으로 맺은 머리 행·상위 조로 가른 항은 추천, 본문만으로 맺은 짝은 상위 조·하위 항·앞뒤 조 중 하나가
>   같은 쪽으로 대응될 때만, 띄어쓰기로 맺은 짝은 추천하지 않는다. 후보가 없는 새 조문은 "새 조문"을 골라 둔다. 같은 자리 본문 바뀜·판정 보류는 반드시 사람이.
> - 장·절은 대응된 조문이 가장 많이 온 장·절로 맞추고(같으면 번호가 같은 쪽), 장 번호·제목 변경과 새 장을 장 단위로 묶어 보인다 — 장이 하나 끼어들어도
>   뒤 장의 조문은 "그대로"다. 원문 번호를 그대로 쓰지 못해 `buildCommitPlan` 이 다시 매긴 행은 번호로 잇지 않는다(본문으로만). 부칙·별표는 이번 범위 밖.
> - 결정: 한 기존 조문은 한 항목만(분할·병합은 보류로), 원문에 없는 조문의 폐지는 관리자, 이어진 원문에 없는 조문은 유지·폐지를 따로 정하지 않는다.
>   같은 원문을 다시 비교하면 앞 검토는 지나가고 결정은 같은 항목이면 옮긴다(옮긴 뒤 규칙에 어긋나면 옮기지 않는다). 비교 뒤 규정 상태나 원문 트리가 바뀌면 "다시 비교" 안내.
> - **2단계(T-110 ②) 계획 — 코덱스 자문**: 반영 = 검토 대상 만들기(이동도 승인 전에는 현재 계층을 바꾸지 않는다). 개정·이동·조 제목 변경은 기존 조문의 초안(제안 계층),
>   새 조문은 새 조문 + 초안 v1, 원문에 없음은 "삭제 여부 미결"로 남고 유지로 닫거나 관리자가 폐지(T-126 절차). **버전별 계층 최소안(PAT-04)**: `ArticleVersion.structure` —
>   시행본은 조문 행 값, 새 버전에 밀려 내려가거나 폐지될 때 그때의 계층을 얼리고, 초안은 제안 계층을 가졌다가 승인 때 옮긴다. 시점 조회·신구 대비는 얼린 계층으로 조립.
>   jo-order·번호 직접 수정은 현재 계층의 바로잡기. 재파싱 묶음은 같은 시행일로 함께 검토 요청·승인(전부 되거나 전부 안 됨), Policy → Article 순 잠금 아래 규정 계층 지문을
>   다시 확인하고, 묶음 초안을 단건 승인·한꺼번에 시행으로 우회하지 못하게 막는다.

> **구현(2026-10-09, T-110 ② — 반영·묶음 승인·버전별 계층, 사용자 지시로 코덱스 자문 세 차례)**
> - **반영** = 기존 조문의 묶음 초안(`reparseItemId`, 본문 + 제안 계층 `structure`)만. 새 조문·새 장·절은 행을 만들지 않고 계획(`ReparseReview.plan`)에 둔다 —
>   승인 전 행이 화면·조회에 새지 않고, 묶음이 만든 새 조문에 일반 초안을 붙이는 우회도 생기지 않는다. 버전이 없는 조 머리 행(제목만, 항으로만 이루어진 조)은
>   초안을 만들 본문이 없어 승인 때 행만 옮긴다. 묶음이 아닌 작업본이 남은 조문을 바꾸려 하면 반영하지 않는다(그 항목을 보류로).
> - **장·절 번호·제목 변경**은 장·절 행 하나지만 그 장·절의 모든 조문의 계층이 바뀐다 → 시행 중인 조문마다 계층만 바꾸는 초안(그대로·보류·유지한 조문도). 새 계층은
>   승인한 시행일부터다(그 전 날짜는 얼린 옛 장 번호로).
> - **얼리기** — 계층이 바뀌는 조문(제안 계층·장·절 변경)의 발행 이력 중 아직 얼리지 않은 버전 **모두**에 승인 직전 계층을 넣는다(직전 버전만 얼리면 더 오래된
>   버전이 새 계층을 따라간다). 계층이 바뀌지 않는 승인(일반 승인·후보 승인·폐지)은 얼리지 않는다 — 얼린 값 = 실제 계층 변경 이력.
> - **시점 조회·신구 대비**: 고른 버전의 얼린 계층으로 자리·조 제목·장·절을 놓는다(지운 장은 그때 번호·제목으로 다시 세우고, 장의 조문이 모두 얼린 값이면 그때 장
>   번호·제목). 얼린 계층이 없으면 지금 조문 행.
> - **바로잡기**(조 순서 재정렬·번호 직접 수정)는 버전을 만들지 않으니, 바뀐 조문의 새 자리가 다른 조문의 얼린 자리 어느 것과도 같으면 막는다(기간을 따지지 않는
>   보수적 검사).
> - **묶음 승인** — 같은 시행일로 전부 되거나 전부 안 됨. 더 늦은 시행본이 있으면 거부, 폐지 뒤 다시 시행이면 폐지일 이후. 승인 시행일과 그 뒤 모든 시행일마다 그날
>   시행 중인 버전의 계층으로 자리 겹침을 본다(유지한 원문에 없는 조문·미래 폐지로 남긴 조문·시행 예정 버전이 새 조문·이동과 같은 자리면 거부). 폐지는 시행일이
>   오늘 이전이면 그 날로, 미래면 미결로 남긴다(번호가 바뀌는 장·절에 있으면 거부 — 장 번호가 시행일에 바뀌는데 그 조문엔 새 버전이 없어서).
> - **잠금·지문** — 반영·묶음 검토 요청·승인·반려는 규정 → 그 규정의 모든 조문(id 순) 잠금 아래 묶음 지문을 다시 계산한다. 계층을 바꾸는 쓰기(재정렬, 조문
>   생성·번호 수정·삭제, 장·절 생성·수정·삭제)는 규정 행을, 버전 쓰기(초안 생성·수정, 단건 검토 요청·승인·반려, 폐지, 한꺼번에 시행, 시행일 보정)는 조문 행을
>   잠근다. 지문은 저장 전후 키 순서가 바뀌는 jsonb 때문에 키를 정렬한 JSON 으로 만든다.
> - **우회 차단** — 묶음 버전은 단건 검토 요청·승인·반려 409, 한꺼번에 시행에서 빠진다. 묶음 반려는 묶음 초안을 거두고(발행된 적 없는 검토 대상) 원문을 다시
>   비교할 수 있게 돌려 둔다.
> - 옮김·본문 바뀜을 새 조문으로 돌리면 그 기존 조문은 곧바로 원문에 없음 항목이 된다(반영 전에 유지·폐지를 정한다 — 반영 뒤에 생기면 승인 전에는 정할 길이 없다).
> - 결정을 정하며 찾은 순서 결함 두 가지는 1단계 판정에 반영했다(머리 행·항을 번호로 먼저 차지).

---

> **잠금 순서·세기·기다림(T-131, 배포 전 검토 뒤 보강)** — 쓰기는 모두 **규정 → 조문(id 순) → 재파싱 검토 행 → 원문** 순서로 `FOR NO KEY UPDATE` 잠금을 잡는다(공용 `common/row-locks` — 이 파일 밖의 `FOR UPDATE` 는 시험이 막는다). 규정을 새로 만드는 쓰기(새 규정·가져오기 확정·텍스트 가져오기·일괄 등록)는 그 앞에 **회사 행**을 잡고 플랜 상한·코드 중복을 센다(T-135, `policies/policy-slots`). 가져오기 확정은 회사 → 원문 순서로 잡은 뒤 원문 상태·미리보기를 다시 보고 규정 전체를 한 트랜잭션에 넣는다(특허 도 4 S450). 텍스트 가져오기도 같은 행 만들기·넣기(`policies/new-policy-records`)를 쓴다. ① 첫 시행이면 규정 시행일을 채우는 한꺼번에 시행·시행일 보정도 규정부터 잡고, 판단에 쓰는 값(첫 시행 여부·초안 본문·폐지·규정 시행일)은 잠근 뒤 다시 읽는다 — 예전에는 조문을 잡은 채 규정을 기다려 조 재정렬·재파싱과 교착(500)했다. 계층 쓰기(장·조문 고치기·지우기·조 재정렬)와 규정 정보 고치기도 잠근 뒤 읽는다. ② 반영·검토 요청·승인·반려는 검토 행(반영은 원문까지) 잡은 뒤 결정·상태를 읽고, 결정·다시 비교도 규정부터 잡는다. 다시 비교는 잠그기 전에 계산하므로 잠근 뒤 원문·규정 상태를 다시 본다(쓴 원문 409 `원문을 다시 가져와`, 바뀌었으면 409 `다시 비교`). 승인 뒤 원문에 없는 조문 폐지는 폐지와 항목 결과를 한 트랜잭션으로. ③ `FOR NO KEY UPDATE` 는 쓰는 쪽끼리는 줄 세우되 FK 확인(의견·즐겨찾기·개정 후보 넣기)은 막지 않는다. 지우기만 조문을 id 순으로 `FOR UPDATE` 로 미리 잡는다. ④ 잠금 문장은 3초(긴 트랜잭션 30초) 안에 못 잡으면 409(잠시 뒤 다시) — `lock_timeout` 은 앞선 대기자 뒤에 한 번, 잠근 쪽에 또 한 번 따로 세서 여럿이 몰리면 두 배 넘게 기다리므로 잠금 문장에는 `statement_timeout` 도 같은 값으로 건다. 그 뒤의 암묵적 대기·교착은 전역 필터가 409(교착은 오류 로그), 트랜잭션을 시작하지 못하면(커넥션 부족) 503. 규정을 지울 때는 규정 행을 처음부터 `FOR UPDATE` 로 잡는다(약하게 잡았다가 올리면 조문 즐겨찾기 넣기와 엇갈려 멈춘다). 재파싱 반영을 쓴 뒤 632466a 이전으로 되돌리는 절차는 [런북 7](../16_Runbook_배포롤백/Runbook_배포롤백.md).

## 8. 명세서와 현재 제품의 불일치 (변리사 확인 필요)

대표가 "만들 것을 썼다"고 확인했으므로 **미구현 자체는 문제가 아니다.**
다만 아래는 출원 전에 한 번 짚어야 한다.

| # | 항목 | 내용 |
|:--:|---|---|
| 1 | **청구항 5의 변수 마스터** | 명세서는 변수 값에 *유효기간*과 *테넌트 범위*가 있다고 한다. 현재 `Variable`은 `defaultValue` 하나뿐이고 유효기간이 없다. 테넌트 범위는 `Variable.tenantId`로 있으나 **값 단위가 아니라 변수 단위**다 → **해소(T-109 ①)**: 값마다 유효기간, 범위는 그 회사 |
| 2 | **청구항 5의 사용 위치** | *"본문 내 가변 문구의 사용 위치"* — 현재 `VariableUsage`는 `(versionId, variableId)` 뿐이라 위치 정보가 없다 → **해소(T-109 ①)**: `VariableBinding`(구간·문구·순번·기준 버전). 후보 생성 때 그 위치에 예정 사내 시행일 값을 넣는다(T-109 ②) |
| 3 | **도6의 재파싱 지문** | 코드에 지문·fingerprint 로직이 없다 → **해소(T-110)**: 계층·내용 지문 2축 판정과 재파싱 검토(①), 반영·묶음 승인·버전별 계층(②) |
| 4 | **청구항 7의 날짜 3종** | 현재 2종(개정일·시행일). 법령 시행일을 담을 곳이 없다 → **해소(T-108·T-111)**: 발행일 기록(옛 발행은 승인 시각으로 보정·표시), 법령 시행일은 변경 이벤트 연결, 세 날짜를 함께 보이고 시점 조회는 사내 시행일 하나로 |
| 5 | **구현했으나 청구항에 없는 것** | 시점 조회, 대비표(신구법비교), 3단비교, 법령체계표, 테넌트 격리, 감사 로그, HWPX 내보내기 — 배경 요소로만 들어가 있다. **종속항을 더 세우면 보호 범위가 넓어질 수 있다** (변리사 판단 영역) |
| 6 | **상위 조항으로 영향 찾기 (T-148, 2026-10-14)** | 청구항 1·3은 *변경된 법령조항*을 기점으로 관계 정보를 따라 영향 조문을 식별한다. 구현은 바뀐 조항의 **상위 조항(조·항)에 건 관계 정보**도 따라가고, 그렇게 찾은 후보는 표시와 함께 신뢰도를 낮춘다(5.3 구현 메모). 관계 그래프의 경로로 보아 청구항 범위 안인지, 종속항으로 세울지 확인이 필요하다. 대표 피드백(2026-10-13)으로 계획한 AI 검토 우선순위·AI 관련 조문 찾기(SRS LAW-23·24)도 청구항 밖 요소라 구현할 때 이 표에 올린다. 저장소가 공개라 상세 설계를 올리기 전에 출원 일정·공지예외 기간도 함께 확인한다 |

## 9. 단계 계획

각 단계는 **그 자체로 쓸모가 있어야 한다.** 4단계가 끝나야 뭔가 되는 계획은 세우지 않는다.

| 단계 | 내용 | 단독으로 쓸모 있나 | 작업 |
|:--:|---|---|---|
| **1** | 법령 엔티티 + 법령 관계 정보 (`LawSource`/`Law`/`LawArticle`/`LawLink`) + 연결 화면 | ✅ 자유 텍스트 메모가 **추적 가능한 연결**이 된다. "이 법이 바뀌면 어디가 영향받나"를 사람이 직접 볼 수 있다 | T-100~T-102 |
| **2** | 변경 감지 (`LawChangeEvent` + 주기 동기화 + 이력) | ✅ 개정을 **놓치지 않는다.** 후보 생성이 없어도 "제60조가 바뀌었고 우리 제28조가 걸려 있다"까지 알려 준다 | T-103~T-104 |
| **3** | 영향 분석 + 후보 생성(규칙) + 검토 화면 + 승인 발행 | ✅ **청구항 1 완성.** 여기까지가 발명의 최소 실시 | T-105~T-108 |
| **4** | 명세서 정합성 — 변수 유효기간·사용 위치, 재파싱 지문, 날짜 3종 | ✅ 청구항 2·5·7 충족 | T-109~T-111 |
| **5** | 언어모델 생성 방식 (청구항 4 제2 방식) | 3단계 위의 선택지 | T-112 |

**1단계부터 순서대로 간다.** ②가 없으면 ③④⑤가 성립하지 않는다 — 건너뛸 수 없는 순서다.

| **틀린 연결이 만든 그럴듯한 초안** | 자동 추천 관계로 초안을 만들면 검토자가 근거를 믿고 승인한다 | `confirmed` 관계로만 후보를 만든다(5.3). 화면에 확정 상태를 항상 표시 |
| **폴링 조용한 실패** | 법제처 API는 실패해도 HTTP 200 | `LawSyncRun` 이력 + 실패 시 종료 코드. "개정 없음"과 "확인 못 함"을 구별해 표시 |
| **사라진 법령조항의 연결 소실** | 전부개정 같은 구조 변경으로 조항이 응답에서 사라지면 `LawArticle` 삭제와 함께 연결이 cascade 로 지워진다. 영향도 후보도 만들 수 없다 | 지금은 사유(`unresolvable`)만 보인다(T-105). 삭제 전 연결 스냅샷 또는 조항 보존은 **T-124**. 법제처는 보통 삭제 조항을 "삭제 <날짜>" 본문으로 남겨 연결이 유지된다 — 그 경우는 `law_provision_repealed` 로 사람에게 넘긴다(T-106) |
| **`versionKey` 정규화 변경** | 규칙이 바뀌면 전체가 "개정됨"으로 보여 가짜 이벤트가 쏟아진다 | 정규화 규칙에 버전을 붙이고, 바꿀 때 재계산 마이그레이션을 동반 |
| **변수 치환 offset 밀림** | 앞에서부터 치환하면 뒤쪽 위치가 전부 틀어진다 | 내림차순 치환(5.3). 단위 테스트로 고정 |
| **법제처 호출량 제한** | 인증값(OC) 단위로 제한된다 | 법령을 테넌트 공용으로 둬서 중복 호출을 없앤다(4.1). 폴링은 `lastCheckedAt` 오래된 순 N건 |
| **개정이 사내 규정에 그대로 안 맞음** | 법 문구를 그대로 넣으면 문장이 깨진다 | 후보는 **초안**이다. 검토 화면에서 손질 가능(`PATCH /amendments/:id`) |

## 11. 이 설계가 바꾸지 않는 것

- **조·항·목을 단일 `Article` 테이블에 담는 구조** — [ADR-0011](../10_ADR_의사결정기록/ADR.md). 청구항 2가 이 구조를 그대로 기술한다
- **`Article.chapterId` 필수 유지** — [ADR-0019](../10_ADR_의사결정기록/ADR.md)
- **시점 조회의 기준일은 사내 규정 시행일** — 5.5
- **테넌트 격리는 애플리케이션 계층** — [ADR-0002](../10_ADR_의사결정기록/ADR.md). RLS를 새로 도입하지 않는다
- **기존 버전 워크플로(draft→review→published→archived)** — 후보가 승인되면 이 흐름에 합류할 뿐, 별도 상태를 만들지 않는다
