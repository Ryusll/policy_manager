## ADR-0001 — 조·항·목을 단일 Article 테이블 + nullable 번호로 표현

**상태**: Accepted

**맥락**
법령정보센터 방식의 조(條)·항(項)·목(目) 3계층을 표현해야 한다. 계층마다 별도 테이블(Article/Clause/Item)로 나누는 방식과, 한 테이블에서 번호 컬럼으로 계층을 구분하는 방식이 있다.

**결정**
`Article` 단일 테이블에 `number`(조), `clauseNumber`(항, nullable), `itemNumber`(목, nullable)를 두고 행 유형을 번호 null 여부로 판별한다. 조 루트=`clauseNumber·itemNumber` 둘 다 null, 항=`clauseNumber`만 있음, 목=`itemNumber` 있음. (근거: `apps/api/prisma/schema.prisma`의 Article, `apps/web/src/lib/articleStructure.ts`, `legalArticleLabel.ts`)

**결과**
- (+) 조인 없이 한 테이블 정렬(`number → clauseNumber → itemNumber`)로 전체 트리를 구성. 스키마가 단순하고 마이그레이션 부담이 적다.
- (+) "1항에 잘못 들어간 제목을 조 제목으로 승격" 같은 구조 편집이 번호만 바꾸면 되는 단순 연산이 된다.
- (−) 행 유형 판별 로직이 DB가 아닌 애플리케이션 코드에 흩어진다(`articleStructure.ts` 등). DB 제약으로 무결성을 강제하기 어렵다.
- (−) 가져오기 시 항·목 매핑이 파서의 별도 추론에 의존한다(DB가 계층을 강제하지 않으므로). 2026-07-30 [ADR-0010](#adr-0010--가져오기-항목-추론을-클라이언트에서-수행)으로 추론을 추가해 수동 편집 부담은 해소했다.

## ADR-0002 — 멀티테넌시를 공유 DB + tenantId 컬럼(앱 레벨 격리)로 구현

**상태**: Accepted

**맥락**
여러 고객사(테넌트)가 한 인스턴스를 공유하는 SaaS다. 테넌트별 DB/스키마 분리, PostgreSQL Row-Level Security(RLS), 공유 테이블+`tenantId` 컬럼 중 선택이 필요했다.

**결정**
모든 핵심 테이블에 `tenantId` FK를 두고 애플리케이션 코드(서비스 계층)가 매 쿼리에 `tenantId` 필터를 건다. RLS는 사용하지 않는다. (근거: `schema.prisma` 전 모델의 `tenantId`, 각 `*.service.ts`의 `where: { tenantId }` 패턴, `common/guards`)

**결과**
- (+) 단일 DB로 운영·마이그레이션·백업이 단순하다. 소규모 팀에 적합.
- (+) 테넌트 간 통계·통합 관리(global_admin)가 쉽다.
- (−) **격리가 코드 규율에 의존한다.** 어느 한 쿼리라도 `tenantId` 필터를 빠뜨리면 테넌트 간 데이터 노출이 발생한다(보안 검토 대상, [15_보안검토서](../15_보안검토서/보안_검토서.md)). 404로 위장되지만 근본 방어는 아니다.
- (−) 데이터 급증 시 테넌트별 분리/샤딩으로 전환하려면 대규모 마이그레이션이 필요하다.

## ADR-0003 — 테넌트 브랜딩을 서버가 아닌 브라우저 localStorage에 저장

**상태**: **Superseded by [ADR-0014](#adr-0014--테넌트-브랜딩을-서버-저장으로-전환하고-localstorage는-캐시로-강등)** (2026-08-22)

**맥락**
고객사 로고·브랜드 마크·테마 색을 저장해야 한다. 플랫폼(운영사) 브랜딩은 서버(`PlatformBranding` 테이블)에 두기로 이미 결정됨.

**결정**
테넌트 브랜딩은 서버에 저장하지 않고 브라우저 localStorage에 Zustand persist(`veda-brand`)로 저장한다. (근거: `apps/web/src/stores/brandStore.ts`의 `persist(..., { name: 'veda-brand' })`) 플랫폼 브랜딩만 서버 API(`/platform-branding`)로 관리한다.

**결과**
- (+) 브랜딩 CRUD를 위한 백엔드 API·테이블·업로드 스토리지가 필요 없어 구현이 빠르다.
- (−) **기기/브라우저를 바꾸면 브랜딩이 유실된다.** 팀원 간 공유도 안 된다(각자 로컬에만 존재). SRS BRAND-2에 제한사항으로 명시.
- (−) 로고 이미지가 data URL로 localStorage에 들어가 용량 한계가 있다.
- 향후 서버 동기화가 필요하면 별도 결정(ADR)으로 이 결정을 대체한다.

## ADR-0004 — 결제를 provider 추상화로 두되 결제 이력 테이블은 미사용

**상태**: Accepted · **이력 미사용 부분은 2026-08-23 해소(T-17)** · **기본값 `mock` 은 2026-10-08 [ADR-0022](#adr-0022--결제는-설정이-없으면-닫힌다--가격-확정-전-요금제-변경은-플랫폼-관리자만)로 대체**

**맥락**
플랜 업그레이드(Pro/Enterprise) 결제가 필요하나, 초기에는 특정 PG사 연동 없이 데모/개발이 가능해야 한다.

**결정**
`PAYMENT_PROVIDER` 환경변수로 분기한다. `mock`(기본)은 즉시 플랜을 올리고, 그 외 값은 `PAYMENT_HOSTED_CHECKOUT_URL`로 리다이렉트한 뒤 웹훅(`payment.succeeded`, 시크릿 검증)으로 반영한다. 결제 처리 결과는 `tenant.plan` 갱신 + 감사 로그만 남긴다. (근거: `apps/api/src/billing/billing.service.ts`)

> **2026-10-08 변경(ADR-0022)**: 비어 있으면 `mock` 이 아니라 **결제 미사용**이다. 운영이 이 값을 넘겨받지 않아 mock 으로 돌았고, 고객사 관리자가 결제 없이 요금제를 올릴 수 있었다. "시크릿 검증"도 비밀키가 설정됐을 때만 하던 것을, 이제는 비밀키가 없으면 웹훅을 받지 않는다.

**결과**
- (+) PG 없이도 전체 업그레이드 플로우를 데모할 수 있고, 나중에 웹훅만 실제 PG에 물리면 된다.
- (−) ~~스키마에 있는 `BillingCustomer`/`BillingSubscription`/`BillingPayment` 테이블을 전혀 쓰지 않는다~~ → **2026-08-23 해소(T-17)**. 결제 성공 시 세 테이블에 기록하고 `tenant.planExpiresAt` 을 구독 종료일로 채운다. 기록 경로가 provider 와 무관하므로, 실 PG 를 붙일 때 바뀌는 곳은 웹훅 해석뿐이다.
- (−) 특정 PG SDK·영수증·환불 처리가 없다. 실서비스 결제 전 별도 구현 필요(D-03).
- (−) **mock 결제는 0원으로 기록된다.** 실제로 돈이 오가지 않으므로 요금표를 지어내 넣지 않았다 — 이력이 그럴듯하게 거짓이 되는 것을 피한 것이다. 요금 정책이 정해지면(D-03) 실 결제 금액이 그대로 들어간다.
- (−) 청구 주기를 **한 달 고정**으로 뒀다. 연간 결제나 비례 정산(proration)은 없다. 실 PG 연동 시 다시 볼 지점.

## ADR-0005 — 컨테이너 기동 시 migrate 실패하면 db push로 폴백

**상태**: **Superseded by [ADR-0012](#adr-0012--마이그레이션을-baseline으로-스쿼시하고-db-push-폴백을-제거) (2026-08-02)**

**맥락**
API 컨테이너 기동 시 DB 스키마를 자동으로 최신화해야 한다. Prisma에는 `migrate deploy`(이력 기반)와 `db push`(스키마 강제 반영)가 있다.

**결정**
`docker-entrypoint.sh`에서 `prisma migrate deploy`를 먼저 시도하고, 실패하면 `prisma db push --accept-data-loss`로 폴백한 뒤 데모 시드를 실행한다. (근거: `apps/api/docker-entrypoint.sh`)

**결과**
- (+) 마이그레이션 이력이 깨져도 컨테이너가 뜬다(개발/데모 편의).
- (−) **`--accept-data-loss` 폴백은 운영 데이터 손실 위험이 있다.** 초기 스키마를 만드는 baseline 마이그레이션이 없어 이 폴백에 실질적으로 의존한다([13_기술부채대장](../13_기술부채대장/기술부채_대장.md), [16_Runbook](../16_Runbook_배포롤백/Runbook_배포롤백.md) 5절).
- 개선 방향: baseline 마이그레이션 생성 후 운영에서는 폴백 경로를 제거하고 `migrate deploy`만 사용.

## ADR-0006 — 검색을 pg_bigm 우선 + ILIKE 폴백으로 구현

**상태**: Accepted

**맥락**
한국어 규정 본문·제목의 부분 일치 검색이 필요하다. PostgreSQL 기본 `LIKE`/`ILIKE`는 한국어 부분 일치에 인덱스 활용이 어렵다.

**결정**
`pg_bigm` 확장을 설치해 우선 사용하고, 사용 불가 환경에서는 `ILIKE`로 폴백한다. 검색 대상은 규정명·코드 + **게시(published) 상태** 조문 본문/제목. (근거: 마이그레이션 `20250416180000_enable_pgbigm`, `apps/api/src/search/search.service.ts`)

**결과**
- (+) 한국어 2-gram 인덱스로 부분 일치 검색 성능을 확보한다.
- (+) 확장이 없는 환경(로컬 등)에서도 폴백으로 동작한다.
- (−) `pg_bigm`은 표준 PostgreSQL에 없어 커스텀 이미지/설치가 필요하다(인프라 종속성).
- (−) draft/review 조문은 검색에서 제외된다(의도된 동작이나, 편집 중 콘텐츠는 안 잡힘).

## ADR-0007 — JWT를 Authorization 헤더로, CORS는 origin reflect

**상태**: Accepted

**맥락**
사용자가 `localhost`, `127.0.0.1`, LAN IP, 실제 도메인 등 다양한 URL로 접속한다. `PUBLIC_URL` 하나로 모든 브라우저 오리진을 열거할 수 없다.

**결정**
인증 토큰은 쿠키가 아닌 `Authorization: Bearer` 헤더로 전달한다. CORS는 `origin: true`(요청 오리진 반사) + `credentials: true`로 설정한다. (근거: `apps/api/src/main.ts`의 `enableCors({ origin: true, credentials: true })` 및 주석)

**결과**
- (+) 어떤 접속 URL에서도 로그인이 동작한다(개발·사내망 편의).
- (+) 토큰이 헤더에 있어 CSRF 표면이 쿠키 방식보다 작다.
- (−) 오리진을 반사하므로 CORS가 사실상 모든 출처를 허용한다. 토큰이 헤더 기반이라 브라우저 자동 전송은 없지만, 운영 환경에서는 허용 오리진 화이트리스트를 고려할 수 있다(보안 검토 여지).
- (−) 토큰이 JS에서 접근 가능한 저장소에 보관되면 XSS에 노출된다 — 프론트 XSS 방어가 중요.

## ADR-0008 — PDF 텍스트 추출을 런타임 Python 서브프로세스로 수행

**상태**: Accepted

**맥락**
규정 가져오기에서 PDF의 텍스트·레이아웃을 추출해야 한다. Node 생태계 PDF 파서보다 Python `pdfplumber`/`pymupdf`의 한국어·표 추출 품질이 낫다고 판단.

**결정**
API 런타임 이미지에 Python과 `pdfplumber`·`pymupdf`를 설치하고, Node에서 `spawnSync`로 파이썬 추출 스크립트를 호출한다. (근거: `apps/api/Dockerfile`의 `pip3 install ... pdfplumber pymupdf`, `apps/api/src/regulation-parse/regulation-parse.service.ts`의 `spawnSync`)

**결과**
- (+) PDF 추출 품질을 검증된 Python 라이브러리로 확보한다.
- (−) 이미지에 Python 런타임이 더해져 크기·빌드 시간이 증가한다.
- (−) Node↔Python 프로세스 경계로 오류 처리·성능·배포 복잡도가 늘어난다. 프론트 UI가 아직 없어(regulation-parse UI 미연결, SRS 14.2) 현재는 API로만 사용된다.
- (−) **현재 이 결정은 빌드를 깨뜨린다**: `pip install pymupdf pdfplumber`가 Alpine(musl)에서 C 툴체인/호환 wheel 부재로 실패한다(2026-07-21 스모크 테스트에서 확인, [13_기술부채대장](../13_기술부채대장/기술부채_대장.md) #7). 베이스 이미지(debian-slim) 전환·빌드툴 추가·wheel 고정 중 하나로 재검토 필요.

## ADR-0009 — 템플릿 sanitize를 서버 sanitize-html + 클라이언트 DOMPurify로 이원화

**상태**: Accepted (2026-07-30)

**맥락**
Enterprise 플랜은 출력 템플릿의 HTML/CSS를 자유 편집할 수 있다. 기존 sanitize는 서버·클라이언트 모두 정규식으로 위험 태그·속성을 지우는 방식이었는데, 실측에서 **따옴표 없는 이벤트 핸들러**(`<img src=x onerror=alert(1)>`)와 허용목록에 없던 태그(`<svg onload=…>`, `<details ontoggle=…>`)가 통과했다(대표 벡터 6건 중 5건 우회). 정규식으로 HTML을 파싱하려는 접근 자체의 한계다.

**결정**
허용목록(allowlist) 기반 라이브러리로 교체한다. 서버는 `sanitize-html`(순수 Node), 클라이언트는 `DOMPurify`(브라우저 DOM 기반)를 사용한다. **서버를 보안 경계**로 삼아 저장 시점에 정화하고, 클라이언트 sanitize는 렌더 시 2차 방어로 둔다. CSS는 두 라이브러리의 대상이 아니므로 `expression()`·`behavior:`·`@import`·`url(javascript:)`·`</style>` 탈출을 제거하는 별도 정책을 양쪽에 둔다.

**대안**: 한쪽 라이브러리를 양쪽에서 쓰기(`isomorphic-dompurify`). 서버에 jsdom이 필요해 이미지가 무거워지고, 이미 취약한 Docker 빌드(ADR-0005·기술부채 #7)의 실패 지점을 늘릴 위험이 있어 채택하지 않았다.

**결과**
- (+) XSS 벡터 11건 전부 차단 확인. 정상 템플릿(`.tmpl-*` 클래스, data URI 로고)은 보존됨.
- (+) 새 우회 기법은 라이브러리 업데이트로 흡수된다(정규식 유지보수 부담 제거).
- (−) **허용목록이 서버·클라이언트 두 곳에 존재한다.** 한쪽만 고치면 정책이 어긋난다(토큰에서 겪은 drift 문제와 동일 구조). 지금은 주석·문서로 "함께 수정" 규약을 두었고, 공용 패키지(`packages/*`)로 추출하는 것은 후속 과제.
- (−) `<a>`는 기존 고객 템플릿 호환을 위해 허용했다(DOMPurify·sanitize-html의 URI 스킴 검사에 의존).

## ADR-0010 — 가져오기 항·목 추론을 클라이언트에서 수행

**상태**: Accepted (2026-07-30)

**맥락**
가져오기 파서는 조 단위(`number`/`title`/`content`)까지만 만들고 항(①②…)·목(1. 2. …)은 본문 텍스트에 섞여 있었다. 조·항·목 편집 기능은 이미 완성돼 있었으나 입구가 끊겨 "가져온 뒤 전부 수동 정리"가 필요했다(개발정의서 8.3의 명시된 한계).

**결정**
추론을 **클라이언트(`apps/web/src/lib/policyImportHierarchy.ts`)** 에서 수행한다. 기존 파싱·정제·미리보기 파이프라인이 모두 클라이언트에 있어 같은 자리에서 미리보기(인식된 항·목 개수)를 보여줄 수 있기 때문이다. 등록 시 `clauseNumber`/`itemNumber`를 채워 기존 조문 생성 API로 보낸다(API 변경 없음). 오인식 대비로 「항·목 자동 인식」 토글을 두고 기본 ON.

**결과**
- (+) 백엔드 변경 없이 연결고리를 메웠다. 기존 파서·분할모드·정제 옵션과 조합해 동작한다.
- (+) 보수적 매칭으로 오인식을 줄였다: `2026. 1. 1.` 같은 날짜는 목으로 보지 않고, 상위 항이 없는 `1.`은 조 본문으로 남긴다.
- (−) 서버 측 가져오기 경로(`POST /admin/import/policies`, `regulation-parse`)는 이 추론을 **거치지 않는다.** 해당 경로로 들어온 데이터는 여전히 조 단위다. 법제처 연동(T-54)에서 매퍼를 만들 때 이 로직을 서버와 공유할지 재검토가 필요하다.

## ADR-0011 — 절(節)을 선택 계층으로 추가하되 `Article.chapterId`는 필수로 유지

**상태**: Accepted (2026-08-02)

**맥락**
법령은 `편 > 장 > 절 > 조 > 항 > 목` 구조를 갖지만, 사내 규정은 이를 반드시 따르지 않는다. 짧은 내규는 장·절 없이 `제1조`부터 시작하는 경우가 흔하다. 대표 지시(2026-08-02)로 ① 절 계층을 추가하고 ② 장 없이 조부터 만들 수 있어야 한다는 요구가 확정됐다.

"조는 필수, 장·절은 선택"이 정석이지만, `Article.chapterId`를 nullable로 바꾸면 **모든 조회 경로가 영향받는다.** 현재 조문은 `Article → Chapter → Policy`로만 규정에 도달하므로(테넌트 격리도 이 경로에 의존), nullable로 만들려면 `Article.policyId`를 새로 두고 전 서비스·목차·검색·렌더러의 조인을 다시 짜야 한다.

**결정**
- `Section` 모델을 신설하고 `Article.sectionId`를 **nullable**로 둔다. 절에 속하지 않는 조와 속하는 조가 같은 장에 공존할 수 있다.
- `Article.chapterId`는 **필수로 유지**한다. 대신 장이 없는 규정은 `suppressHeader: true`인 장 1건을 만들어 담고, 목차·전문·인쇄에서 장 제목을 표시하지 않는다. 사용자에게는 "장이 없는 규정"으로 보인다.
- 가져오기 경로가 원문에 장이 없을 때 임의로 붙이던 `"제1장 총칙"`/`"원문"` 제목을 없애고 숨김 장을 쓰도록 고친다.

**대안**: `Article.chapterId` nullable + `Article.policyId` 추가. 정석에 가깝지만 조인·테넌트 격리 경로를 전면 수정해야 하고, 자동화 테스트가 없는 현 상태([기술부채 #1](../13_기술부채대장/기술부채_대장.md))에서 회귀 위험이 크다고 판단해 보류했다.

**결과**
- (+) 사용자 관점의 요구("장 없이 조부터")를 스키마 대수술 없이 충족한다.
- (+) 절을 쓰는 규정과 쓰지 않는 규정을 한 모델로 다룬다.
- (−) DB상으로는 여전히 조가 장에 종속된다. "장 없음"은 **숨김 장이라는 관례**로 표현되므로, 이 관례를 모르는 코드가 빈 제목 장을 그대로 노출할 위험이 있다(`isChapterHeaderHidden` 헬퍼를 반드시 경유해야 함).
- (−) 정석 구조로 가려면 후속 마이그레이션이 필요하다. 테스트 기반이 갖춰진 뒤 재검토한다. → **2026-08-28 재검토 완료(T-84): 이행하지 않기로 확정. [ADR-0019](#adr-0019--articlechapterid는-필수로-유지한다-adr-0011-재검토-완료)**

## ADR-0012 — 마이그레이션을 baseline으로 스쿼시하고 db push 폴백을 제거

**상태**: Accepted (2026-08-02). [ADR-0005](#adr-0005--컨테이너-기동-시-migrate-실패하면-db-push로-폴백)를 대체한다.

**맥락**
마이그레이션 13건 중 첫 번째(`enable_pgbigm`)가 확장만 만들고 테이블은 만들지 않아, 빈 DB에서 `migrate deploy`가 두 번째 마이그레이션부터 `relation "users" does not exist`로 실패했다. 그래서 기동 스크립트가 `db push --accept-data-loss`로 폴백했는데, 이는 **운영 데이터 손실 위험**이 있고 스키마가 마이그레이션 이력으로 재현되지 않는다는 뜻이기도 했다. 실제로 개발 DB의 `_prisma_migrations`에는 `google_oauth`가 실패 상태로 남아 있었다.

**결정**
Prisma 표준 baseline 절차대로 이력을 스쿼시한다.
- `00000000000000_init` — 현재 스키마 전체(`migrate diff --from-empty --to-schema-datamodel`로 생성, 23개 테이블)
- `00000000000001_enable_pgbigm` — 기존 pg_bigm 커스텀 SQL을 그대로 보존(가드 포함)
- 기존 13개 마이그레이션 파일은 제거한다. 재생이 불가능했으므로 이력으로서의 가치가 없었다.

기동 스크립트에서 `db push --accept-data-loss`를 **제거**하고, 대신 baseline 이전 DB를 자동 처리한다: `migrate deploy` 실패 → `users` 테이블 존재 확인 → 현재 이력에 없는 `_prisma_migrations` 행 정리(스쿼시로 사라진 실패 기록이 P3009를 유발) → baseline을 applied로 표시 → 재시도. 그래도 실패하면 **종료**(1)한다.

**결과**
- (+) 빈 DB에서 `migrate deploy`만으로 전체 스키마가 재현된다. `migrate diff`로 **드리프트 0** 확인.
- (+) 데이터 손실 경로가 사라졌다. 실패는 조용히 넘어가지 않고 컨테이너를 멈춘다.
- (+) 앞으로 `prisma migrate dev`가 섀도 DB에서 정상 동작하므로 마이그레이션을 손으로 쓰지 않아도 된다.
- (−) 2026-08-02 이전 마이그레이션 이력이 사라졌다(어차피 재생 불가였다).
- (−) 기존 DB는 최초 1회 자동 baseline 처리를 거친다. 이 경로는 `_prisma_migrations`의 과거 행을 지우므로, 커스텀 마이그레이션을 따로 넣어 쓰던 환경이 있다면 확인이 필요하다.

## ADR-0013 — 컨테이너 베이스를 Alpine → Debian slim으로 전환

**상태**: Accepted (2026-08-02)

**맥락**
[ADR-0008](#adr-0008--pdf-텍스트-추출을-런타임-python-서브프로세스로-수행)에 따라 런타임 이미지에 `pdfplumber`·`PyMuPDF`를 설치하는데, Alpine(musl)에서 `pip install`이 실패해 **이미지 자체를 빌드할 수 없었다**. 실측 결과 원인은 명확했다: PyMuPDF는 musllinux wheel을 **아예 배포하지 않아**(`No matching distribution found`) 소스 빌드로 넘어가고, Alpine에는 C 툴체인이 없어 `cc` 127로 죽는다. pdfplumber는 순수 Python이라 문제없다.

**결정**
빌더·런너 모두 `node:20-slim`(Debian bookworm)으로 전환한다. 두 스테이지의 베이스가 같아야 builder에서 생성한 Prisma 엔진을 런너가 그대로 쓸 수 있다. Prisma `binaryTargets`도 `linux-musl-openssl-3.0.x` → `debian-openssl-3.0.x`로 바꾼다. pip 설치에는 `--only-binary=:all:`을 붙여 wheel이 없으면 **즉시 실패**하게 한다(소스 빌드로 조용히 새다가 뒤늦게 깨지는 것을 막는다).

**대안**: Alpine 유지 + 빌드 툴체인 설치. MuPDF 소스 빌드는 느리고 취약해 채택하지 않았다. PyMuPDF를 빼고 pdfplumber만 쓰는 안도 검토했으나, PyMuPDF는 pdfplumber 실패 시의 폴백 엔진이라 추출 견고성이 떨어져 보류했다.

**결과**
- (+) 원본 Dockerfile 그대로 빌드·기동되고, 런타임에서 `import pdfplumber, fitz`가 성공한다.
- (+) wheel 부재가 빌드 실패로 즉시 드러난다.
- (−) 이미지 크기가 Alpine 대비 커진다.
- (−) Alpine 전용 설정(musl 타깃)이 남아 있으면 엔진 불일치가 나므로, 베이스를 다시 바꿀 때는 `binaryTargets`도 함께 봐야 한다.

## ADR-0014 — 테넌트 브랜딩을 서버 저장으로 전환하고 localStorage는 캐시로 강등

**상태**: Accepted (2026-08-22). [ADR-0003](#adr-0003--테넌트-브랜딩을-서버가-아닌-브라우저-localstorage에-저장)을 대체한다.

**맥락**
ADR-0003은 브랜딩을 브라우저 localStorage에만 뒀다. 구현은 빨랐지만 그 결정이 적어둔 두 가지 제약이 그대로 현실이 됐다 — **기기·브라우저를 바꾸면 사라지고, 팀원끼리 공유되지 않는다.** 브랜딩은 Pro 이상 **유료 기능**이라, 돈을 낸 쪽에서 보면 유실은 제약이 아니라 고장이다.

**결정**
`TenantBranding` 테이블(테넌트당 1행, `tenantId` PK, Tenant 삭제 시 Cascade)에 저장하고 서버를 정본으로 삼는다. localStorage는 **버리지 않고 캐시로만** 남긴다.

- 조회 `GET /tenant-branding` — 플랜·역할 제한 없음. 헤더는 모든 구성원이 그리므로 여기를 막으면 Starter 테넌트 화면이 깨진다
- 저장 `PUT /tenant-branding` — `admin` + Pro 이상
- 로고는 `data:image/...` 만 받는다. 외부 URL을 허용하면 헤더가 매번 남의 서버를 부른다(추적·가용성)

**localStorage를 남긴 이유**: 새로고침마다 서버 응답을 기다리면 헤더가 기본 배지 → 회사 로고로 한 번 튄다. 로고는 화면 맨 위 고정 자리라 이 깜빡임이 눈에 띈다. 캐시로 즉시 그리고 응답이 오면 조용히 맞춘다.

**함께 정한 것 두 가지**

1. **기존 로컬 브랜딩 이관.** 서버에 행이 없고(`updatedAt === null`) 이 브라우저에 기본값 아닌 값이 남아 있으면 한 번 올린다. 저장 방식이 바뀌었다는 이유로 이미 설정해 둔 로고가 사라지면 사용자에겐 그냥 기능이 고장 난 것이다. 권한·플랜 때문에 못 올려도 화면에는 로컬 값을 계속 보여 준다.
2. **역할 제한을 새로 건다.** localStorage 시절에는 각자 자기 브라우저만 바뀌어서 아무나 만져도 그만이었다. 서버로 옮기면 한 사람이 바꿀 때 **회사 전체 화면과 인쇄물**이 바뀌므로 관리자로 제한한다.

**결과**
- (+) 기기·브라우저를 바꿔도 브랜딩이 남고 팀원 전체가 같은 화면을 본다. ADR-0003의 두 제약이 해소됐다.
- (+) 캐시에 `cachedTenantId`를 함께 적어, 한 브라우저로 회사를 옮겼을 때 남의 로고가 남던 문제도 함께 막았다(로컬 전용 시절에는 드러나지 않던 결함).
- (−) 로고 data URL이 DB `text` 컬럼에 들어간다. 상한 350KB. 이미지가 커지면 오브젝트 스토리지(MinIO)로 옮겨야 하고, 그때는 다시 결정이 필요하다.
- (−) 테마 색(`themeStore`)은 여전히 localStorage 전용이다. 이번 범위는 로고·배지 문자뿐이다.
- (−) 플랜을 Pro → Starter로 내려도 이미 저장된 브랜딩은 계속 표시된다. 유료 기능을 정확히 회수하려면 조회 쪽에도 플랜 판단을 넣어야 하는데, 그건 화면이 깨지는 방향이라 별도 결정으로 미뤘다.

## ADR-0015 — 내보내기를 동기 처리로 확정하고 ExportJob 테이블을 제거

**상태**: Accepted (2026-08-23). [ADR-0004](#adr-0004--결제를-provider-추상화로-두되-결제-이력-테이블은-미사용)와 같은 종류의 정리다.

**맥락**
`ExportJob` 테이블(`status`·`fileUrl`·`finishedAt`)과 빈 `ExportModule` 이 초기 설계부터 남아 있었다. 컬럼 구성이 말하듯 **비동기 작업 큐**를 상정한 것이다. 그런데 실제로 만들어진 내보내기는 전부 동기다.

- PDF(T-76): `POST /policies/:id/export/pdf` 가 렌더 결과를 **응답 본문으로 바로** 돌려준다
- 전문 인쇄·선택 인쇄(T-74): 브라우저 인쇄
- 템플릿 JSON: 클라이언트에서 파일로 저장

실측: `export_jobs` 행 수 **0**, 이 테이블을 참조하는 코드 **0곳**. `ExportModule` 은 `@Module({})` 한 줄이다.

**결정**
테이블과 빈 모듈을 제거한다. 내보내기는 앞으로도 동기로 간다.

큐를 만들지 않는 이유는 규모다. 규정 하나의 PDF 는 수 초 안에 렌더된다. 작업 테이블·워커·폴링·실패 재시도·만료된 파일 정리를 얹으면, 얻는 것(진행률 표시)보다 잃는 것(운영해야 할 부품)이 크다.

**대신 감사 로그에 남긴다.** `ExportJob` 이 노리던 "누가 언제 무엇을 뽑았나"는 실제로 필요한 물음이다 — 규정 PDF 는 회사 밖으로 나가는 문서다. 다만 그 기록의 자리는 별도 테이블이 아니라 이미 있는 감사 로그다(`policy.export.pdf`). T-11 화면에서 다른 변경 이력과 함께 보인다.

**결과**
- (+) 쓰이지 않는 테이블이 ERD에서 사라졌다. 문서만 읽은 사람이 "내보내기 이력이 있다"고 오해할 여지가 없어졌다.
- (+) 내보내기 추적이 실제로 생겼다 — 테이블이 있던 3개월 동안은 한 건도 기록되지 않았다.
- (−) 나중에 대량 일괄 내보내기(예: 규정집 전체를 한 파일로)가 필요해지면 그때는 비동기가 맞을 수 있다. 그 시점에 다시 결정한다 — 빈 테이블을 미리 두는 것보다 낫다.
- (−) 마이그레이션이 `DROP TABLE` 이다. 되돌리려면 테이블을 다시 만들어야 하지만, 데이터가 없었으므로 잃는 것은 없다.

**T-85(HWP)와의 관계**: HWP 도 같은 방식으로 간다. 변환기가 느리다면 그때 비동기를 다시 검토한다.

## ADR-0016 — 한/글 내보내기를 `.hwp` 가 아닌 `.hwpx`(OWPML)로 구현

**상태**: Accepted (2026-08-23)

**맥락**
대표 지시(8/1)의 "HWP 저장"을 구현해야 한다. T-85가 **"변환 수단 선정이 선행 과제"**라고 적어 둔 대로, 먼저 만들 수 있는 형식을 정해야 했다.

세 가지를 놓고 봤다.

| 후보 | 한/글이 여는가 | 리눅스 컨테이너에서 만들 수 있는가 |
|---|---|---|
| `.hwp` (바이너리) | 모든 버전 | **불가**. CFBF 컨테이너 + 압축 레코드의 독점 포맷이고, 공개 라이브러리는 전부 **읽기 전용**이다(`pyhwp`, `hwp.js`). 쓰기는 한컴 SDK뿐인데 Windows·라이선스다 |
| `.hwpx` (OWPML) | **한/글 2014 이상** | 가능. KS X 6101 국가표준이고 실체는 ZIP + XML |
| `.docx` 로 대체 | 열리긴 한다 | 가능하지만 **"HWP 저장"이 아니다.** 이름을 바꿔 부르는 것은 요구를 만족한 게 아니다 |

**결정**
`.hwpx` 로 만든다. 변환은 `pyhwpxlib`(순수 파이썬, 한컴 오피스 불필요)를 쓴다.

라이브러리를 쓰고 XML을 손으로 쓰지 않은 이유: OWPML의 `header.xml` 에는 글꼴·문단·글자 모양 표가 들어가고 본문은 그 표를 ID로 참조한다(실측 44KB). 이 표가 조용히 어긋나면 한/글이 파일을 **열지 못하고**, 우리는 그걸 확인할 수단이 없다.

구조는 PDF(T-76)와 같다 — 전문 보기가 만든 HTML을 받아 파이썬 서브프로세스로 변환한다(ADR-0008과 같은 방식). 템플릿·토큰 치환·절 계층이 모두 프론트에 있어서 서버가 다시 조립하면 두 벌이 갈라진다.

**결과**
- (+) 리눅스 컨테이너에서 한/글 문서를 만든다. 새 인프라 없이 기존 파이썬 경로에 얹었다.
- (+) 확인한 것: ZIP 무결성, OCF 규약(`mimetype` 이 첫 항목·무압축·`application/hwp+zip`), 필수 파일 8종, XML 파싱, 네임스페이스가 OWPML 규격과 일치, 본문·`①`·가운뎃점 보존.
- (−) **한/글에서 실제로 열리는지는 확인하지 못했다.** 개발 환경에 한/글도 LibreOffice도 없다. 규격 적합성까지가 여기서 검증 가능한 한계이고, **첫 배포 전에 실제 한/글로 한 번 열어 봐야 한다.**
- (−) **한/글 2014 미만에서는 열리지 않는다.** 화면 안내와 툴팁에 적었다. 구버전 사용자가 많다면 그때는 변환 서비스를 붙이는 별도 결정이 필요하다.
- (−) 서식은 문단 수준까지다. 표·이미지·머리말은 변환기가 지원하는 범위를 따라가며, 조판이 PDF와 완전히 같지는 않다.

## ADR-0017 — ESLint를 타입 인식(type-aware) 설정으로 도입하고, 스타일 룰은 두지 않는다

**상태**: Accepted (2026-08-25)

**맥락**
`apps/api`·`apps/web` 양쪽에 `npm run lint` 스크립트가 있었지만 저장소에 설정 파일이 없었다. 명령은 성공한 것처럼 끝나고 아무 룰도 돌지 않았다 — **"있는데 안 도는" 상태가 가장 나쁘다.** 실제로 아무도 몇 달간 눈치채지 못했다(T-32).

설정을 넣는다면 무엇을 잡을 것인가가 먼저다. 이 코드베이스에서 타입체크와 테스트가 **둘 다 통과시키는** 실수는 이런 것들이다.

- `await` 누락. `this.prisma.auditLog.create(...)` 를 기다리지 않으면 요청은 성공으로 끝나고 기록만 사라진다.
- `catch` 없는 async 함수. 실패가 unhandled rejection 으로 흘러가 화면에는 "비어 있음"으로 보인다.
- 죽은 코드. 만들어 놓고 화면에 연결하지 않은 mutation, 아무도 부르지 않는 시드 스크립트.

들여쓰기·따옴표는 이 목록에 없다.

**결정**
1. **flat config 하나를 리포 루트에 둔다**(`eslint.config.mjs`). 워크스페이스별 설정을 두지 않는다 — 룰이 갈라지면 어느 쪽이 진짜인지 알 수 없다. 워크스페이스의 `lint` 스크립트는 루트로 올라가 실행한다.
2. **타입 정보를 쓰는 룰을 켠다**(`recommendedTypeChecked`). 위 목록이 전부 타입 정보 없이는 잡히지 않는다. 대상은 tsconfig 에 속한 소스뿐이고(`apps/api/src`, `apps/web/src`, `tests`), 그 밖의 설정 파일은 문법 룰만 적용한다. 이를 위해 `tests/tsconfig.json` 을 새로 만들었다.
3. **포맷 룰은 넣지 않는다.** Prettier 도 아직 도입하지 않는다(개발컨벤션 4절, 미정). 스타일 지적이 섞이면 진짜 지적이 묻힌다.
4. **에러와 경고를 나눈다.** CI 는 에러에서만 멈춘다. 경고는 지금 고칠 수 없지만 기록해 둘 부채다.
5. **`npm run lint` 는 깨끗한 트리에서 0 을 반환해야 한다.** 통과할 수 없는 lint 는 다시 안 돌리는 lint 가 된다 — 그게 애초에 이 상태가 된 경로다.

**소음을 끈 곳과 이유** (전부 설정 파일에 같은 내용을 주석으로 적어 뒀다)

| 대상 | 처리 | 이유 |
|---|---|---|
| `no-floating-promises` 의 `invalidateQueries` 등 | 예외 허용 | TanStack Query 의 캐시 무효화는 설계상 기다리지 않는 호출이다. 49건 중 40건이 이것이었고, 여기까지 잡으면 `onSuccess` 마다 `void` 를 붙이는 습관이 생겨 **진짜 누락을 덮는다** |
| `no-misused-promises` 의 JSX 속성 | 검사 제외 | `onClick={async () => …}` 은 React 관용 표현이다. 인자·프로퍼티 자리는 계속 잡는다 |
| `no-explicit-any` | 경고 | 370건. 외부 응답 경계에 몰려 있다. 에러로 두면 그날로 `eslint-disable` 주석이 370개 생긴다 |
| React Compiler 룰 4종 | 끔 | 컴파일러를 쓰지 않으므로 "지금 버그"가 아니라 "컴파일러를 켜려면 고칠 목록"이다. 게다가 메시지가 여러 줄이라 켜 두면 출력 정렬이 무너져 다른 지적까지 안 읽힌다(기술부채 #11) |
| `no-unnecessary-type-assertion` (apps/api 만) | 끔 | `apps/api` 는 `strictNullChecks: false` 라 이 룰이 `x!` 를 전부 "불필요"로 본다 — null 이 타입에 없기 때문이다. 지우면 strict 로 올리는 날 다시 붙여야 하고, 그때는 어디에 필요했는지 알 수 없다(기술부채 #10) |

**결과**
- (+) 248개 파일에서 **에러 0 · 경고 384**(`no-explicit-any` 370, `exhaustive-deps` 14). CI `verify` job 에 `Lint` 단계를 넣었다.
- (+) 도입 과정에서 잡은 것: 첨부파일 목록 로딩 실패가 조용히 사라지던 `catch` 누락(`loadTemplates`), 화면에 연결된 적 없는 첨부파일 삭제 mutation, 아무도 부르지 않는 시드 스크립트(`prisma/seed.js`), 부팅 실패가 원인 없이 죽던 `bootstrap()`, `FileReader` 결과가 `[object ArrayBuffer]` 로 둔갑할 수 있던 자리.
- (+) `tests/eslintConfig.test.ts` 가 **룰이 실제로 지적을 만드는지**를 확인한다. "설정 파일이 존재한다"가 아니라 동작을 본다 — 이 프로젝트가 빠졌던 함정이 정확히 그것이기 때문이다.
- (−) 타입 인식 룰이라 느리다. 248개 파일에 약 29초(실측). 커밋 훅에 걸 만한 속도는 아니다 — 그래서 걸지 않고 CI 에만 두었다.
- (−) 경고 384건은 줄어들지 않으면 그냥 배경 소음이 된다. 숫자를 개발컨벤션에 적어 두었으니 늘어나는지만이라도 보이게 했다.

## ADR-0018 — Google 로그인은 초대받은 계정만 받고, `state`를 서명·쿠키로 묶는다

**상태**: Accepted (2026-08-26) · **Superseded by [ADR-0023](#adr-0023--구글-로그인을-없앤다--로그인은-이메일비밀번호-하나) (2026-10-10)** — 구글 로그인 자체를 없앴다

**맥락**
T-42는 "`state` 위조·재사용 방어 검토"였다. 들어가 보니 `state` 자체보다 그 옆이 더 컸다.

`GET /auth/google?mode=login&tenantSlug=<조직코드>` 로 들어오면, 그 조직에 없던 이메일에도 **`viewer` 사용자를 새로 만들어 줬다.** 구글 계정이 있는 누구나 조직 코드만 알면 남의 회사 규정 열람 권한을 얻었다는 뜻이다. 조직 코드는 로그인 화면에 사용자가 직접 입력하는 값이라 비밀이 아니다.

이건 [SRS AUTH-6](../03_SRS_요구사항명세/SRS_요구사항명세.md)("팀원 초대는 admin만 가능")을 정면으로 어긴다. 플랜별 사용자 상한(`maxUsersForPlan`)도 이 경로에서는 보지 않았다.

`state` 는 별개로 `base64url(JSON)` 이 전부였다 — 서명도 난수도 없어서, 공격자가 만든 콜백 URL 을 피해자가 열면 피해자 브라우저에 공격자의 토큰이 심겼다(로그인 CSRF).

**결정**

1. **Google 로그인은 계정을 만들지 않는다.** 조직 합류는 관리자의 사용자 생성(`POST /users`) 한 경로뿐이다. 구글은 **이미 있는 계정에 붙는 수단**이다 — 비밀번호로 만들어 둔 계정에 첫 구글 로그인 때 신원을 연결한다.
   - `mode=register` 는 그대로 둔다. 그건 **새 조직**을 만드는 것이라 남의 공간에 들어가는 일이 아니다.
2. **조직이 없을 때와 초대받지 않았을 때 같은 답을 준다.** 다르게 답하면 조직 코드가 실재하는지를 밖에서 확인할 수 있다.
3. **`state` 는 서명하고, 브라우저에 묶고, 만료시킨다.** HMAC-SHA256 + 난수를 담은 `httpOnly`·`SameSite=Lax` 쿠키 + 10분. 콜백은 성패와 무관하게 쿠키를 지운다 — 재사용 방어가 여기서 나온다.
   - 서명 키는 **`JWT_SECRET` 을 그대로 쓴다.** 새 시크릿을 만들면 아무도 회전시키지 않는 값이 하나 늘 뿐이고, 시크릿 가드가 이미 `JWT_SECRET` 을 지킨다. 용도는 HMAC 입력 앞에 도메인 문자열을 붙여 분리했다.
   - 서버측 저장소(Redis)에 nonce 를 두는 대신 쿠키를 쓴 이유: `REDIS_URL` 은 선택 설정이라(없으면 프로세스 메모리 캐시) 로그인이 그 가용성에 묶이면 안 된다.
4. **`SameSite=Lax`** 로 충분하다. 콜백은 `accounts.google.com` 에서 넘어오는 최상위 GET 이동이고 Lax 는 그 경우 쿠키를 보낸다. `None` 으로 열면 아무 사이트나 이 쿠키를 실은 요청을 만들 수 있다.
5. **판단을 순수 함수로 뺀다**(`google-account-resolution.ts`). OAuth 콜백은 구글 없이는 통합 테스트로 재현할 수 없는 경로다. 분기를 DB 밖으로 꺼내야 실제로 확인할 수 있다.

**결과**
- (+) 남의 조직에 스스로 들어가는 문이 닫혔다. AUTH-6 과 플랜 사용자 상한이 이 경로에서도 성립한다.
- (+) 위조·재사용·만료 지난 `state` 가 모두 막힌다. 단위 13건 + 통합 14건, 보호 장치를 하나씩 빼서 담당 테스트가 실제로 실패하는 것까지 확인했다.
- (−) **동작이 바뀐다.** 전에는 구글 로그인만으로 조직에 들어갈 수 있었다. 이제는 관리자가 먼저 계정을 만들어 줘야 한다. 그 사용자는 "이 조직에 등록된 계정이 아닙니다"를 보게 된다 — 화면에 사유를 그대로 띄우도록 함께 고쳤다.
- (−) 브라우저가 쿠키를 막으면 구글 로그인이 되지 않는다. `httpOnly` 한 개, 유효시간 10분, 인증 경로 한정이라 실질적인 제약은 아니라고 봤다.
- (−) 토큰을 URL 쿼리로 배달하는 문제는 **남아 있다**(기술부채 #12). 세션 전달 방식 자체를 바꿔야 해서 별도 결정으로 뺐다.

## ADR-0019 — `Article.chapterId`는 필수로 유지한다 (ADR-0011 재검토 완료)

**상태**: Accepted (2026-08-28) — [ADR-0011](#adr-0011--절節을-선택-계층으로-추가하되-articlechapterid는-필수로-유지)의 보류 항목을 종결

**맥락**
ADR-0011은 `Article.chapterId`를 필수로 두면서 정석 구조(`chapterId` nullable + `Article.policyId` 추가)로의 이행을 **"테스트 기반(T-30)이 갖춰진 뒤 재검토"**로 미뤘다. 그 조건은 충족됐다(단위 320 · 통합 225). 그래서 실제로 재검토했다.

**측정한 것**

| 항목 | 실측 |
|---|---|
| `Article`을 다루는 Prisma 호출 | 52곳 |
| 그중 `chapter`를 경유해 테넌트·규정을 거는 것 | **17곳 / 6개 파일** (comments · versions · favorites · policies · search · variables) |
| 숨김 장 관례를 아는 코드 | 화면·인쇄·읽어주기·재정렬·가져오기 등 15곳 |
| 관례가 실제로 어긋나 있던 곳 | **4곳** (아래) |

**이행했을 때 얻는 것과 잃는 것**

얻는 것은 **개념적 정합성뿐이다.** 사용자는 이미 "장 없는 규정"을 화면·인쇄·PDF·HWPX·목차에서 정상으로 본다. 이행해도 사용자 화면은 한 픽셀도 바뀌지 않는다.

잃는 것은 구체적이다. 17곳은 전부 **테넌트 격리를 지탱하는 쿼리**다. [T-41 감사](../15_보안검토서/보안_검토서.md)에서 뚫린 두 곳이 정확히 이 종류였다 — "테넌트는 맞는데 그 안의 부모 사슬을 안 본" 경우. 그 코드를 한꺼번에 다시 쓰는 것은, 눈에 보이지도 않는 결함을 이 시스템에서 가장 심각한 실패 유형과 맞바꾸는 일이다.

**이행 쪽의 가장 강한 논거도 적어 둔다** (반대 근거만 적으면 재검토가 아니다): `Chapter`에 `@@unique([id, policyId])`를 두고 `Article(chapterId, policyId)`를 복합 외래키로 걸면, "조의 규정과 장의 규정이 일치한다"를 **DB가 강제**할 수 있다. 즉 비정규화가 조용히 어긋날 위험은 없앨 수 있다. 그래도 17곳을 다시 쓰는 비용은 그대로 남고, 얻는 것은 여전히 사용자에게 0이다.

**결정**
**이행하지 않는다.** 대신 관례가 새는 곳을 막고, 관례를 **테스트로 고정**한다.

이번에 막은 네 곳:

1. **전문 텍스트(.txt) 내보내기가 유령 장 제목을 찍었다.** 화면·인쇄·읽어주기는 `isChapterHeaderHidden`을 거치는데 여기만 거치지 않아 `===== 제1장  =====`이 나왔다. 컴포넌트 안에 있던 문자열 조립을 `policyPlainText.ts`로 꺼내 테스트로 묶었다.
2. **판단 함수가 둘이었다.** 읽어주기는 "제목이 빈 장"도 감췄는데 화면·인쇄는 감추지 않았다. `isChapterHeaderHidden` 하나로 합치고 빈 제목까지 포함시켰다.
3. **보이는 장의 제목을 수정으로는 비울 수 있었다.** 생성(`POST`)은 400으로 막는데 수정(`PUT`)에는 그 검사가 없었다(실측: `{"title":""}` → 200, `title=""`·`suppressHeader=false` 저장). 규칙을 `chapter-header.ts` 한 곳에 두고 생성·수정이 같이 쓰게 했다.
4. **일괄 가져오기는 "장 없는 규정"을 아예 표현할 수 없었다.** 입력이 `policy.chapters[].articles[]`뿐이고 장 제목이 필수라, 넣으려면 **없는 장 제목을 지어내야** 했다 — T-83이 다른 가져오기 경로에서 없앤 바로 그 문제다. 최상위 `policy.articles[]`를 받아 서버가 숨김 장으로 눕힌다.

3번은 이 저장소에서 **네 번째** 같은 유형이다(T-58 템플릿 복원, T-13 일괄 가져오기, T-42 구글 로그인). 코드리뷰 체크리스트에 항목으로 넣었다.

**이 결정을 뒤집을 조건** (다음 재검토는 조건이 생겼을 때만 한다)

- **편(篇)이 장 위에 추가될 때.** 선택 계층이 둘 이상이면 관례로 버틸 수 없다.
- **조가 장 사이를 자유롭게 오가는 것이 사용자 기능이 될 때.** 지금 재정렬(T-60)은 장 안에서 끝나거나 목적지 장을 따라간다.
- **관례가 다섯 번째로 샐 때.** 테스트로 막았는데도 또 샌다면 그건 관례가 감당할 수 있는 복잡도를 넘었다는 신호다.

**결과**
- (+) 격리를 지탱하는 17곳을 건드리지 않았다. 마이그레이션도, 데이터 이전도 없다.
- (+) 관례가 새던 4곳이 막혔고, 단위 24 + 통합 7건으로 고정됐다. 보호 장치를 하나씩 빼서 담당 테스트가 실제로 실패하는 것을 확인했다.
- (+) 일괄 가져오기로도 "장 없는 규정"을 넣을 수 있다 — 세 가져오기 경로(화면·PDF·일괄)가 같은 개념을 같게 다룬다.
- (−) DB상으로는 여전히 조가 장에 종속된다. **"장 없음"은 관례이고, 관례는 새로 쓰는 코드가 모를 수 있다.** 이번에 테스트로 묶은 범위 밖에서 또 샐 수 있다.
- (−) 숨김 장은 `chapters` 배열에 실재하므로, API 응답을 그대로 쓰는 외부 연동이 생기면 "장이 하나 있는 규정"으로 보인다. 지금은 외부 연동이 없다.

## ADR-0020 — 상위 법령을 `Policy`가 아닌 별도 엔티티로 두고, 테넌트 공용으로 저장한다

**상태**: Accepted (2026-09-21)

**맥락**
법제처 연동(`lawgokr`)을 붙인 뒤로 열려 있던 질문이 있었다 — **"가져온 법령을 사내 규정과 어떻게 구분하나?"**
지금까지는 답을 미뤄도 됐다. `lawgokr` 모듈이 요청이 올 때만 법제처를 조회해 보여 주고 **아무것도 저장하지 않는 프록시**였기 때문이다.

2026-09-21에 대표가 특허 명세서(`26PD0271KR_명세서_수정안rev1.docx`)를 "만들 것을 쓴 것"이라고 확인하면서 답을 미룰 수 없게 됐다.
명세서의 청구항 1은 **법령조항 식별자와 사내 조문 식별자를 연결하는 법령 관계 정보**를 저장하도록 요구한다. 저장하려면 법령이 먼저 있어야 한다.

선택지는 셋이었다.

1. **`Policy`에 플래그를 달아 같이 담는다** — `isExternalLaw: true` 같은 컬럼
2. **테넌트별로 복사해 담는다** — 고객사마다 자기 근로기준법 사본을 갖는다
3. **별도 엔티티로 분리하고 참조만 한다** — `Law`/`LawArticle`을 새로 만들고 `LawLink`로 잇는다

**결정**
**3번.** 그리고 법령 데이터(`LawSource`/`Law`/`LawArticle`/`LawChangeEvent`)에는 **`tenantId`를 두지 않는다.**

근거는 취향이 아니라 청구항이다.

- 청구항 1은 *법령조항 식별자*와 *조문 식별자*를 **서로 다른 것으로 전제**하고 그 사이에 관계 정보를 둔다. 같은 테이블에 담으면 이 구조가 표현되지 않는다.
- 청구항 3은 영향 조문 식별이 *"복수의 사내 규정에 속한 사내 조문 노드들"* 에 도달한다고 한다. 즉 **법령 1건 : 사내 조문 N건**(여러 규정·여러 테넌트)이다. 1번·2번은 이 N:M을 테넌트 복사본으로 쪼개 버린다.
- 실무적으로도 근로기준법은 모든 고객사에 같은 내용이다. 테넌트마다 복사하면 **같은 법을 고객사 수만큼 폴링**하게 되는데, 법제처 DRF는 인증값(OC)당 호출량이 제한된다.
- 1번은 더 나쁘다. `Policy`는 플랜 상한(규정 개수)에 걸리므로, 법령을 가져올수록 고객사의 규정 한도가 줄어든다. 개정 이력·버전 워크플로·검색·인쇄 템플릿이 전부 법령에도 적용되는데 그중 어느 것도 법령에는 의미가 없다.

대신 **경계는 `LawLink`가 진다.** 어느 법에 우리 회사의 어느 조문이 걸려 있는지는 회사 기밀이므로 `LawLink`와 `AmendmentCandidate`에는 `tenantId`가 **필수**다.

**결과**
- (+) 법령 1건을 한 번만 받아 모든 테넌트가 참조한다. 법제처 호출량이 테넌트 수와 무관해진다.
- (+) 법령이 플랜 상한·검색·템플릿에 섞이지 않는다.
- (+) 청구항 3의 "관계 그래프"가 자연스럽게 표현된다 — `LawLink`가 간선이고, 법령조항 노드에서 출발해 여러 규정의 조문 노드로 퍼진다.
- (−) **테넌트 경계가 한 단계 멀어졌다.** `LawArticle`에는 `tenantId`가 없으므로 **법령조항 id로 시작하는 조회에는 경계가 없다.** 반드시 `LawLink.tenantId`에서 걸어야 한다.
  T-41 감사에서 찾은 2건이 전부 **"부모 사슬을 안 보고 자식만 확인한"** 경우였고 여기가 정확히 같은 형태다 — 영향 분석·후보 조회의 테넌트 격리 통합 테스트를 **구현보다 먼저** 쓴다.
- (−) 신규 테이블이 6개 늘고 마이그레이션이 필요하다.
- (−) 법령 본문의 정확성 책임이 우리에게 온다. 프록시일 때는 "법제처가 준 것을 그대로 보여 준다"였지만, 저장하면 **우리 DB의 법령이 낡을 수 있다.** `Law.lastCheckedAt`을 노출해 언제 확인한 것인지 화면에서 보이게 한다.

## ADR-0021 — 법령 개정은 **추천**이며, 발행은 사람의 승인을 거친다

**상태**: Accepted (2026-09-21)

**맥락**
제품 방향을 정할 때 두 갈래가 있었다 — **(a) 법이 바뀌면 사내 규정을 자동으로 고쳐 준다**, **(b) 어떻게 바꿔야 하는지 추천하고 사람이 결정한다.**
이 질문이 오래 열려 있었던 이유는, 이 요구사항 자체가 개발문서 어디에도 없었기 때문이다(특허 명세서에만 있었다).

기술적으로는 (a)가 가능하다. 후보 본문을 만들어 그대로 `published`로 넣으면 된다.

**결정**
**(b). 시스템은 개정 후보를 만들어 보여 줄 뿐, 발행은 사람이 승인해야 한다.**

두 가지 독립된 이유가 같은 답을 가리킨다.

1. **법적** — 사내 규정은 취업규칙 신고·이사회 의결 등 **사내 절차를 거쳐야 효력이 생긴다.**
   시스템이 임의로 바꾼 규정은 효력이 없고, 오히려 "규정이 바뀐 줄 알았는데 아니었다"는 더 나쁜 상태를 만든다.
2. **특허** — 청구항 1의 마지막 구성요소가 *"상기 검토 단말로부터 상기 제2 조문에 대한 승인 정보를 수신한 것에 응답하여 … 발행 상태로 전환하는 단계"* 다.
   **사람의 승인이 청구항의 구성요소**이므로, 자동 발행은 청구항 1을 실시하지 않는 게 된다. 보호받으려고 낸 특허의 범위 밖으로 제품이 나간다.

이 결정에서 따라오는 하위 규칙 두 가지:

- **자동 추천된 법령 관계(`confirmState = suggested`)로는 후보를 만들지 않는다.** 확정된 관계만 쓴다.
  틀린 연결이 그럴듯한 개정안을 만들어 내면, 검토자는 근거를 믿고 승인한다. 사람의 승인을 요구하는 의미가 사라진다.
- **후보에는 반드시 변경 근거가 붙는다.** 청구항 6도 *"변경된 부분을 변경 근거 정보와 함께 표시"* 하라고 한다.
  근거 없이 초안만 내놓으면 검토가 형식이 되고, 그러면 (a)와 실질적으로 같아진다.

**결과**
- (+) 제품이 법적으로 성립한다. 개정 이력에 항상 승인자가 남는다(청구항 6의 감사로그).
- (+) 특허 청구항 안에 머문다.
- (+) 후보 생성이 틀려도 손해가 없다. 최악이 "쓸모없는 초안 1건"이지 "잘못 바뀐 규정"이 아니다.
- (+) 후보 생성 방식을 **규칙 기반부터** 시작할 수 있다. 완벽할 필요가 없기 때문이다(청구항 4는 규칙과 언어모델 둘 다 허용한다).
- (−) 개정이 밀릴 수 있다. 아무도 승인하지 않으면 초안만 쌓인다 → 미처리 후보를 알림·대시보드로 드러낸다.
- (−) "자동으로 고쳐 준다"보다 영업 문구가 약하다. 대신 **"놓치지 않게 해 준다 + 근거까지 준다"** 가 실제로 파는 것이다 — 법무 담당자가 두려워하는 건 손이 많이 가는 게 아니라 **빠뜨리는 것**이다.

## ADR-0022 — 결제는 설정이 없으면 닫힌다 — 가격 확정 전 요금제 변경은 플랫폼 관리자만

**상태**: Accepted (2026-10-08, PM) — **가격 확정 전 임시 운영 방침.** 가격 정책(D-02)·실 PG(D-03)가 정해지면 다시 본다. [ADR-0004](#adr-0004--결제를-provider-추상화로-두되-결제-이력-테이블은-미사용)의 "`mock`(기본)"을 대체한다. 작업 T-125.

**맥락**
- ADR-0004 는 `PAYMENT_PROVIDER` 가 비어 있으면 `mock` 으로 두었다(데모·개발 편의). mock 은 돈을 받지 않고 요금제를 바로 올린다.
- 운영 서버는 compose 가 넘기는 환경변수만 받는데, 이 값을 넘기지 않았다. 그래서 **운영이 mock 으로 돌았고**, 고객사 관리자가 요금제 창의 "업그레이드"(월 ₩39,000 확인창)나 "도입 문의" 버튼으로 결제 없이 Pro·Enterprise 를 쓸 수 있었다(0원 테스트 결제로 기록).
- 같은 창에 정해지지 않은 가격·할인·조건과, 서버와 다른 인원 상한(3명/20명 — 서버는 10명/50명)이 나가고 있었다.
- 계정 체계가 "아스트룸이 고객사를 개설"하는 방식으로 바뀌어(T-122), 고객이 스스로 가입·결제하는 흐름은 쓰이지 않는다(D-10).
- 로그인 없이 열린 결제 웹훅은 **비밀키가 설정되지 않으면 검사를 건너뛰었다.** 그런데도 요금제가 바뀌지 않은 건 입력 검증이 본문의 `data` 를 통째로 거부했기 때문이다. 막아 둔 게 아니라 우연이었고, 같은 이유로 정상 결제 웹훅도 처리될 수 없었다.

**결정**
1. **결제 미사용이 기본이다.** `PAYMENT_PROVIDER` 가 비어 있거나 `none`·`off`·`disabled`·`false` 면 결제 미사용이고, 결제 시작은 403 `BILLING_CLOSED`(아스트룸 문의 안내)다. `mock` 은 명시해야만 켜지는 개발용이다. **운영에는 이 값을 넣지 않는다.**
2. **요금제는 통합 관리의 플랫폼 관리자만 바꾼다**(`PATCH /platform-admin/tenants/:id/plan`). 결제가 아니므로 결제·구독 기록은 만들지 않고, 감사 로그(`platform_admin.tenant_plan.update`)만 남긴다.
3. **웹훅은 실결제 서버 + 비밀키 설정 + 같은 값일 때만 받는다.** 결제 미사용·mock 이면 403 `PAYMENT_DISABLED`, 비밀키 미설정은 403 `WEBHOOK_SECRET_NOT_CONFIGURED`, 불일치는 401 이다. 본문을 보기 전에 판단하고, 비교는 응답 시간으로 비밀키를 맞혀 볼 수 없게 한다. `data` 에 검증을 붙여 결제를 켠 서버에서는 실제로 동작하게 했다.
4. **결제 기록 함수도 결제 미사용 서버에서는 거부한다.** 들어오는 길이 새로 생겨도 요금제·구독·결제 기록이 바뀌지 않게 하려는 것이다.
5. **요금제 창은 비교만 한다.** 가격 자리와 버튼은 "아스트룸에 문의"이고, 누르면 안내만 보이며 서버를 부르지 않는다. 인원은 서버 값(Starter 10명·Pro 50명)으로 표시한다.

**결과**
- (+) 설정을 빠뜨린 서버는 닫힌다. 운영 compose 는 이 값을 넘기지 않으므로, `.env.oracle` 에 잘못 넣어도 열리지 않는다.
- (+) 개발·CI 의 docker API 도 결제 미사용이라, 통합 테스트 기본 실행이 운영과 같은 상태를 검증한다. mock·실결제 동작은 API 를 그 설정으로 띄우고 `BILLING_TEST_PROVIDER` 를 지정해 따로 돌린다(`billing-policy`·`billing-records` 통합 테스트).
- (−) 고객이 스스로 요금제를 올릴 수 없고 아스트룸이 처리해야 한다. 가격이 정해지기 전에는 이게 맞는 상태다.
- (−) 플랫폼 관리자가 바꾼 요금제에는 결제·구독 기록이 없다. 유효기간(`planExpiresAt`)은 콘솔에서 직접 넣는다(T-17 이전과 같다).
- **다시 열 때**(D-02·D-03 확정 후): 실 PG 이름을 `PAYMENT_PROVIDER` 에 넣고, `PAYMENT_HOSTED_CHECKOUT_URL`·`PAYMENT_WEBHOOK_SECRET` 과 함께 운영 compose 가 넘기게 한 뒤, 요금제 창에 결제 버튼을 다시 붙인다. 웹훅 본문 형식은 실제 PG 에 맞춰 다시 본다.

## ADR-0023 — 구글 로그인을 없앤다 — 로그인은 이메일·비밀번호 하나

**상태**: Accepted (2026-10-10, PM 지시 "이거 b2b 인데 왜 이게 아직 남아있지"). 작업 T-136. [ADR-0018](#adr-0018--google-로그인은-초대받은-계정만-받고-state를-서명쿠키로-묶는다)을 대체한다.

**맥락**
- 계정 체계가 "아스트룸이 고객사와 마스터를 개설하고, 마스터가 직원 계정을 발급"하는 B2B 방식으로 정해졌다(T-122, 2026-10-08). 공개 회원가입은 운영에서 닫혀 있다.
- 구글 로그인은 개인이 스스로 들어오는 흐름을 전제로 만들어졌다. ADR-0018 로 "초대받은 계정에만 연결"하게 좁혔지만, 계정 연결 판단·`state` 서명·쿠키·콜백 URL 토큰 배달(기술부채 #12) 같은 공격 면과 유지 비용이 남았다. 운영 서버에는 구글 설정이 들어가 있지 않아 실제로 쓰이지도 않았다.

**결정**
- 구글 로그인 경로(`GET /auth/google`, `/auth/google/callback`)와 전략·`state`·계정 연결 코드, 웹의 버튼·콜백 화면, `passport-google-oauth20` 의존성을 없앤다. 경로는 404 다.
- **데이터는 지우지 않는다.** `users.oauth_provider`·`oauth_sub` 열은 남긴다(기록·되돌리기 대비, 마이그레이션 없음).
- 비밀번호 없이 구글로만 만든 예전 계정은 로그인 시 401 `PASSWORD_NOT_SET` 으로 안내하고, 회사 관리자가 비밀번호를 재설정해 주면 들어온다(첫 로그인 때 변경 — T-122).
- 예전 콜백 주소(`/oauth/callback`)로 들어오면 로그인 화면으로 돌린다.

**결과**
- (+) 로그인 경로가 하나라 공격 면·테스트·운영 설정(`GOOGLE_*`)이 줄었다. 콜백 URL 로 토큰이 배달되던 문제(기술부채 #12)도 함께 사라졌다.
- (−) 구글 계정으로 들어오던 사람이 있다면 관리자에게 비밀번호를 받아야 한다. 운영에는 구글 설정이 없었으므로 해당자는 없을 것으로 보지만, 확인은 읽기 전용 점검(비밀번호 없는 계정 수)으로 한다.
- 다시 SSO 가 필요해지면(대기업 고객의 사내 계정 연동 등) 구글 개인 로그인이 아니라 고객사별 SSO(SAML/OIDC)로 따로 설계한다.

## ADR-0024 — 로그인 세션을 기기마다 두고, 자동 로그인은 30일

**상태**: Accepted (2026-10-10, PM 지시 "자동로그인 기능 추가하자"). 작업 T-137.

**맥락**
- 갱신 토큰을 **사용자당 하나**(`users.refresh_token`) 저장했다. 다른 PC·브라우저에서 로그인하면 먼저 쓰던 쪽은 다음 갱신(15분 안)에 튕겼다.
- 서버는 갱신마다 토큰을 회전하는데(T-42) **화면이 새 갱신 토큰을 버렸다.** 그래서 로그인 30분쯤 뒤 두 번째 갱신이 거절돼 모두가 로그인 화면으로 튕겼다. 실제 Chrome 에서 접근 토큰을 6초로 줄여 재현했다(갱신 200 → 401 → 401…).
- 자동 로그인은 "회사 PC 와 집 PC 에서 각자 오래 유지"가 핵심인데, 위 두 가지가 있으면 체크박스를 붙여도 쓸모가 없다.

**결정**
- **세션 표(`auth_sessions`)** — 로그인마다 기기 세션 하나. 토큰에 세션 id(`sid`)를 싣고, 갱신 토큰은 **sha256 해시만** 저장한다. 갱신은 "지금 유효한 해시"를 조건으로 바꿔(compare-and-swap) 같은 토큰의 동시 갱신은 한쪽만 성공한다. 행 잠금 구문은 쓰지 않는다.
- **수명** — 자동 로그인 30일, 아니면 12시간. 둘 다 갱신마다 다시 늘어난다(쓰는 동안은 유지, 안 쓰면 끝남). 자동 로그인이 아니면 화면이 브라우저를 닫을 때 로그인 정보를 지운다 — 탭끼리 공유하려고 localStorage 를 쓰므로, 만료일 없는 쿠키를 "브라우저가 켜져 있다"는 표시로 쓴다.
- **끝내기** — 로그아웃은 그 기기 세션만, 비밀번호 변경·재설정은 모든 세션. **이미 받은 접근 토큰은 예전처럼 만료(15분)까지 통한다** — 매 요청 세션 조회로 즉시 끊는 안은 기존 동작(T-114·T-122: 비밀번호를 바꾼 그 요청 흐름이 이어짐)을 깨고 요청마다 DB 조회가 늘어 택하지 않았다.
- **화면 갱신** — 새 갱신 토큰을 저장하고, 같은 탭의 동시 401 은 한 번만, 탭 사이는 Web Locks 로 차례로 갱신하며 다른 탭이 먼저 갱신했으면 저장소의 새 토큰을 쓴다. 저장소 변경을 다른 탭이 따라간다(로그아웃 포함).
- **배포 이행** — 세션 id 없는 옛 토큰은 저장된 값과 맞으면 한 번만 세션(12시간)으로 옮긴다. 배포했다고 모두를 로그인 화면으로 보내지 않는다.

**결과**
- (+) 여러 기기에서 동시에 로그인이 유지되고, 30분마다 튕기던 문제가 사라졌다. DB 가 새어도 갱신 토큰 원문은 없다.
- (−) 토큰은 여전히 localStorage 에 있다(XSS 에 노출되는 위치는 그대로). httpOnly 쿠키로 옮기는 것은 CSRF 설계가 함께 필요해 따로 다룬다(기술부채 #13).
- (−) 공용 PC 에서 자동 로그인을 켜면 다음 사람이 들어올 수 있다 — 기본 꺼짐, 화면에 안내.
- (−) Web Locks 가 없는 오래된 브라우저는 탭 사이 순서를 보장하지 못한다(같은 탭 안은 보장). 드물게 한 탭이 다시 로그인해야 할 수 있다.

## ADR-0025 — 규정 질문의 외부 AI 전송은 공개·동의로 다루고, 처리 지역은 미국으로 고정한다

**상태**: Accepted (2026-10-14, PM 지시 "145 바로 착수하고 23 문서 작업해" — D-09 재결정). 작업 T-146·T-147. D-09(2026-10-09)의 "기본 켜짐"을 바꾼다.

**맥락**
- D-09 는 고객사 규정 본문을 외부 AI(Anthropic)로 보내도 된다고 정하고, 규정 질문을 회사별 **기본 켜짐**으로 두었다. 계약서 조항은 "영업 몫"으로 미뤘다.
- PM 이 고객사 대외비 규정의 국외이전을 걱정하자, 대표가 슈퍼로이어(로앤컴퍼니) 담당자 메일을 근거로 "같은 방식이면 되지 않냐"고 했다. 메일은 세 가지다 — 자사 학습 미사용, LLM 제공사 약관상 학습 재사용·외부 제공 금지, AWS 저장 데이터 AES-256 암호화.
- 검토(2026-10-12, 공식 문서·법령 원문 대조): 세 가지는 "학습에 쓰나"와 "저장할 때 암호화하나"의 답이고 국외이전(어느 나라에서 처리하나)의 답이 아니다. 슈퍼로이어도 개인정보처리방침에 입력 내용이 OpenAI·Anthropic·Microsoft·AWS(미국)로 간다고 공개하고(개인정보 보호법 제28조의8 제1항 제3호 가목) 그렇게 운영한다.
- 개인정보위 제2024-010-184호(2024.6.12)는 해외 LLM 서버가 데이터를 저장하지 않고 지웠고 학습도 하지 않았는데도, 처리방침에 공개하지 않은 것을 국외이전 위반으로 봤다. 학습 미사용·무보존은 고지 의무를 없애지 않는다.
- VEDA 는 고객사의 수탁자다(고객사 = 개인정보처리자). Anthropic 에 다시 맡기려면 고객사 동의가 필요하다(제26조 제6항). 직원 질문에는 병가·경조사·징계 같은 개인정보가 섞인다.
- Anthropic 1st-party API 에는 한국 처리 옵션이 없다 — 처리 지역은 `global`(기본, 미국·유럽·아시아·호주의 여러 나라)과 `us` 뿐이고 저장은 미국이다. 운영 AI 키는 아직 넣지 않아 실제 전송은 없었다(2026-10-12 확인).

**결정**
- **기본 꺼짐 + 관리자 확인** — 규정 질문은 회사별로 꺼진 채 시작한다(기존 회사도 끈다). 회사 관리자가 외부 전송 고지(받는 곳·국가·보내는 항목·보관 기간)를 보고 확인해야 켜지고, 동의한 사람·시각·고지 판을 회사 행과 감사 로그에 남긴다. 고지 판이 바뀌면 다시 확인하기 전까지 꺼진 것으로 본다.
- **처리 지역 미국 고정** — Anthropic 호출에 `inference_geo: "us"` 를 준다. 처리방침에 적는 "이전 국가"를 사실과 맞추려는 것이다(`global` 이면 여러 나라를 모두 적어야 한다). 단가는 1.1배다.
- **질문 기록 90일** — `ai_qa_logs` 는 90일(`AI_QA_LOG_RETENTION_DAYS`)이 지나면 지운다. 월 한도 계산에는 그달 기록만 필요하다.
- **공개와 계약** — 개인정보처리방침에 국외이전 항목을 두고, 이용약관과 고객 위탁 계약서로 재위탁·국외이전·비밀유지 동의를 받는다(`19_법무문서`, 공개·체결 전 변호사 검토). 질문 화면 고지에 국가·보관 기간·조 목차 전송을 적는다.

**택하지 않은 것**
- **메일의 세 문장만 갖추기** — 법적 고지·재위탁 동의를 채우지 못한다(위 사례).
- **AWS Bedrock 서울 리전 안 처리** — 2026-09-29 부터 Claude 를 한국 안에서만 처리할 수 있지만, 지금 쓰는 모델보다 한 세대 낮은 모델(Opus 5·Sonnet 5)이고 구조화 출력·서버 재시도 모델을 쓸 수 없어 코드를 바꿔야 한다. 국내 처리 요구가 반복되면 다시 본다.
- **국내 모델** — 약관(고객 데이터 활용·영업비밀 입력 금지)과 사내 규정 질의 품질 근거가 부족하다.
- **무보존(ZDR)으로 대신하기** — 따로 신청할 수 있지만 승인이 불확실하고, 받아도 고지·동의 의무는 그대로다.

**결과**
- (+) 고객사 동의 없이 외부로 나가는 일이 구조적으로 없다. 처리방침에 적는 국가가 실제와 맞는다. 질문 기록이 무기한 쌓이지 않는다.
- (−) 기본 꺼짐이라 기능을 켜는 회사가 줄 수 있다. AI 비용이 1.1배다.
- (−) 공공·금융·방산·국가핵심기술 고객은 이 방식으로도 쓸 수 없다(국정원 지침·금융 망분리·국가핵심기술 안내서). 업종 확인과 국내 처리는 수요를 보고 정한다.

## ADR-0026 — 감사 로그는 추가만 하고, 승인·반려 뒤 정정은 원 기록을 가리키는 후속 기록으로 남긴다

**상태**: Accepted (2026-10-24, 코덱스 자문을 받아 개발이 정함 — 사용자 지시 "의사결정이 필요한 경우 코덱스에 문의"). 작업 T-178(PAT-21, 특허 도 12). 보관·파기와 DB 수준 강제는 D-19(대표·PM·법무), 남은 정정 종류는 T-179.

**맥락**
- 특허 도 12: "감사로그를 상태 변경에 따라 추가되는 기록으로 관리하고, 승인 또는 반려 후 정정이 필요한 경우 기존 기록을 삭제하는 대신 정정 사유와 정정 내용을 포함하는 후속 기록을 저장한다."
- 감사 로그(`audit_logs`)는 앱 코드에서 추가만 했지만 규칙으로 정한 것이 아니었고, 정정을 잇는 칸·action 이 없었다.
- 승인 정정에 해당하는 유일한 경로인 시행 예정 철회(T-132 ②)는 버전의 승인자·승인 시각·발행일·시행일을 지우고, 개정 후보를 "반려"로 돌렸다(정정과 반려가 구분되지 않음). 철회된 초안이 원천 후보 id(유일)를 쥐고 있어 같은 후보를 다시 승인하면 500 이 났다(T-178 시험으로 재현).
- 잘못된 반려를 본문 수정 없이 되돌릴 길이 없었다(같은 본문 손질은 400).

**결정**
- **정정 기록의 모양** — `audit_logs.corrects_id`(같은 회사의 원 감사 기록, 자기 참조 FK)와 정정 action, details `{reason, before, after}`. 원 기록은 고치거나 지우지 않는다. 정정 짝(어떤 action 이 어떤 action 을 정정하는가)은 `audit/audit-correction.ts` 의 표 하나에 두고, 정정 기록은 거기 함수로만 쓴다. 서버가 고른 원 기록이 짝이 아니거나 다른 회사 것이면 쓰지 않는다. 원 기록을 찾지 못하면 짐작해 잇지 않고 비워 둔다("원 기록 없음").
- **이번 정정 종류는 둘** — ① 개정 후보 반려 정정(본문을 바꾸지 않고 작성 상태로) ② 시행 예정 철회를 승인의 정정으로(지운 승인 정보·원천 연결을 before 에, 원 승인 감사를 가리킴, 후보는 작성 상태로, 철회된 초안의 원천 연결을 떼어 재승인 가능). T-178 전 철회 초안은 같은 후보를 다시 승인하거나 반려에서 다시 열 때(반려 정정·반려 뒤 손질 — 같은 함수 `reopenRejectedLocked`) 원천 연결을 떼고 그 버전 대상 감사(`version.source_detach`)를 남긴다(다시 열 때는 조문 잠금을 잡고 판정·떼기를 한 트랜잭션에 — 그 사이 초안이 일반 승인으로 발행되지 않게). 그 초안이 이미 일반 승인으로 다시 발행돼 후보를 쥐고 있으면 승인·반려 정정·손질 모두 409(`issued_source`)다. T-178 전에 이미 다시 열린 후보는 이 판정을 지나지 않으므로, 마이그레이션이 발행되지 않은 버전이 쥔 원천 연결을 한 번에 떼고 버전마다 감사(cause `migration`)를 남겼다 — T-178 철회는 늘 떼므로 그 뒤로는 이런 초안이 생기지 않는다. 사유 문구 오기 정정·시행된 승인의 시행일 정정 등은 T-179.
- **상태값은 늘리지 않는다** — 후보 상태는 draft/review/approved/rejected 그대로, 상태 전환 기록에 종류(`transition`/`correction`)를 둔다. 목록 필터·알림·통계가 새 상태를 몰라도 된다.
- **누가** — 회사 관리자(admin)만, 두 번째 승인 없이(승인·반려와 같은 권한). 원 결정자 본인으로 제한하지 않되 정정자·사유를 남긴다. 규정별 승인 권한(PAT-19)·결재선(D-12)이 정해지면 따른다.
- **같은 트랜잭션** — 상태 변경과 그 정정 기록은 같은 트랜잭션에 쓴다(되돌려지면 기록도 없다). 잠금을 쥔 채 다른 연결로 감사를 쓰지 않는다(그 연결이 같은 잠금을 기다리면 멈춘다). 규칙 문서(`.claude/rules/api.md`)의 "감사 로그는 잠금 트랜잭션 밖" 문구를 이 뜻으로 고쳤다.
- **불변성은 이번엔 앱 수준** — 감사 수정·삭제 API·코드가 없고, 생기면 가드 시험(`tests/auditAppendOnly.test.ts`)이 실패한다. DB 트리거·역할 분리(REVOKE)는 회사 삭제 연쇄·시험 정리에 예외 경로가 필요하고 보관·파기 정책(개인정보 삭제권·계약 종료 파기, T-147 변호사 검토)과 얽혀 D-19 로 넘긴다.
- **원 기록 고르기** — 철회의 원 기록은 그 버전의 마지막 철회 뒤에 남은 승인(후보 승인·일반 승인) 가운데 마지막 것이다. T-178 전 철회는 원 기록을 가리키지 않아 "정정됨"만으로는 이미 거둔 승인을 거를 수 없다. 그래서 일반 승인 감사(`version.approve`)를 발행과 같은 트랜잭션으로 옮겼다(커밋 뒤에 쓰면 그 틈에 철회가 끼거나 감사만 빠진다). 반려 정정의 원 기록은 후보를 반려로 들인 마지막 전환의 감사다. 마이그레이션은 T-178 전 철회가 남긴 승인 → 반려 전환을 종류 정정으로 채웠다(상태·사유·시각은 그대로).
- **조회** — 대상(entityType·entityId) 필터, 상세에서 원 기록 ↔ 정정 기록 양방향(대상이 다른 후보 승인 ↔ 버전 철회도 `corrects_id` 로 잇는다), 색인 `(tenant_id, created_at)`·`(tenant_id, entity_type, entity_id, created_at)`·`(tenant_id, corrects_id)`.

**택하지 않은 것**
- **정정 전용 테이블** — 원 기록과 정정 기록을 한 흐름에서 볼 수 없고, 조회·권한·보관을 두 벌 둬야 한다.
- **도메인 표(상태 전환)에만 정정 행** — 후보 밖의 정정(버전 철회)은 담을 곳이 없고, 감사 로그만 보는 사람에게는 정정이 보이지 않는다. 후보 정정은 두 곳 모두에 남긴다.
- **후보 상태 `withdrawn` 추가** — 목록 탭·필터·알림·통계를 모두 고쳐야 하고, 정정 뒤 다시 검토하는 흐름은 작성 상태와 같다.
- **DB 트리거로 UPDATE·DELETE 막기(이번에)** — 위 D-19.

**결과**
- (+) 승인·반려를 바로잡아도 원래 결정과 그 근거가 남고, 누가 왜 바로잡았는지가 원 기록에 이어진다. 철회한 후보를 다시 승인할 수 있다(500 해소).
- (+) 감사 기록을 고치는 코드가 생기면 시험이 막는다.
- (−) DB 소유 계정이면 여전히 감사 행을 고칠 수 있다(D-19). 회사 행을 지우면 감사도 함께 지워진다.
- (−) 감사가 버전 하나를 가리키지 않는 발행(한꺼번에 시행·가져오기)의 철회는 원 기록을 잇지 못한다("원 기록 없음", T-179).
