# 작업 진행

작업 상태의 원본은 작업관리대장(`docs/Deliverables/17_작업관리대장/작업관리대장.md`)이다. 사람의 결정이 필요한 곳에서는 멈추고 묻되, 관례로 정할 수 있는 기본값은 스스로 정하고 알린다.

인자: $ARGUMENTS

## 1. 작업 고르기

- 인자가 T-xxx면 대장의 그 행을 읽는다. 할 일 설명이면 대장에 같은 일이 있는지 먼저 찾는다.
- 대장에 없으면 알맞은 표에 T 행을 만든다: 다음 번호(session-start hook·상태 줄, 쓰기 직전 다시 확인), 우선순위, 완료 정의, **출처 링크**(SRS 절·D-xx·발견 경위).
- 인자가 없으면 칸반 "다음" 줄과 P0·P1 Backlog를 보여 주고 사용자에게 고르게 한다.

## 2. 해설

- task-explainer에게 T-ID를 넘긴다. 받은 해설의 "5. 미결 질문"에 사람이 정할 것이 있으면 선택지와 추천을 붙여 묻는다.
- 사업·방향 결정이면 대장 "결정 대기"에 D 행으로 올리고 이 작업은 멈춘다.

## 3. 구현

- 대장 행 상태를 `진행`으로 바꾼다(여러 세션이 같은 일을 잡지 않게).
- 여러 파일에 걸친 기존 코드 파악은 code-explorer(흐름)나 Explore(위치)에 맡긴다.
- 완료 정의 항목마다 테스트를 먼저 쓴다 — 단위 `tests/*.test.ts`, API는 통합 `tests/integration/*.int.test.ts`. 거부 케이스도 넣는다.
- 변경을 되돌리면 그 테스트가 실패하는지 확인한다(revert-to-verify). 화면 변경은 실제 Chrome에서 확인한다.
- 마이그레이션은 최근 것보다 뒤 시각 이름으로, 다른 세션의 새 마이그레이션과 겹치지 않게 만든다.
- 해설의 "2. 범위" 밖에서 발견한 문제는 고치지 말고 보고 목록에 남긴다(새 T 제안).

## 4. 검사

- `npm run typecheck`, `npm run lint`(오류 0, 경고 수가 늘면 이유 확인), `npm test`.
- API를 바꿨으면 `npm run test:int`(docker API :3001이 최신 코드여야 한다). 다른 세션이 docker를 쓰는 중이면 따로 띄운 API로 돌린다.
- 실패가 다른 세션의 미커밋 변경 때문이면 고치지 말고 그 세션과 사용자에게 알린다.

## 5. 검토

- adversarial-reviewer에게 T-ID, 변경 파일(또는 hunk), 해설의 완료 정의를 넘긴다.
- Critical·High는 고친 뒤 다시 검토받는다. Medium은 보고한다. 검토 뒤에 코드를 고치면 다시 검토받아야 완료 기록이 허용된다(done-gate hook).

## 6. 커밋

- 내 파일만 경로를 적어 올린다(`git add -A`·`commit -a` 금지 — git-guard hook). 남의 줄이 섞인 파일과 공유 문서는 /shared-commit 으로 올린다.
- 메시지: `feat|fix|perf|refactor|test|docs|chore: 한국어 설명 (T-xxx)`. push는 사용자가 요청할 때만.

## 7. 대장 기록

- T 행 상태를 `**완료(MM/DD)** → C-nn`으로, "완료" 표에 C 행을 더하고, 칸반 줄을 고친다. Edit 도구로 고친다(done-gate hook이 검토 기록을 확인한다).
- SRS·ADR·테스트결과서·기술부채대장 등 바뀐 내용이 있는 문서도 함께 고치고, /shared-commit 으로 올린다.

## 8. 보고

완료 정의 항목별 증거(테스트 이름·확인 결과) 표, 검토 결과(등급별 건수와 처리), 커밋 해시, 범위 밖 발견 사항.
